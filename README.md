# Harness Foundry 1.2.2


**用 Codex 为项目搭建可继续使用、可检查、可修复的 Harness。**

Harness 是项目自己的工作规则、工具入口、任务流程、独立检查和运行记录。Foundry 帮助你从需求出发，把这些部分设计、搭建并交付给目标项目；后续使用者依靠交付件和声明的宿主工具继续工作，而不是长期依赖搭建时的聊天上下文。

Foundry 不是另一套模型，也不是固定行业流水线。Codex 负责需求理解、设计和实现；Foundry 核心管理已声明的运行范围、任务依赖、累计预算、独立检查和恢复。搭建 Harness 不等于完成整个业务应用；需要一并开发应用时，应在目标和验收范围中明确。

## 新增能力

### 1. 按需求设计 Harness

新增[内置设计指南](docs/HARNESS_DESIGN_GUIDE.md)，将“需求 → 必须完成的行为 → 实现责任 → 实际调用 → 独立检查 → 交付后使用”串起来。

设计先看原始需求，再选择适合的资料、工具、工作流或项目代码，不要求按任务类型强制分流。已有能力足够时直接复用；没有选用能力包的项目，也可以沿原流程搭建。指南同时明确外层 Codex、实施子任务、Foundry 核心、目标 Harness 和独立检查方的职责。

### 2. 可选能力独立接入和升级

新增显式能力包清单、材料准备、环境绑定、调用前版本核对和目标交付入口。一个能力可以包含方法资料、程序、运行依赖和检查方法，不要求全部做成代码模块。

能力按名称和版本选择，项目配置保存本机位置与业务需求；第三方 SDK 仍由其原安装方式管理。能力准备不自动安装、授权或执行，升级也不会静默覆盖已固定的旧版本。

| 可选能力 | 1.1.0基线入口与用途（本次新版本见第10节） |
|---|---|
| Qt/CMake | `qt-cmake@1/@2`：配置、构建、CTest、报告与环境适配；@2 补充可交付环境接入 |
| Python 环境 | `python-environment@1`：解释器、依赖和原生库观察，绑定启动配置及实际探测交接 |
| DATA | `data-summary@1`：按项目配置执行 CSV 汇总、计数、比率、单位换算及精确小数处理 |
| DOC | `doc-export@1`：结构化文档与引用导出，并接入独立检查 |
| PRD、设计与市场调研 | `host-review@1`：公开工作流、成果快照及真实宿主观察交接；浏览器和检索由实际宿主执行 |
| 只读进度看板 | `local-dashboard@1–4`：观察 Foundry 或目标 Harness 的明确运行范围，展示进度、步骤和历史 |

这些能力在源码的 [capability-adapters](examples/capability-adapters/README.md) 中按版本维护。目标只接收实际需要的公开工具和运行材料；私有预期与检查依赖保留在宿主保护域。通用运行包、独立能力包和完整源码的文件范围不同，应按实际分发清单选择，不能假定一个 ZIP 包含全部组件。

### 3. 保留项目定制的连续升级

新增[组件组装与升级工具](examples/harness-composition-upgrade/README.md)：对照旧组件基线、项目当前文件和新组件版本，形成候选并按显式文件清单应用。

能确定的未冲突变化自动合并；双方都改过且无法直接判断的内容保留为冲突，交给项目实施和独立检查。支持连续版本升级、文件新增／更新／移除和文件级接续；没有可靠旧组件基线时走正常项目增量修改，不猜测覆盖。文件级接续不等于允许重放已完成的业务命令，也不提供多文件事务保证。

### 4. 技术栈环境接入与交付

新增[环境接入约定](examples/capability-adapters/STACK_ENVIRONMENT.md)，首批覆盖 QtCore/CMake 和 Python。它把工具路径、SDK、解释器、启动参数、所需读取路径和实际观察交给搭建、检查与后续运行使用，减少只在开发机终端里补配置的情况。

环境解析、真实探测和业务验收分别记录。路径存在或材料 READY 不代表受限进程能够运行；需要验证时，沿已声明条件进行实际调用。交付不复制开发机 `.venv`、整套 SDK 或临时聊天脚本，使用者在自己的环境中重新绑定所需工具。

其他技术栈可以沿相同清单和交接方式提供适配包，不要求每新增一种工具都改 Foundry 核心；这不表示 Node、浏览器或所有 SDK 已有同等环境适配。

### 5. 只读看板与 Chat 展示

看板可接入 Foundry 控制记录，也可接入目标 Harness 自身的运行记录。画中画与主页面共用状态，按窗口空间展示进度、当前步骤及详情；支持主题偏好和历史查看。

1.1.0基线的 `local-dashboard@4` 提供内嵌与外置显示地址：Chat 通过宿主工具打开 Codex 内嵌页或外置 Chrome；外置页在浏览器实际支持时提供画中画和全屏。页面不自行移动到 Codex 侧栏，也不依赖 User-Agent 猜测所有宿主能力。看板始终只读，不派发、修复、接受或重放业务。

### 6. 更灵活的模型与服务配置

新日常请求默认跟随 Codex 全局模型和推理强度；仍可手动指定，或为对照测试在准备时读取默认值后冻结。不继承当前 Chat 的临时选型，也不改变已有批准配置。

新增通用模型服务配置接入、声明凭据注入和逐命令配置回执。服务凭据按声明交给客户端环境，不作为模型正文或业务工具输入。每次新命令记录实际选用配置；历史恢复使用原记录，不用当前设置改写过去。模型服务访问与检查器的业务联网配置分别管理，支持配置不等于任意自定义服务已经验收。

### 7. 一次完整确认与同范围宿主修正

完整合同和实际运行条件已经齐备时，可使用 `preview-build` → `materialize-build-preview`，一次展示并明确确认合同与运行范围。预览不创建目标、不启动业务，原先分两步确认的方式继续可用。

新增可信宿主的检查器等义修正和技术误阻断处置入口。已核实属于原范围的适配问题，可以保留原批准与累计消耗继续处理；只复验有独立身份，不重放已完成的生产命令。它不允许放宽业务断言，也不代替真正缺失的用户决定。具体条件见 [Build CLI](docs/GENERIC_BUILD_CLI.md)。

### 8. 可选的 RSI 持续改进工具

本次新增 RSI 工具，用于把问题记录、开发验证和候选采用连接起来。这里的 RSI 是**有证据的持续改进流程**，不是自动学习、自动改写自身或自动部署的后台服务。按项目需要选择使用，不要求每个任务都查询 Wiki、执行 TDD 或调用 Reviewer。

| 新增能力 | 能做什么及使用入口 |
|---|---|
| 通用案例导入与归因 | `tools/import_rsi_case.py`：保留来源版本、运行事实、归因假设和证据不足；不自动确认根因。见[案例导入](docs/RSI_CASE_INTAKE.md) |
| Wiki 条件查询与采用记录 | `tools/rsi_wiki.py`：查询明确声明的本地知识集合，记录采用或不采用理由，保留来源、版本、限制和反证撤回。当前是关键词与条件匹配，不是语义搜索。见[Wiki 指南](docs/RSI_WIKI.md) |
| 独立 Reviewer | `tools/rsi_review.py`：准备公开评审请求和既有 Plan 提案，取回绑定报告；实际模型评审复用现有宿主、授权与预算。报告格式通过不等于意见正确，也不接受原产品。见[Reviewer 与 TDD](docs/RSI_REVIEW_AND_TDD.md) |
| TDD 红绿证据关联 | `tools/report_rsi_tdd.py`：关联选中测试的失败、修改和成功，保留整套回归状态；合法补测可记为 GREEN_ONLY，不适用时不强制制造 RED。开发 GREEN 不代替独立验收 |
| 目标 Harness 交付支持 | `tools/prepare_rsi_delivery.py`：准备所选工具、指南、知识及依赖的新目录，由原搭建流程交付给目标 Harness；准备完成不是搭建或验收完成。见[交付指南](docs/RSI_DELIVERY.md) |
| 候选证据与采用交接 | `tools/report_rsi_adoption.py`：关联候选版本、证据、采用理由和维护归属，区分项目已修、主版本已修、实际部署已升级；不自动 apply 或发布。见[采用说明](docs/RSI_ADOPTION.md) |

交付工具使用 Python 标准库；独立 Reviewer 仍需要声明的 Foundry 宿主和 Codex 接收器。知识文件由项目显式选择，不自动扫描私人目录，也不把模型总结提升为已验证知识。缺少知识或暂不采用，不阻断原来的可行工作。

### 9. 按需读取、可选正文去重与增量报告（1.1.0）

控制视图按同一 revision 读取，需要原文时再补读来源；原完整读取接口继续可用。新库可显式选择同库正文去重，默认格式不变，旧库不会自动迁移。开发源码提供[隔离副本转换工具](docs/REVISION_STORAGE_MIGRATION.md)，保留旧事件、累计预算、库外证据和回滚材料；它不随通用运行 ZIP 交付，也不切换活动库。

可选[增量报告入口](docs/RSI_REPORT_HANDOFF.md)使用固定基线与差异重建当前材料，支持分页及原文取回，保留旧失败、原条件、缺失来源和未验依赖。包内 `tools/report_rsi_view.py` 和通用交接辅助脚本只整理、关联和读取材料，不派发业务或生成接受决定。

### 10. 通用连接、功能选择与交付（1.2.0）

通过 [connections.py](examples/capability-adapters/CONNECTIONS.md) 连接目录或ZIP，发现版本、基础资料和Skill；按原准备入口选择全部功能（ALL）或需求对应的功能（ON_DEMAND）。功能、共享文件、调用入口与工具环境分别记录，未选工具不会因共享脚本自动启用。

[功能选择指南](examples/capability-adapters/FEATURES.md)说明真实冲突与决定复用、搭建期依赖及第三方映射。[交付接口](examples/capability-adapters/EXTERNAL_DELIVERY.md)携带所选依赖、公开说明与清单；接收端重新绑定工具，检查器保持隔离。原G/C/N流程保留定制，报告恢复沿原命令取回。

新增 qt-cmake@3、python-environment@2、data-summary@2、doc-export@2、host-review@2、local-dashboard@5、text-count@2、reference-notes@2；旧版本均保留。本发行提供通用 adapter_path 接口，不预装或默认激活任何具体第三方提供方。

## 修复与可靠性改进

| 修复方向 | 现在如何处理 |
|---|---|
| 最终交付依赖（1.2.0） | 按最终形态核对运行与搭建期依赖，保留合法依赖组合 |
| 旧Skill混入新选择（1.2.0） | 只重算采用映射的连接，其他连接及旧入口保持原选择 |
| 第三方决定缺少来源绑定（1.2.0） | 绑定相关来源并在交付前复查；无关变化和同字节迁移复用原决定，不新增审批 |
| 授权原因随错误措辞变化（1.1.0） | 使用稳定原因码区分未授权、撤销、过期、被替代和绑定错误；复用原校验，不放宽权限或清零预算 |
| 参数错误输出不统一（1.1.0） | 公共CLI参数错误按约定输出JSON及非零退出码；帮助与正常调用保持原行为 |
| 报告和库外材料缺口（1.1.0） | 目录遍历失败显式标为待核对，保留其他文件、合法空目录和链接事实；增量报告不因新差异省略旧条件和失败 |
| 授权状态与模型上下文不一致 | 静态准备仍未授权；派发前核对当前 prepared、Plan 和有效批准，再向模型提供对应的实际授权状态与绑定 |
| 预算与限时准备（1.2.2） | 按完整Plan分列首轮尝试、模型调用和检查命令；提醒不足或无返修余量但不阻断。整次模型调用共享限时，沿原授权路径增额或延时，旧消耗不清零。见[准备说明](docs/GENERIC_BUILD_CLI.md#按任务准备次数和时间) |
| 指令文件与目录诊断（1.2.2） | 准备与接收器共用override优先级和链接解析；提前诊断缺失指令文件误填目录，同时保留合法父目录、别名和被有效override遮蔽的目录 |
| 真实批准后的累计增额（1.2.1） | 显式声明增量并沿原接续链重新批准，保留旧尝试；重复请求不重复加额，原接受结果可按条件复用。总额度与各任务统一上限分别核对，新增上限不会自动授予权限。见[具体用法](docs/GENERIC_BUILD_CLI.md#保留累计消耗的显式增额) |
| 跨准备版本预算与合法续修 | 保留原生产消耗和接受复用关系；区分未派发、生产失败与只复验，不因重新准备或恢复重复计数、清零或误判产品失败 |
| 检查器修正后的重复生产 | 完整捕获、产物及效果已核实后，修正检查器另存并绑定新版本，仅执行必要独立检查；历史失败保留，检查通过后才接受 |
| 自动派生授权的撤销 | 派生批准继续依赖原批准；来源或中间批准撤销、到期会阻止后继执行，独立新人工批准按自身范围判断 |
| 中断、重连与报告恢复 | 补齐退出观察与配置回执绑定，识别合法重连和 `declined`；对已完整捕获的历史误判追加核实记录，完整报告只取回，未知结果不推定成功或直接重试 |
| 凭据脱敏影响协议判断 | 保留合法协议事实和重连计数，敏感详情继续脱敏，覆盖跨结构边界的凭据；不限制凭据格式，未知错误仍按失败处理 |
| Qt 构建目录及路径适配 | 正确观察合法 framework 软链接，不因误扫构建目录误判业务失败；补齐工具别名、实际写域与启动依赖核对，保留不同虚拟环境的调用语义 |
| 能力材料合并与检查隔离 | 保留旧版本绑定和诊断，防止同名冲突被覆盖；补齐零选择分支的检查依赖隔离、去重与合并，允许合法公开共享输入 |
| 本机组合网络 | 可以显式同时声明回环网络和指定 Unix socket，旧单模式不自动扩大；实际回环权限包含 TCP/UDP 全端口及接收器可能保留的 DNS 53 例外，不承诺单服务隔离 |
| 看板进度与状态 | 累计已完成工作和当前有效接受分开显示，核实的额外缺陷修复加入新增工作量，而非把历史清零；同一修复链重试不重复计数，补齐真实步骤、历史和 prepared 范围区分 |
| 看板缺失记录与文案 | 单项来源缺口不抹掉其他已知结果；保留原 FAIL/ERROR 和证据引用，PASS 仍要求完整绑定；简化文字时保留异常与原始信息入口 |
| 独立检查与报告附件 | 补齐 DOC 实际导出、正文和引用核对，API 实际状态及未知路由、Qt 公开自检完整 JSON 拒错等断言；原始报告进入归档，清理后从归档取回 |
| 干净源码回归与 Python 启动 | 随源码提供锁定的历史开发规范，不再隐式依赖本机相邻目录；错误 Python 入口尽早给出路径、版本及正确启动方式，运行沿已绑定解释器，不修改全局 PATH |

本次 RSI 实现中的修复与上述新增能力分开记录：

| RSI 修复项 | 修后行为 |
|---|---|
| 来源暂不可读时整条记录丢失 | 保留其他已知记录、原引用和证据不足状态；来源恢复后重新核对，可读来源中的无效引用继续报错 |
| 只复验接受后的 Reviewer 报告取回 | 沿只复验身份和原报告绑定取回完整结果，保留原生产及检查消耗，不重新派发已完成模型任务 |

| Wiki 截断前忽略适用条件 | 先考虑条件匹配程度再按 limit 截断，保留未知、不适用、反例和限制说明；排序不增加硬性过滤或运行门禁 |

搭建验证材料还修正了公开测试入口识别及试验清单的错误分类；这些是验收材料修正，不包装成所有目标 Harness 都新增了通用测试发现能力。具体证据与适用范围见 [WP10 最终交付说明](docs/FOUNDRY_RSI_WP10_FINAL_DELIVERY_2026_10_24.md)。

GitHub 自动生成的 Source code ZIP 是源码快照，不等于已验收的通用运行包。旧项目不会因源码分支更新自动升级，切换前应核对实际加载路径、固定版本、交付材料和已有控制记录。

### 准备环境

- Python **3.11+**；通用运行包只使用 Python 标准库。源码维护所需依赖另见[开发规范说明](docs/DEVELOPMENT_SPECIFICATION.md)。
- 真实 CODEX 执行需要可用、已登录的 Codex 可执行程序及支持所需权限的原生接收器。
- 项目自己的 Qt、CMake、数据库客户端或其他工具按实际需要准备，不要求所有项目安装全部工具。
- 原生验证主要来自 macOS；Linux 上的源码 CI 成功不能证明所有平台的原生沙箱和浏览器行为一致。具体条件见[兼容性说明](docs/USER_GUIDE.md#系统与客户端兼容性)。

在所选源码或运行包根目录，先用 Python 3.11+ 检查入口；使用虚拟环境时，将 `python3` 换成该环境的解释器：

```bash
python3 --version
python3 tools/hffactory.py version --json
python3 tools/hffactory.py --help
```

不要通过复制旧 `.venv` 迁移环境。macOS 下，运行包、输入、检查器、控制库和目标的目录选择应遵循[使用指南](docs/USER_GUIDE.md)，不要放在共享 `/tmp` 或 `/private/tmp`。

### 从一次问题开始使用 RSI

先阅读[RSI 交付指南](docs/RSI_DELIVERY.md)，提供改进对象和版本、原需求、公开验收条件、成功或失败记录、环境、改善目标和可改范围。输入不限于错误日志，也可以是希望降低成本的成功任务。

沿原任务推进：核实问题和维护归属 → 按需查询知识并记录理由 → 固定基线、候选和独立检查 → 在已有授权内开发及复验 → 只拿交付件和声明工具完成新会话使用 → 比较结果并决定采用、拒绝或暂缓。项目业务规则留在项目，工具适配归能力包，通用机制缺陷经核实后归 Foundry。

所有工具使用项目绑定的解释器，完整参数和输入格式见上表链接。准备、导入和报告工具不自行授权或执行业务；实际测试与模型评审仍使用原控制器和分列预算。保留旧版本、失败及累计消耗，完整报告只取回，不为刷新状态重放已接受任务。

收益需比较正确性、首次通过、返修、模型／工具消耗、耗时和人工介入，另列公共设施成本。**本次有限试验尚未证实 RSI 收益**；收益不明显可以暂缓采用，不自动扩样或无限返工。
