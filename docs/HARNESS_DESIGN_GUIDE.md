# 从需求设计可交付的 Harness

本指南帮助 Codex 把原始需求接成可建设、可检查、可在后续任务中使用的 Harness。设计从任务需要出发：先说明要解决什么、交付后怎样使用，再选择已有能力和必要的项目实现。

规范入口仍是[搭建文档政策](GENERIC_BUILD_PLAN.md)；本指南解释怎样运用其中的质量指引，不另设审批、Plan 字段、固定阶段或评分。运行及恢复沿用 [Build CLI](GENERIC_BUILD_CLI.md) 和[运行合同](GENERIC_BUILD_RUNTIME.md)。协议及现有 G1/G2 职责不变。

## 从当前材料开始

先读取原需求、已确认问答和相关现有工程，分清当前事实、期望行为、持续约束与用户尚未决定的事项。材料是需求依据，不是宿主权限。保留完整来源及定位，摘要不能代替原文；具体来源绑定见[来源接入](GENERIC_SOURCE_INTAKE.md)。

设计会话使用实际选定版本的 Skill 和本指南，按需读取[离线素材命名检查](../examples/harness-design/offline-naming.md)或[音频选段与宿主审听](../examples/harness-design/audio-handoff.md)。它们是公开开发说明，不是正式保留测试、唯一正确方案或运行批准。需要验证本次设计实际采用的方法时，引用所选版本、实际加载路径及已有读取或上下文装载记录，关联形成的搭建文档；普通使用不新增日志前置。已经加载的同版材料可以引用已有记录，不为补日志重读、另开模型或新增状态库。需求、环境、依赖没有变化的结论继续复用；有变化时回看受影响部分。

已有外接连接时，先按[连接与加载说明](../examples/capability-adapters/CONNECTIONS.md)读取明确实例和项目的能力目录及基础材料，相关 Skill 按需展开。无连接不增加准备要求，不从组织关键词或电脑全盘扫描选插件。记录实际读取来源及版本，沿用未变材料；连接和准备就绪不等于插件初始化、实际调用或模型采用。所选 RSI 仍沿原交付工具接入，不因连接外包自动启用。

下面六个问题可以合并、调整顺序。它们不是六次模型调用、六个 Workpack、六份文件或六次审批。简单需求用一段具体设计即可覆盖；复杂任务按实际关系展开。

## 六个设计问题

### 1. 要交付什么，之后怎样使用？

明确用户要的是一次业务结果、可重复使用的工具，还是能组织后续工作的目标 Harness。若要求 Harness，只交一份报告或一个示例结果还不够：说明后续使用者、任务输入、加载入口、宿主环境、输出与未决事项怎样交接。

把必要行为和非目标写入现有搭建文档。例如“检查指定目录中的素材名称并给出改名建议”是否包含实际改名，需要按原需求确认；不能把建议功能默认为写文件许可。任务没有要求跨任务复用或性能比较时，不自行追加这些验收义务。

### 2. 原始需求有哪些必须落实的行为？

从原材料提取正常行为、关键异常、全局约束和验收口径，再检查各项由谁实现、在哪里观察。可以使用下面的简短对应表，也可以在正文中说明；不要求新字段或每项单独建模块。

| 原始要求及来源 | 实现位置或责任方 | 独立检查与未决项 |
| --- | --- | --- |
| 当前需要实现的公开行为 | 项目规则、已有工具、宿主动作或其组合 | 应看到的结果、依据；尚缺的用户决定或观察 |

同一需求可由多个部分协作，一项实现也可覆盖多个需求。保留完整交付与实际使用的义务，把它们放到确实能够取得证据的阶段。不要用能力目录反推需求，也不要因现有包没有覆盖某项行为就删掉它。

区分用户决定与实施选择。目标、重要业务口径、权限和不可逆动作的缺口需要真实决定；类名、算法、模块组织及范围内的普通工具顺序通常由实施者选择。来源冲突或无法判定的验收条件明确列出，不猜成既定事实。

### 3. 用谁完成，缺什么？

| 参与者 | 设计时要明确的责任 |
| --- | --- |
| 外层 Codex／可信宿主 | 理解来源、展示设计、核对真实确认与运行范围；需要宿主工具时实际调用并交接观察 |
| Foundry 核心 | 管理已声明范围、依赖、执行、累计预算、独立检查提交与耐久恢复 |
| CODEX 实施子任务 | 在收到的材料、工具、读写域内生产本次产物，返回实际结果和缺口；不能自行决定接受 |
| 可复用能力或项目现有工具 | 按其真实接口提供资料、处理或环境帮助；能力登记与材料准备不产生执行权限 |
| 目标 Harness | 携带项目自己的规则、配置、适配、必要本地步骤及使用入口，组织约定的后续任务 |
| 独立检查方 | 按公开合同和独立预期检查实际产物或资源效果，保留无法判定的部分 |

已有能力够用就复用，缺少的领域行为由项目补齐；不要求为每个职责生成一个代理或服务。零能力包、离线方案、项目自带工具都可以成立。只有真实需求需要时才增加记忆库、路由、数据库、常驻服务或看板。

现有资源接口与边界见 [Build CLI](GENERIC_BUILD_CLI.md)。可选能力以所选分发或能力包实际提供的接口和随包说明为准；没有提供准备器时，继续原搭建路径或使用项目已有工具，不把它当作缺失的必装依赖。提供 `prepare.py` 的分发中，`build_materials(config, output_root)` 返回材料及拟写文件，不执行所选工具；`write_materials` 写新的准备目录。不必为调用准备器选择无关包。

准备器合并原材料、选定版本、环境和检查依赖时，重新组合的 request 不继承旧 `document_review` 或运行调用上下文。按原流程绑定实际确认，不能把材料 READY 当作批准。完整宿主材料及私有检查依赖不交给生产者；标为共享的只能是确实公开的输入或运行依赖。SOURCE 绑定用于来源和依赖关系，不提供每个 Workpack 单独的读取隔离。

选用提供功能描述 v2 的分发时，按实际需求确定 ALL 或 ON_DEMAND，读取功能清单和缺口；共享文件、选中调用入口和工具环境分别核对。第三方原包通过旁置映射接入，不能由连接自动启动上报或初始化。真实未决冲突沿已有合同集中确认，相同有效决定复用，不新增审批。入口见 [功能接入说明](../examples/capability-adapters/FEATURES.md)。

### 4. 这些部分能实际接起来吗？

沿一个公开有效输入推演必要的生产者与消费者：调用谁、传什么、输出交给谁、失败后保留什么。明确参数和数据形状、路径、解释器及版本、工作目录、临时数据、读写域、网络和必要副作用。运行目录、可读目录和可写目录是不同约束。

先使用既有项目配置和工具绑定；确需所选栈的环境帮助时，按对应包随附说明接入。仅当所选分发实际提供 `consume`／`stack_handoff` 时使用这些接口；否则按项目已声明的调用方式处理，不假定它们处处存在。环境解析和其 `prepare_call` 只形成已绑定的调用材料；路径存在、版本字符串匹配或 argv 已生成，都不证明接收器内实际可运行。工具缺失或配置不完整时记录具体缺口，沿现有范围处理，不猜路径，也不由准备结果推断安装或扩大权限已经获准。

运行获准后，尽早让一个有效输入穿过必要步骤并被下游实际消费。它用于发现接口问题，不能替代全部已约定交付；不为此增加切片审批或每项目必跑的通用预检。只检查本次选择及改变的环境条件，适用的既有观察可以复用。

需要临时文件、数据库或服务的检查，引用 CLI 中现有可选资源接口；没有相关需求就不添加。现有资源服务限于单条有限命令，不提供跨命令后台服务管理。若业务确需更长宿主生命周期，在实际合同中说明持有者、调用关系、预算和清理，不能把计划中的接法写成已经具备的能力。

### 5. 怎样判断正确，出错交给谁？

先按公开需求确定应观察的业务结果、合理拒错和独立预期，再让实施方生产。公开调用条件、输入结构和允许的实现自由必须可读；私有测试实例、答案及判定代码保留在保护域。公开开发检查可以帮助实现，但不能替代独立检查。具体接口见[验收合同与检查器对齐](ACCEPTANCE_CONTRACT_ALIGNMENT.md)。

对关键机制区分三件事：声明存在、在适用场景被实际触发、结果满足公开要求。检查器运行、文件存在、HTTP 成功或模型说“完成”，各自只证明有限事实。外部操作还需其实际效果证据；未知保持未知。自动可判的部分与宿主负责的视觉、语义判断分别说明。

有宿主工具需求时，先核对实际调用者。CODEX 子进程不会隐式继承主聊天的浏览器、搜索、设计或媒体工具；`ONE_ATTEMPT` 在一次实施和检查结束后交回，不是中途暂停点。按具体合同可先接受有限的自动准备成果，再由外层实际调用工具并独立审阅，随后由 LOCAL 检查读取受保护证据。每段说明自身能够证明什么，未到实际取证阶段的义务仍保留。无宿主工具需求时不用加入这条交接。

诊断先定位责任：项目规则或局部适配违约回项目；工具环境、检查基础设施或公开合同问题沿各自原入口处理；可复现的 Foundry 公共保证缺陷才回其负责实现。不能通过放宽检查器、篡改原合同或让目标修改控制库解决问题。固定 LOCAL 检查或复制器不具备推理修复能力，真实缺陷应回原生产者或宿主。

沿既有修复、报告恢复与预算记录保留首次失败和实际消耗。完整捕获只取回，不为补报告重放业务；范围内合法修复及必要复验仍可执行。对已接受产物使用现有适用返修入口，不先改接受字节制造漂移。若需保留旧版供比较，应在覆盖前归档实际文件；旧摘要不能恢复旧字节。具体条件和接续方式查 CLI，不由本指南创建新控制器或清零计数。

#### 项目修复与主版本归并

项目隔离修复先解决原范围的问题，是否归并 Foundry 按根因、可复用性和验证证据另作判断。先核对项目实际加载的代码路径、源码/固定包与能力版本；主版本已修而项目仍用旧交付件时，处理升级或漏包，不重复实现同一补丁。仅旧版受影响时明确旧版回补范围。一个合法用法的确定缺陷即可提出归并，不以第二个项目再次复现为前提。

主版本的维护范围包括核心、能力包、Skill/指南及交付工具，按实际责任处理：

| 核实后的原因 | 维护归属 |
| --- | --- |
| 通用授权、执行、累计预算或恢复实现违约；现有通用接口确实无法表达必要行为 | 对应 Foundry 核心实现；新增接口能力与原实现缺陷分别说明 |
| 技术栈工具发现、SDK、环境或启动适配 | 对应能力包及必要公共接入代码；本机位置留在项目配置 |
| 交付漏文件、依赖未声明、解释器启动诊断缺口 | 打包、依赖或启动入口 |
| 可复用的需求理解、设计或交付交接遗漏 | Skill/指南及适用样例，验证所声称的改进 |
| 项目专属规则、算法或局部配置错误 | 目标项目；确有公共机制缺口再提取通用修复 |
| 检查器误报或预期与公开要求不一致 | 对应检查材料或公共检查器维护方，保留原失败及误报依据 |
| 工具未安装、路径漏配或平台权限不足 | 先处理实际环境与已有授权；必要时改进公共配置说明或诊断，不以补丁绕过权限 |

归并建议说明修复的是哪项已承诺行为或新增支持，保留根因与适用版本；项目临时补丁不原样视为通用实现。提取后应能按声明配置使用，不依赖原项目业务 ID、开发机固定路径、未交付脚本或主聊天临时兜底；技术栈/服务适配及合法项目差异可以保留，不为泛化另造框架或扩大支持范围。

验证沿用已有工程要求，并按改动影响补齐：适用的修前失败、修后成功与合法用法对照；受影响的关联回归。已有证据覆盖同版实现、环境及断言时可复用，不重开无关已接受任务。环境包补相应实际工具验证；涉及模型交接或声称改善模型设计效果时，工程夹具不替代必要实际模型验证；授权、预算、恢复变化核对原累计、合法接续、接受复用和完整报告取回，不能重复派发或重复计数。单纯说明性文档修改不新增模型或业务运行。只验证了一个平台、接收器或环境组合时保留其边界，不将 SKIP、模拟或未执行记为真实通过。

交付或环境接入发生变化时，核对修复进入所选包与能力版本、必要依赖及实际加载位置，并按影响在隔离目录/新会话验证交付件和声明工具足以运行，不借开发目录或旧缓存补漏。源码检查通过不自动证明固定包或原部署已更新；未涉及交付的局部文档修改无需据此重打包。

交接中分别记录以下事实，不能互相推导，也不是新增机器状态或顺序审批：

| 状态 | 可说明的事实与边界 |
| --- | --- |
| 项目已修 | 本项目范围的问题已复验；写明隔离副本或实际项目，副本修好不推定原项目已替换 |
| 主版本已修 | 公共维护源已包含修复及相应验证，注明源码/能力版本和归并状态；候选分支或未提交改动仍注明待归并，不能称已合入 main 或已发布 |
| 交付包已包含 | 明确哪个固定包/能力版本包含修复及包内验证，旧包保持原身份 |
| 实际部署已升级 | 目标环境实际加载新版，受影响入口已核对；仅下载新包或修改主源码不算，其他设备/项目不自动继承 |

沿现有问题记录简要交接：实际版本、问题与根因（或待核实）、维护位置、修复与合法对照、验证/未验范围、归并和交付状态及后续动作。可给出“建议归并”“仅留项目”“已有修复待升级”或“证据待补”的结论；无需新文件、字段、登记库或逐项确认。归并建议不授予主线合并、推送或发布权限，也不自动授权额外验证。通用修复的后续归并不作为原项目收尾的新前置，原必要验收仍须满足。

保留旧产物、失败证据、原授权及累计消耗，不因归并、换包或重准备清零；完整捕获只取回。运行中的源码、检查器、固定包和 Readback 不原位替换，安全交回后沿已有适用升级/接续入口处理变化；已批准范围内无需再次确认的工作继续自主推进，只有原规则要求的真实范围变化沿原授权处理。本文不增加控制器、审批、通用限制或 G1/G2 职责，协议2.9、原R3和既有验收分母不变。

### 6. 交付是否足以支持约定的新任务？

从新使用会话的角度检查：只拿交付物、公开任务和声明工具，能否找到入口、绑定环境、提供输入、运行并核对结果，能否读懂已有任务记录和未决事项。目标不能依靠搭建聊天、准备目录里的未交付脚本、私有检查器或开发机的隐含路径。

交付内容由约定用途决定，包括必要规则、代码或宿主工作流、配置、依赖说明、调用入口和检查方法。能力包只交付公开的必要文件；不把完整宿主材料、私有预期、开发机环境 profile 或 `.venv` 当作目标依赖复制。`stack_handoff` 的公开交付仍需目标绑定自己的环境，不等于已经通过实际运行。目标携带自己的规则即可，无须复制整份 Foundry 设计指南。

实际使用验证按已确认范围进行。若约定同版 Harness 承担不同任务，第二任务应改变工作目的和必要操作，不能只换几条输入。规则和入口没有现场改造才可据此报告同版使用；正常业务输出与任务记录变化不等于改版。发现交付缺陷后保留原结果、修复并明确新版覆盖，不能拼接旧版和新版证据声称原版复用已证实。

v2 交付按功能清单固定公开依赖、说明引用和交付后步骤，核对当前适用报告；BUILD_ONLY、未选、SKIP、尚未操作的宿主工作流不计为行为通过。保留当前有效接受状态，不从清单完整性或历史 PASS 推导新任务可用。

## 接入现有建设流程

形成并展示版本化搭建文档，覆盖原政策中的目标、来源、行为、职责、边界、交付、验收及未决事项。示例设计和无状态编译不创建 Program、目标或业务执行，也不替代用户决定。

现有顺序保持为：

1. 加载选定方法及完整公开原材料，形成并展示设计；经实际人工 Review 确认该版本与范围。
2. 按已确认文档准备 Requirement/Plan、来源及独立检查，通过 `record-build-plan`、`capture-build-sources`、`prepare-build-authorization` 进入原有准备流程。
3. 展示实际 Readback：模型及服务、工具、检查器、读写域、网络、尝试和时间预算、有效期等；记录真实运行批准。
4. 在批准范围内建设、独立检查、必要修复及交付后使用，沿 `read-build` 恢复已保存上下文；不增加逐 Workpack 确认。

文档确认和运行批准分别解决内容与权限。二者充分展示后，一条真实回复可以明确作出两种决定，不能默默相互推断。重要合同变化走原 Review／授权流程；普通实施选择沿现有范围自主推进。

最终按实际结果说明哪些行为已通过、哪些仍未验证、限制及后续动作。`PLAN_CHECKS_ACCEPTED`、材料 READY 和工程回归都不单独证明整个 Harness 可用或发行完成。达到约定交付即停止，额外优化另列，不用扩样或重开已接受任务证明方法有效。

## 按需交付持续改进工具

合同选择 Wiki、Reviewer 或 TDD 时，读取 [RSI 交付指南](RSI_DELIVERY.md)，将实际工具、知识版本及使用说明列为交付材料，通过现有来源与生成入口接入。生成的 Harness 应引用自身交付指南，使用声明宿主完成独立评审与结果检查，不依赖搭建聊天。未选用则沿原流程；无命中和不适用不成为门禁。源码／包内验证不替代新会话实际使用。


可选的候选证据关联及通用修复交接见 [RSI 采用说明](RSI_ADOPTION.md)。复用现有组件升级 helper 和源码工程路径；报告不执行升级、不改变授权或预算，未选用的任务不新增记录要求。


持续改进从当前任务的问题、版本和材料开始；按需选择Wiki、开发红绿与独立Reviewer。完整输入、步骤和报告解读见[交付指南](RSI_DELIVERY.md#从一次问题开始使用-rsi)，新建、已有Harness／能力升级及公共源码归并见[采用说明](RSI_ADOPTION.md#使用者如何选择并升级)。工具可用性、特定缺陷修复、比较收益和实际部署分别判断；有限试验未证实收益时不自动默认采用或扩大返工。说明中的假设场景不是实际证据，原权限、预算、恢复及独立验收职责保持不变。


所选 RSI 的外层正常触发、材料恢复和知识集合版本见[修复交接](../examples/capability-adapters/RSI_HANDOFF.md)。设计时沿原选择明确作用范围、分析材料位置和维护者；未选不加前置。原负责人修复，原控制器验收；该宿主接入工程完成不替代目标新会话自动使用验证。

非标准外部包可按[作者入口](../examples/capability-adapters/AUTHORING.md)形成独立候选。优先保留原实现、来源和副作用说明；准备转换不替代真实调用、独立检查及交付后使用。
