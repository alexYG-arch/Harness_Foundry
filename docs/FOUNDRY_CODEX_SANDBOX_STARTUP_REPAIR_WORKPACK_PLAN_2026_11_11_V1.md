## 1. 目标与已核实问题

目标是让已声明的 Codex 接收器在实际沙箱条件下使用一致的入口，尽早发现可确定的准备错误，并准确交回启动失败；减少把环境问题推入生产尝试、业务返修或重复人工处置的情况。保留已有授权、同范围纠正、累计预算、独立检查与报告恢复机制。

## 4. 最小行为设计

### 4.1 Codex 入口统一，普通工具保留语义

只在 **Codex 接收器专用准备/解析链** 处理普通链接：保留用户输入入口，记录解析后的实际路径和必要的已有文件身份，生成供配置读取、预检和实际启动共同使用的绑定。可复用现有 `model_defaults_source` 的身份内容；手动模型和 LOCAL receiver 不能漏掉。是否需要一个小型公共 helper 在 WP01 决定，不新增接收器控制器。

对脚本包装器，不通过搜索其内容猜测另一个“真正 Codex”后绕开包装器；保持其既有调用语义，并用同范围实际诊断核实。遇入口语义不能判定时，准确报告需要明确的启动方式，不把所有别名或包装器一律禁止。

旧 prepared 按原绑定解释，不回写为新路径。新准备将实际入口及必要变化呈现在现有 Readback；旧任务若需变更入口，沿原 rebind/纠正资格核对权限和版本，不能只因二进制摘要相同就认定扩大读取无需授权。旧报告读取不要求升级旧 prepared。别名、解析目标或实际二进制发生相关变化时，按已有绑定规则重新核对，不扫全目录生成新哈希体系。

`LocalCommand.prepare` 保留 Python venv 的 argv[0]；不把这次 Codex 特定启动语义推广为“所有程序都用真实二进制路径”。只读来源及工作区别名也保持已有合法语义。

### 4.2 纯检查前移；真实探测与批准分开

把已有 `CodingCommand.validate` 中可无副作用判定的状态目录、配置来源和路径检查抽为可复用逻辑，准备/预览与实际派发使用同一逻辑。工作区尚未创建、未来产物尚不存在的合法准备不能因复用运行态检查而被误拒。只核对该分支已有声明，不要求所有任务添加环境表。

状态目录保护维持不变：公开来源可以在项目或独立准备目录按原字节另存并绑定；不开放整个 `.codex`，不移动原证据。全局 AGENTS 的已有精确单文件例外保留。

真实诊断使用所选 Codex、当前有效权限、声明目录和现有接收器，以 `--version` 等无模型命令检查实际入口。静态准备没有执行授权时，只生成诊断范围，不暗中执行探测；工程环境诊断可沿已授权工程范围执行。首次接入或相关环境变化时补诊断，适用证据可复用，不把全套诊断强加到每个 Workpack。

同一已批准调用中的必要探测计入其实际耗时，不重置每命令剩余时限或授权到期时间；单列宿主工程探测的命令和用时，不计成模型 turn，也不伪装为免费生产任务。派发前仍做轻量当前身份/批准复核。

探测需要绑定实际入口、影响它的路径和权限配置、cwd、Codex 版本及是否受外层限制。仅 `help`、`true` 或 `--version` 成功不能证明 AGENTS helper、模型会话或业务已通过。当前没有经核实的公开“零模型完整会话启动”接口，不编造该命令；完整会话链由 WP05 实际验证。必要时使用已安装 CLI 支持的 denial 日志诊断，缺少系统日志权限就保留未知，不能借诊断扩大权限。

### 4.3 失败事实与原生状态分开

下表是需要表达的事实，不要求新增同名状态枚举或一套状态机；优先在现有结果及命令回执中增加最少的可选诊断信息。旧结果缺字段时按旧语义读取。

| 条件 | 记录与交回 | 不能推出的结论 |
| --- | --- | --- |
| 纯校验同步拒绝，包装器可以证明未进入进程启动 | 保存前置拒绝原因、实际绑定及未启动事实；准备阶段不记生产尝试；若旧流程已经记尝试，原消耗保留 | 不能清除同尝试内更早命令的副作用；不能只因缺 started.json 就认定未启动 |
| Codex 父进程启动，helper execvp 失败、没有会话终态 | 保留父进程启动与 helper 失败两个事实，归为启动/环境诊断，不记业务断言失败 | 不能写成“Codex 从未启动”；不能仅凭 stderr 将整个尝试改为 NOT_DISPATCHED |
| 已有模型/工具执行，随后出现同一错误文本 | 保留已发生的工具、用量和效果，按原恢复条件处理 | 不能按关键词退款或自动重放 |
| 零退出并有 PATH aliases 警告 | 保存警告和零退出；按实际被测命令给局部结论 | 不自动判失败；也不据此宣称模型或业务通过 |
| 超时、截断、缺退出、观察丢失 | 原始记录保留；完整捕获可取回则只取回，否则沿原未知效果处置 | 不用 PID 消失、空目录或自然语言成功声明代替原恢复证据 |

准确记录前置拒绝，应在接收器能够证明的同步边界返回现有结构化失败；不把 `BuildController` 的总异常兜底普遍改成已结清，也不扩大现有 `NOT_DISPATCHED` 或技术纠正资格。若某个旧 BLOCKED 不符合 `resolve_technical_attempt` 的完整捕获及效果要求，继续使用原可适用恢复入口，不为本计划放宽该函数。

### 4.4 交接、报告及预算

诊断附着于已有准备或 command 身份。实现前明确最小字段对应关系：用户入口、有效入口及版本引用、所处阶段、实际进程/会话观察、原退出及输出引用、现有恢复建议；具体机器字段在 WP01/WP03 同版确定，不能与原字段冲突或制造第二份权威状态。

读取历史报告不重新构造当前配置或调用当前 Codex；清理成功后仍从原归档取回。新增启动诊断不替换旧失败；敏感配置、凭据、原生错误详情仍沿现有脱敏链处理。重复读取或重试同一个登记不新增执行/扣额。

本计划不调整“已记生产尝试是否耗额”的规则。准备阶段提前拒绝意味着尚未开始一项新尝试；已存在的旧消耗、原接续链和真实额外成本全部保留。产品当前是否有效接受，与启动故障修复、模型 turn 是否发生分别展示。

## 5. Workpack 拆分和顺序

顺序：**WP00 → WP01 → WP02 → WP03 → WP04 → WP05**。共享 `build_runtime.py`、`coding_process.py` 的改动依次整合；可提前准备后续独立检查材料，但不提前记运行通过。每个行为包都包含自己的针对性测试，不等最后一包才验证。
