# Foundry 通用更新：Workpack 拆分与执行方案 v0.1

日期：2026-09-18。上位计划：[通用更新计划 v0.2](FOUNDRY_GENERIC_CODEX_HARNESS_UPDATE_PLAN_v0_2.md)。状态：`ENGINEERING_IN_PROGRESS`。

本文将上位计划 W0–W7 的八个主题拆为十三个可交付工程工作包，规定先后顺序、输入输出、验收与失败返回。它是修复 Foundry 源码的执行方案，不是已经生成的目标 Workpack、授权记录或运行状态。2026-09-18 用户授权“执行方案”后启动工程；包级进度与未闭合项统一记在现有 Tracker，历史证据仅作为基线复用。

2026-09-19 的运行缺陷细化见 [R0–R5 可靠性修复执行方案](FOUNDRY_RUNTIME_RELIABILITY_WORKPACK_EXECUTION_v0_1.md)。
该细化仅制定方案，补充原工作包的实施与验收顺序，不替代 W0–W7、不改变实际权限或已记录进度。

## 1. 执行原则和权限边界

2026-09-19 后续用户修订优先：所有 Harness 搭建需求保留问答，先输出搭建文档，经真实人工
Review 后再进入 Foundry。W1B 消费已确认文档，Coding 场景含开发内容；W5A 增加跨路由的
真实 Review 绑定与变更失效；W6 同步正式入口；W7/M1 重新准备输入与覆盖映射，旧 PRD
直入结果不算新流程验收。详见 [入口合同](GENERIC_BUILD_PLAN.md#搭建文档与人工-review-统一入口2026-09-19)。
程序门禁已接入公开入口，新案例仍待运行，不提前标 DONE。问答结束、后台 PASS、旧批准或委托均不能代替
文档交付和用户确认；这不是每个 Workpack 都增加审批。

- 工作包固定要解决的问题、产出和验收；Astra 自主选择内部调查、实现、调试和局部拆分方式，不冻结逐工具操作配方。
- 保留已验证的通用生成、启动和控制能力；剔除专项时同步处理 Producer、Validator、Schema、指令、测试和发行清单。
- 新通用链 Hash 只允许上位计划 H1/H2 基本用途，不以更多摘要、回执或审批推进工作。
- 在已批准的工程范围内连续执行、修复和复验；包与包之间没有额外“继续”或人工签字门。缺失的用户决策、权限扩大、超预算和不可核实副作用仍是停止条件。
- 普通 Foundry 源码修复、测试不等于真实目标执行。真实模型调用、目标根目录、隔离加载验收必须由实际运行范围覆盖；Git 推送、正式发布不能从“执行修复计划”自动推定。
- 现有 authoring-only 限制须在 W5A 中明确分路线修订；不能靠本计划文字绕开正在生效的 AGENTS、Skill 或平台权限。受保护目录由执行时的正常权限机制处理，不提前索取无关权限。
- 本轮不创建 Program、Candidate、Execution Root、目标 Workpack 或 Driver，不产生任何运行批准。

## 2. 工作包总表与依赖

下表的“前置”指共享合同/实现已集成、局部验收已通过。W0 后可提前阅读、设计独立测试和准备材料，但不能将未完成依赖冒充可执行能力。

| 包 | 唯一交付目标 | 前置 | 主要归属 |
|---|---|---|---|
| W0 | 基线、需求范围与最小接口对齐 | 无 | 集成负责人 |
| W1A | 专项从通用生产路径剔除 | W0 | 生成与合同 |
| W5B | Hash 最小化合同及实现 | W1A；设计/盘点可与 W1A 并行 | 共享合同/状态/校验 |
| W1B | 已确认搭建文档的场景适配，含 Coding 开发内容 | W1A、W5B | 需求与生成 |
| W5A | 指令、建设授权与真实停止点 | W1A、W5B | 授权与宿主指令 |
| W2 | Codex 与本地步骤的统一执行接口 | W1A、W5B；真实执行需 W5A | 执行器 |
| W3 | 独立验收、事务提交与能力消费 | W1A、W5B | 验收器；控制提交由集成负责人合入 |
| W4A | 依赖推进与有界自动修复 | W1B、W2、W3、W5A | 集成/控制 |
| W4B | 中断恢复和受影响证据失效 | W4A 的任务/attempt 接口 | 集成/恢复 |
| W6 | 面向新用户的 Codex 接入与可移植交付 | 最终依赖 W1–W5；依赖/文档盘点可提前 | 打包与接入 |
| W7A | 完整 PRD 新工程的真实建设验收 | 早期联通用最小切片；包级关闭需 W4B、W6 | 验收执行 |
| W7B | 既有工程适配及留出场景验收 | W7A 包级通过、W6 | 验收执行 |
| W7C | 缺陷与发行内容闭合 | W7A、W7B，全部必要回归 | 集成/发布准备 |

W5B 提前执行，是为了避免执行器、验收器完成后再整体改写 Hash 合同。W1A 与 W5B 都会改共享 Producer/Validator，代码合入顺序固定为 W1A → W5B。它们可以并行调查，不能同时写同一文件。

## 3. 波次、并行和里程碑

```text
W0
 └─ W1A → W5B                         共享合同串行合入
             ├─ W1B                   PRD／项目适配
             ├─ W5A                   指令与建设授权
             ├─ W2                    Codex／本地执行
             └─ W3                    独立验收与提交
                    ↓
              W4A 最小切片 → M1       尽早真实 Codex 纵向联通
                    ↓
              W4A 完整闭合 → W4B
                    ↓
              W6 → W7A → W7B → W7C
```

W6 的依赖声明、接入说明以及 W7A/W7B 的需求/验收设计，从 W0 后即可准备。上图表示最终集成顺序，不要求所有准备工作等待前面全部完成。

### 3.1 里程碑

| 里程碑 | 允许作出的结论 | 不能作出的结论 |
|---|---|---|
| M0：W0/W1A/W5B 共享合同切片 | 新路径无专项依赖，Hash 基本用途和接口明确且有回归 | 已能自主建出可用 Harness |
| M1：早期纵向联通 | 真实 Codex 实施 → 本地处理 → 独立验收 → 两个依赖任务接续；一次缺陷被拒绝并修复 | 全部场景/恢复/发行验收通过 |
| M2：W4A/W4B 完整范围 | 约定依赖、修复、预算、取消/恢复场景得到真实验证 | 他人可安装使用或全平台支持 |
| M3：W6/W7A/W7B | 同一发行候选包在独立接入环境完成两类 Coding Harness 场景 | 真实第三方用户试用或已经公开发布 |
| M4：W7C | 承诺范围内无已知未解决缺陷，发行内容可发布 | 没有未知缺陷；已获推送/发布授权 |

M1 可以使用 W1B/W2/W3/W5A/W4A 内已局部验证的最小实现，不等待这些包的全部边界 Case 完成。先进行有边界的真实联通，再补包内剩余义务；没有通过完整包验收前仍记录未完成，不借 M1 提前关闭工作包。这样避免“所有抽象都完成后才首次运行模型”，也不删减最终要求。

### 3.2 并行写入规则

1. 一个文件同一时刻只有一个编辑归属。`compiler.py`、`validator.py`、`service.py`、`cli.py`、`control_kernel.py`、共享 Schema 与核心回归由集成负责人安排串行合入。
2. 执行器与验收器可独立实现；接口变更先更新共享定义，再由消费者适配。禁止各建一份状态机或用临时 JSON 取代 SQLite 权威状态。
3. 打包文档、示例材料和留出验收预期可独立准备，但不得在看到实际错误输出后修改预期来制造 PASS。
4. 同一工作树运行完整回归时暂停相关源码写入，保证结果对应稳定版本；否则明确将该次结果记为不能用于集成关闭。无需为此新建 Hash 锁系统。
5. 仅在用户或工程指令允许并行 Agent 时委派。建议最多一名集成负责人、两名实现者、一名复核者；资源不足则串行，不以多 Agent 数量作为验收要求。角色可由同一 Agent 分阶段承担，但不能声称因此获得外部独立认证。

## 4. 各工作包执行卡

### W0 — 基线、范围和最小接口

- **输入：** 主计划、当前 Git 状态、现有九个工程修改及后续计划文档、旧核心/生成/启动证据。
- **工作：** 核对哪些现有改动已完成局部验证、哪些仍有缺口；把 G1–G13 映射到实现与验收。定义需求、可修订计划、任务输入输出、授权、验收提交的必要边界，避免先扩展平台框架。
- **产出：** 简短接口说明、职责/文件归属、源码修改基线、验收场景和支持环境清单；更新现有 Tracker，不新建第二套工程状态系统。
- **验收：** 保留原有修改；旧核心完成与新目标未完成清楚分开；每项新增要求有负责工作包与可观察结果；没有私有目标 ID 或媒体产物进入新接口。
- **失败返回：** 发现业务范围不清，仅澄清相关问题；发现既有实现损坏先记录并修复，不用重置工作树来获得干净基线。

### W1A — 专项剔除与通用生产基础

- **输入：** W0 接口、主计划 §1.2 剔除清单、专项来源与现有测试。
- **改动归属：** Producer、`semantic_contracts.py`、对应 Validator、Schema、模板/指令及打包引用；共享文件串行编辑。
- **产出：** 无视频/指定 Skill/历史 epoch/固定案例绑定的生产路径；专项条目逐项删除、通用化或非运行归档；保留下来的回归改为领域无关错误形态。
- **验收：** 普通非视频输入可生成合同；生成结果不注入专用阶段/工具/仓库；原通用生成与启动有效；包引用不再拉入专项实现。只搜不到关键词不足以通过，必须检查实际生产行为。
- **失败返回：** 被移除代码仍被通用路径依赖时，抽取必要通用机制后再删除；不将专项换名藏进 Core，也不通过删掉适用测试闭合。

### W5B — Hash 最小化

- **输入：** W1A 新路径、H1/H2 白名单、现有 Hash 消费者与历史读取要求。
- **改动归属：** 状态修订/事务、授权和引用合同、Producer/Validator、Schema、打包；与 W1A/W3 共用处由集成负责人处理。
- **产出：** 对白名单外摘要使用稳定 ID、版本、事务和幂等键替代；删除无消费字段和重复/递归链；旧不可变状态仅隔离读取。
- **验收：** 新工程正常运行无需人工 Hash；同一步骤不重复遍历全树；关键被验对象变化仍会使对应结果失效；重复操作/并发版本冲突仍被正确处理；Producer、Validator、运行消费者使用同一新合同。
- **失败返回：** 必要保护失效时修复版本/事务/作用域设计，或在 H2 的必要对象边界使用基本摘要；不得恢复全量 Hash 网络或仅放宽 Validator。不得重写历史授权/事件链。

### W1B — 搭建文档输入及 Coding 场景适配

- **输入：** W0 的公开业务需求与验收、W1A/W5B 通用合同、经人工确认的搭建文档及原始追溯材料；Coding 场景含完整 PRD、开发需求和既有工程约束。
- **改动归属：** 输入理解、`service.py` 的缺口处理、需求到任务/产物的生成；目标业务代码只进入目标工程。
- **产出：** 上游问答与可读搭建文档交付、确认内容到需求/验收的对应、必要问题/显式假设、项目适配的 Coding Harness；既有工程有复用和不相关修改保护策略。
- **验收：** 自然语言、问答和结构化资料都先输出文档；完整资料不被重复追问，但仍等待真实文档确认；缺页/附件缺失/语义冲突不会被自动编造补齐；需求中的功能、状态、数据、异常与验收没有静默遗漏；产物不是只有 AGENTS.md 或空壳测试。真实开发使用由 W7 验收。
- **失败返回：** 合同表达问题回 W1A；实际需求歧义返回用户；实现选择由 Agent 自行处理，不要求用户设计内部类与函数。

### W5A — 指令、建设授权与停止点

- **输入：** W0 的权限边界、W5B 的新引用方式、当前 authoring-only 与运行授权接口。
- **改动归属：** `runtime_authorization.py`、宿主指令、Skill/AGENTS、生成 Prompt 和授权入口；修改 Skill 时另按 skill-creator 要求实施。
- **产出：** 清晰区分上游文档准备、实际人工 Review、仅 Authoring 和完整 Build；所有搭建入口检查真实 Review 与当前内容绑定，重要内容变化失效。一次明确建设范围覆盖已允许的模型调用、局部实现/修复、本地验证与隔离加载。旧委托和授权不自动升级。
- **验收：** 未确认文档、Agent 自批、后台 PASS 直启、旧批准/委托以及兼容路由绕过均拒绝；真实确认且内容一致后可接入。Review 本身不创建目标或运行模型；正常链路不逐包索要“继续”；缺少真实授权不能执行；范围扩大、撤销、过期、预算与未知副作用得到正确处置；平台限制未被绕过；文档没有把授权理解为验收 PASS。
- **失败返回：** 与平台或现有指令冲突先修正合法路由，不能关闭权限检查。真实执行范围未确定时继续源码/本地测试等不依赖它的工作。

### W2 — Codex／本地统一执行

- **输入：** 通用任务合同、W5A 的可用授权接口、已明确的宿主和模型配置。
- **改动归属：** `coding_process.py`、`coding_protocol.py`、`coding_runtime.py`、`local_runtime.py`；CLI 路由由集成负责人合入。
- **产出：** 同一控制链中可调度 Codex 与本地步骤，真实进程观测绑定任务/attempt，输出可由下游消费；明确模型完成与任务验收的不同含义。
- **验收：** 本地过程与事件分类测试通过；M1 中实际 Astra/Codex 写出可用实现，本地步骤消费其产物；没有模型服务权限时正确停止；未知/截断结果不被当作成功或自动重放。仅 TEST 进程通过最多算局部验证，不能关闭真实模型项。
- **失败返回：** 宿主不兼容返回明确缺口；先修适配器，不静默换模型/SDK、不伪造输出；缺少账户或权限时不影响其他本地工作包。

### W3 — 独立验收与控制器提交

- **输入：** 通用验收义务、任务观测与产物、现有协议证据切片、W5B 新合同。
- **改动归属：** `workpack_acceptance.py`、`workpack_evidence.py`、`project_verification.py`；验收事务接入现有控制内核。
- **产出：** 适用义务的执行验证、当前证据判定、SQLite 验收提交、能力消费和可重建视图；不创建第二状态库。
- **验收：** 行为正确的结果通过；Schema 正确但功能错误、错 Job、陈旧产物、缺义务和任务自报 PASS 被拒绝；验收提交先于后继能力；视图写失败可从已提交事件重建；不存在“任务写自己的权威验收”循环。
- **失败返回：** 验证器缺陷修 W3，产物缺陷回所属 Producer/执行包，合同遗漏回 W1；不得通过删除义务、改预期或返回默认 PASS 消除失败。

### W4A — 自动推进与有界修复

- **输入：** W1B 任务依赖、W2 实际结果、W3 验收提交、W5A 授权范围。
- **改动归属：** 现有控制内核、运行调度与修复路由；共享控制代码单一编辑归属。
- **产出：** 就绪任务选择、不同执行器接续、失败定位与范围内新 attempt、停止解释。实施计划允许调整，但用户目标和验收不可被改写。
- **验收：** 两个存在实际依赖的 Workpack 自动接续；前置失败阻止后继；一次有预期的功能缺陷经真实修复后复验通过；超预算不无限重试；没有新增无必要 Human Gate。
- **失败返回：** 依赖定义错回 W1，执行问题回 W2，误验收回 W3；不靠硬编码 next-node 或直接编辑状态库跳过问题。

### W4B — 中断恢复与失效传播

- **输入：** W4A 的实际任务/attempt 生命周期、已有恢复实现、可观察的进程与产物。
- **产出：** 受支持的结果核对、有限恢复、变化影响范围及未决状态解释；保持已完成工作和原预算累计。
- **验收：** 覆盖派发前、结果已观测未提交、已提交视图缺失、进程仍运行/退出但结果缺失等不同情况；已确认副作用不重复；未知结果不盲目重放；修改相关输入只失效必要后继；撤销/过期不被恢复绕过。
- **失败返回：** 能核实的先核实；不能核实则说明具体未决状态并保留现场。恢复不能承诺外部 exactly-once，不能通过重新创建 Program 重置历史与预算。

### W6 — 新用户接入与发行包

- **输入：** 已集成的新路径、现有打包器、明确的宿主/依赖支持范围、用户接入步骤。
- **入口验收：** 发行包中的 AGENTS、Skill、CLI 帮助和快速开始统一为“问答 → 输出文档 → 人工确认 → Foundry”；从包外启动同样不能把后台自检当确认。指令静态校验不替代 W5A 的实际程序门禁测试。
- **产出：** 一条经过验证的正式 Codex 接入方式、可移植 Foundry 包、目标 Harness 包、快速开始、最小示例、依赖/许可与恢复说明。准备实际包属于后续工程执行范围，本计划不提前打包。
- **验收：** 新会话和干净用户配置能按说明接入；所需规范/运行资源全部随包或按声明取得；不访问原 workspace、作者凭据或隐含 sibling；不覆盖用户原设置；H1 足以核对发行归档，包内无专项实现。
- **失败返回：** 包缺资源或步骤回 W6；构建行为缺陷回 W1–W5。不能靠在验收机临场改目标源码或从开发目录手抄文件通过。

### W7A — PRD 新工程验收

- **输入：** 明确 PRD、预先确定的验收、真实执行授权。早期 M1 使用最小切片；最终使用 W6 发行候选包。
- **产出：** Foundry 生成的 Coding Harness、该 Harness 下完成的应用/命令、实际测试结果、缺陷修复与续跑证据。
- **验收：** 从需求到 Harness 再到真实开发结果全部连通；验收范围内功能完整；失败修复与恢复已观察；包级运行不能引用开发仓库。早期源码联通结果不能替代最终包级结果。
- **失败返回：** 建立可复现缺陷，路由对应工作包；修复 Foundry 后用新候选包重验受影响部分。业务要求保持不变，除非用户明确修改。

### W7B — 既有工程与留出验收

- **输入：** 与主工程业务不同的项目说明、既有代码/测试及可明确识别的无关改动，和 W7A 使用的同一 Foundry 发行包。
- **产出：** 适配既有项目的 Coding Harness、真实增量开发结果、原功能回归和独立接入记录。
- **验收：** 无核心特判或手工注入历史字段；原功能与无关改动保留；完成约定新需求；独立环境只凭发行包、公开说明及合法 Codex 登录即可复现。可自动化执行，不新增外部人工批准门。
- **失败返回：** 通用缺陷回对应包；若发行物改变，使受影响的 W7A/W7B 证据失效并复验。不得把自动化独立环境测试表述为真实第三方用户试用。

### W7C — 缺陷关闭与发行准备

- **输入：** G1–G13 覆盖、W7A/W7B 包级结果、全部必要回归、现有缺陷账本和发行清单。
- **产出：** 最终发行候选、版本/兼容性说明、支持范围、缺陷关闭结论、清楚的接入文档；发布动作留待对应授权。
- **验收：** 主计划 §9 全满足；无范围内已知未解决缺陷；没有以 Skip/静态 PASS/旧包结果替代必要证据；声明与发行内容一致；没有越权推送或发布。
- **失败返回：** 有未闭合项继续路由修复；受预算、真实环境或权限阻塞时如实报告，不改低严重度或缩减承诺后宣称完成。

## 5. 连续执行、失败返回和恢复记录

### 5.1 每包如何推进

1. 读取当前授权与现有工作区，只查该包必要材料；检查前置接口、编辑归属和相关证据是否仍有效。
2. 优先复现要修的可达问题或明确新能力的通过条件；实施最小闭环，不先堆平台抽象。
3. 修改生产路径和必要回归，进行自测；共享文件按归属集成。
4. 用独立断言、公共入口、实际产物复核，记录证据层级与未覆盖项；不是要求另一名人类签字。
5. 当前包验收满足后自动调度下一个就绪包。失败则路由到根因包，仅使受影响证据失效。

工程进度记录使用现有 Tracker 的扩展区域，缺陷使用一份账本。最小记录为：包 ID、状态、当前版本/相关文件、完成的验收及证据位置、未闭合问题、下一步。不要求为这些记录另加摘要、签名或证书。它们是工程记录，不替代真实目标运行的 SQLite 状态。

建议状态为 `PLANNED → IN_PROGRESS → VERIFYING → DONE`，实际阻塞记 `BLOCKED` 并说明原因。`DONE` 只证明本包声明范围；M1/M2/M3/M4 分别承载集成与交付结论。需要真实运行的包不能仅凭 Mock 测试进入 DONE。

### 5.2 并行任务的交接内容

每次交接只给出该包目标、允许编辑范围、输入/共享接口、验收和不能越过的边界。返回变更摘要、实际测试结果、未解决问题和依赖变更；不要求内部思维链，不默认扩大工具/网络/目录或另起工程。

出现重叠编辑或接口冲突时暂停冲突部分、由集成负责人合入；其他不依赖冲突的工作继续。没有理由为每个文件建立永久租约系统或 Hash 树。

### 5.3 停止与续跑

- 用户问题只阻止依赖该决策的工作；能从已有 PRD/说明核对的事实自行查证。
- 已授权测试失败、一般代码修复与复验不是重新授权点；不可把确定性失败简单标成临时错误无限重试。
- 模型额度/网络/工具不可用时完成不依赖它的本地工作，保留未完成项；不偷换模型或伪造实时证据。
- 中断后读当前 Tracker、代码和相关测试证据，再核对目标运行库；不照旧聊天摘要盲目执行命令。
- Git 回退仅处理本次拥有的明确修改，保留用户和其他包的改动；不使用破坏性重置。已执行外部副作用不能靠代码回退撤销。
