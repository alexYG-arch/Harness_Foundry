## 责任边界

`build_runtime.py` 消费 `revision_store.RevisionControlEventStore`；源码兼容 API
`ControlEventStore(storage_format="REVISION_V1")` 转到同一份实现，格式不变。
提案、来源、范围、attempt、进程观测和验收都在同一库的
事件表中；不另建运行状态表、JSON 权威副本或 Hash 链。旧固定启动/兼容消费者
仍只支持历史格式，两者不可交叉解释授权。这是迁移中的两个隔离路由，不是两份
可以同时推进同一 Program 的状态权威。

正常生命周期为：

```text
未批准提案 → 完整来源绑定 → 建设范围准备 → 宿主记录真实用户批准
    → attempt 开始 → 实施观测 → 独立检查 → 控制器验收提交 → 就绪后继
                                      └─ 已知失败 → 预算内修复
```

模型完成、命令退出码、任务自报 PASS 均不直接产生验收。控制器要求全部声明
Case 的独立进程检查成功，并确认被验输出未变，然后以 revision CAS 事务提交。
只有已提交的 `ACCEPTED` 前置任务才能释放后继。

## 来源与授权 API

- `record_source_snapshot`：使用[完整来源接口](GENERIC_SOURCE_INTAKE.md)读取显式
  清单，将全文快照绑定到指定提案。Atom 行定位必须真实存在；不证明语义无遗漏。
- `prepare_build_authorization`：校验并记录范围，创建可读挑战，不创建目标目录、
  不授予权限。源/验证器/依赖须存在；目标及任务目录可不存在，由批准后的 advance 创建。
- `approve_build_authorization`：可信宿主在收到**针对准备事件 ID 的真实后续用户
  批准**后记录该消息引用。字符串本身无法认证用户；该低层 API 不能充当人类批准
  证明。公开宿主路由只验证消息结构，真实身份由聊天宿主核实；模型和目标任务不能写控制库。
- `revoke_build_authorization`：撤销该范围，阻止后续派发和成功验收。通用宿主采集器
  运行期间约每 0.25 秒读取授权事实；发现撤销/到期，停止自己持有的当前有限命令进程组。
  这是合作式宿主观察，不是即时远程取消 SLA；不撤回既有效果，也不向已退出的旧宿主发命令。
- `request_build_repair`：登记外层 Codex 已核实的已接受产物缺陷；校验原授权、版本、依赖及
  重建预算后使影响集合失效，不执行命令、不新增 attempt。精确幂等回放只返回旧事件。
  详见[公开返修请求](GENERIC_BUILD_CLI.md#已接受产物的额外缺陷返修)。
- `reconcile_build_observations`：在不派发、不验收、不清理的情况下取回完整耐久结果；过期或撤销不阻止记录已发生事实，不能据此继续执行。
- `reassess_build_attempt`：纠正旧完整重连流的进程误判，追加观察并绑定待验输出；保持原尝试与消耗，只由后续有效授权内的原检查提交接受。配置回执复用现有校验，正常无重连流程不变。见[历史重判与只复验](GENERIC_BUILD_CLI.md#已完整捕获的重连误判重判后只完成原检查)。
- `resolve_build_attempt`：记录针对已确认退出/未启动的最新失败尝试的真实用户处置。
  保留旧事件，仅允许后续按有效范围和原剩余预算重试；不验收输出、不派发、不授予新权限。

范围明确包含：工作目录、额外只读运行依赖、外部 verifier 目录、逐任务写目录、
逻辑可执行程序绑定、Codex receiver、模型策略或固定值、模型服务许可、总 attempt 与逐任务
attempt 上限、单命令超时及到期时间。Codex 任务仍须声明模型服务许可；日常新请求默认
跟随全局模型/强度，也可手动固定或在准备时读取默认后冻结用于对照。正式执行沿已批准
策略与服务，不静默替换固定选择或切换服务，不继承全局权限或工具配置；仅本地任务
可不授予模型服务许可，详见 [scope 与模型选择](GENERIC_BUILD_CLI.md)。

控制库与实际运行的 verifier 在实施工作区外；资源模式允许检查器源文件在同仓库维护，prepare 复制显式文件到宿主持有的位置；需求文件及绑定执行器/receiver 不得落入任务
写域，检查符号链接实际位置与调用路径。明确写目录内的临时实现文件由任务自行
管理，不要求逐文件永久 lease。根目录绑定变化停止，不扩大既有权限。

计划可在同一 Requirement 内调整待办任务的 `goal` 或 `local_argv`，无需新的人工批准。
`build_replan.py` 还允许未开始任务拆分/合并和独立任务重排：保持全部输出及版本链、
逐输出 Job/执行器、Case 命令及产物绑定、原依赖顺序；只能继承完全相同的原写域，不能增加输入。
新任务从声明输出推导原预算归属；拆分共享原任务上限，合并同时占用各原任务上限，
总预算也不重置。事件记录 `budget_workpack_ids`，旧事件按原 workpack_id 计费。
已开始任务不得拆分、合并、改名或重绑；未验收者可改内部目标/命令，已验收者保持计划不变。
修改外部合同则停止，不能自动弱化验收或沿用旧 PASS。声明输出变化的依赖失效见下节。

`NativeBuildRunner` 重用现有 `CodexCodingRunner` / `CodexSandboxRunner`：

- `CODEX` 接收完整显式来源的只读文件引用和当前任务上下文，全文保留、不截断，
  避免每次 prompt 重复大文档；内部设计/工具选择不被固定为配方。
  原文只作任务数据，不是权限；模型事件只能证明其已观测行为。
  预检默认全局/项目指令链的读取需求，范围准备时可见、运行前再核对；精确文件
  可作为读取绑定，不为读取指令而开放整个父目录，也不禁用指令加载。此静态预检
  不能替代受管配置、实际会话初始化或模型可用性的验证。
  上下文的 `tool_bindings` 直接来自 scope.executables，优先使用绑定绝对路径，
  不假定裸 python3/rg 可用；未因此扩大 PATH 或文件权限，实际模型子命令环境仍需原生案例验证。
- `LOCAL` 使用 Plan 的 `local_argv`，逻辑执行器在批准范围中映射成绝对程序路径；
  不调用 shell、不隐式授予联网、不添加无声明的写目录。
- 验收命令作为产品只读的本地进程运行；选择资源 profile 时可写本次声明的资源叶子。
  `verifier://check.py` 解析到范围中的验证目录；资源模式使用 prepare 生成的受保护副本，旧模式沿用外部验证目录。
  参数中的 `executable://NAME` 只使用范围中已声明的原始执行器路径，使检查器可显式
  传给子进程；未知绑定在范围准备和运行重规划时拒绝，保留 venv 选择，不新增权限。
  适配器在能力探测之后、真正派发之前再次检查权限；无沙箱能力时不降级直跑。
- 独立性指“实施不能改写控制器、判定代码或判定执行器”，不是第三方认证。宿主
  仍须为 Case 选择能验证实际行为的可信程序；一个无意义的 exit 0 检查不是业务证明。

模型服务接入复用原生配置读取。新 CODEX 请求未指定模型、推理强度或策略时，准备入口
默认保存逐命令跟随全局模型/强度的策略；显式模型仍固定，也可读取默认后冻结用于对照。
此推断只用于新准备，不改旧 prepared 的解释；纯 LOCAL 不读取默认，普通动态选择不增加逐次确认。
准备时冻结默认值与逐命令动态选择是两种不同语义，
服务绑定均随现有 scope 审阅；固定模型的既有入口保持原 OpenAI 语义。动态选择只可更新
模型/强度，不静默变更已批准服务。选定凭据引用在客户端启动前解析，工具环境仍不继承；
原始流、JSON 字符串和结果中的已知凭据值脱敏，原始凭据不归档。阻断报告仅保留合法的
`failure_kind="CONTRACT_GAP"` 枚举，非法值仍脱敏并保持原无效报告判定。

每条模型命令在进程启动前另存非秘密配置及来源，并绑定同一 command/executor。
正常结果、完整 capture 恢复和中断后的配置读取共用该附件，不重新读取当前配置冒充旧值。
旧命令无配置附件时保留“当时未记录”的边界，不补造；配置附件本身不证明进程启动或完成，
也不允许跳过退出/效果核对。该附件没有独立授权、计数或验收权。

派发前记录 `BUILD_COMMAND_PLANNED`（不是启动证明），进程建立后记录
`BUILD_COMMAND_STARTED`，宿主流和退出事实先落入目标写域外的私有耐久附件，
再记录 `BUILD_COMMAND_OBSERVED`。附件不是第二状态权威、不能自行验收；不增加事件 Hash。
`BUILD_COMMAND_OBSERVED` 绑定 Program 事件流、提案、授权、attempt、Workpack、
Job、实施/验收阶段以及确切 Case。进程运行期间若撤销授权，已发生结果仍保存，
但不提交成功、不调度后继。实施和验证均接入相同取消检查；关闭 stdout/stderr 不会
停止检查。授权读取失败同样停止当前进程并保留诊断，不能当成可自动修复的业务失败。
取消保存 `cancellation_reason`、退出及流观测，结果为 `UNKNOWN_SIDE_EFFECT`，因为
终止进程不证明副作用回滚；完整耐久附件恢复仍保留这一判定，不自动重跑、不重置预算。
宿主的 `KeyboardInterrupt` / `SystemExit` 会先清理自己持有的进程组并保存实际退出记录，
再传播原中断。SIGKILL、断电、默认 SIGTERM 或持久化过程中再次强制终止仍可能没有完整记录；
这些情况保持未决，沿 [旧未知结果的真实处置](GENERIC_BUILD_CLI.md#旧未知结果的真实处置)
核实后处理，不能自动补造成功或重放命令。
取消检查不读取/Hash 全工作区；完整来源/产物检查仍在派发、验证、接受边界完成。
缺产物或实际检查失败为可修复拒绝；超时、未观测效果
或无法解释的过程结果保持未决，不盲目重试。`MODEL_PROCESS_FAILED`、明确未启动的
命令或适配器禁止自动重试的失败单独记为 `BLOCKED` / `HELD_COMMAND_FAILURE`，
不消耗剩余预算重复同一启动错误；验证器自身无法启动也不应重跑实施。新控制器
读取旧的误分类 REJECTED 事件时同样停止，但不修改旧状态或删除尝试历史。

一次新 attempt 消耗预算，重启不会重置累计。修复沿用原需求和 Case；已知失败
内容进入下一次任务上下文。本地命令只做有界重试，自身不会获得模型推理能力。
非零 verifier 只有退出 1 且输出 `CHECKS_FAILED` / `failure_kind=ASSERTION` 的完整
JSON 才作为正常业务断言失败；崩溃/未分类失败 BLOCKED，不触发目标业务修改。
`reason` 不作为 `failure_kind` 的别名。如果完整结果同时声明 errors、discovery_errors、
skipped、expected_failures，或声明的 tests_run 不是正整数，则不能用 ASSERTION 标签
掩盖未完整执行而触发业务返修。原始 JSON 保留，不重写成通过。
生成提示与[准备模板说明](GENERIC_BUILD_PLAN.md#搭建质量最小方案接口与交付2026-09-26)
使用相同分类和两种合法 scratch 布局；现有 `test_execution.py` 已具备这些行为。
开发用 `release_acceptance.verify` 还拒绝测试计数缺失、矛盾 PASS 及 reason-only 失败，
保留嵌套证据。它不随通用包分发，不替换任何已批准评测绑定的检查器。
普通非 JSON 的 exit 0 独立检查不因此增加新必填字段；未报告错误不能被宣称为错误路径
已验证。失败分支以源码回归为证；后续 Task 正常路径实测不证明未触发的失败路由。
最新结果见开发仓库 `docs/FOUNDRY_UPGRADE_EVALUATION_2026_10_10.md`（不随运行包分发），
不把限定样本通过视为完整 Harness 或发行验收。

独立 ASSERTION 可显式提供 `repair_artifact_ids`，将失败消费者的已声明输入交回其
当前已验收生产者修复。控制器先核对归属、版本和原剩余预算，追加
`BUILD_ACCEPTANCE_INVALIDATED / INDEPENDENT_ARTIFACT_REPAIR_REQUIRED`，使生产者
和依赖后继失效；原失败与次数保留，反馈进入生产者的下一次实施上下文。
不扩展消费者写域、不修改已验收字节制造漂移、不重置预算或新增批准。未声明输入、
未验收生产者或依赖被覆盖历史版本时返回 `HELD_REPAIR_SCOPE`；基础设施/未知错误
不能通过这条路线猜测修改业务。详细接口见[合同对齐 v0.2](ACCEPTANCE_CONTRACT_ALIGNMENT.md)。

## Codex 负责核实，宿主提供返修和交回

外层 Codex 对约定交付做一次有范围的复核，可复用等价证据；修复后只查变化与受影响路径，
不让每个子任务重新全库审查。疑点先核对原要求、当前版本、可达触发、行为差异和反证。
确认且原权限、合法入口、预算及复验足够时自动最小修复；已证伪说明反证，证据不足保留待核实，
可选优化不阻塞交付。子任务只实施当前分配任务并交回增量；Harness 记录原生事实、预算和接受。

全绿后的范围内缺陷可通过 `request-build-repair` 交回 CODEX 原生产者，并重建依赖中的
CODEX/LOCAL 任务。控制器追加已有的接受失效事件，原因明确为外层已核实缺陷，而非伪称
独立检查失败；调用不执行产品命令、不删除文件、不修改旧 PASS、不重置预算。首次入口限当前
全部接受；同链续修在后继尚待重建时即可交回已重新接受但仍有缺陷的生产者。原生路由已处理
消费者必须匹配同一 Program/prepared 下最新失败 attempt，不能使用旧失败记录覆盖新失败。
完整待重建集合还包括尚未重建的原生产者，以及最新 attempt 已由原生恢复实际结算为
NOT_DISPATCHED 且仍关联本链既有失效事件的任务；缺观测或未知副作用不推定未派发。
与本次影响集合按任务去重后核对原剩余重建预算，未派发已消耗的 attempt 和实际时间不返还。
详情与请求形状见[CLI](GENERIC_BUILD_CLI.md#已接受产物的额外缺陷返修)。

当前未接受候选仍按原写域修复。原 Plan 的合法同路径替换继续适用：声明输出的
`replaces_artifact_id` 指向祖先同路径输入、替换链唯一、其他旧版读者已按顺序完成，且权限和
预算有效；创建新候选、重新验收，保留旧记录，不承诺恢复已覆盖旧字节。不得临时添加替换
声明，或先改已接受字节制造漂移。受保护合同/检查器、未知副作用与范围变化沿用原流程。

`BuildController.advance(..., advance_mode="ONE_ATTEMPT")` 只处理一个新 attempt，或恢复一个
已开始 attempt 到真正结算/原生挂起。补一项观测不等于结算；可续跑同一 attempt 尚未派发的
检查，不重跑实施，不再启动新 attempt。新 attempt 交回在下一次原生修复路由或派发之前。
正常交回 `BUILD_CONTROL_RETURNED` 是调用结果，原生 `attempt_status` 为 REJECTED 仍是拒绝；
原 HELD/STOPPED 保留。只有后续原完成分支才报告 `PLAN_CHECKS_ACCEPTED`，原权限、版本、
漂移和预算核对仍执行。省略模式为 CONTINUOUS；模式不隐式跨调用继承。

`codex_handoff` 只随 ONE_ATTEMPT 的实际新 CODEX attempt 保存并进入实施 prompt。
归属不符不派发新 attempt，原生路由已追加的失效仍保留；失败消费者可把相关历史交给生产者。
恢复沿用旧 attempt 已存上下文，调用带来的新摘要明确未用于新实施，不排队到下一 attempt。
LOCAL 不消费模型摘要。写入 STARTED 只证明绑定；结合实施观测才能判断是否实际启动并发送
上下文，不能证明模型已阅读、理解或遵守。摘要不进入检查器 binding，不授权或裁决问题。

外层在收回控制后判断继续：**没有有效修改且没有新的诊断进展**才是无效修复链；无 diff
但排除了具体假设或取得新复现条件可以有进展。到原停止条件则停止该项额外返工。只有原生
恢复实际结算为 NOT_DISPATCHED，才不计产品失败、不据此判方法无效；原 attempt/时间照计。
缺少观测、未知效果不自动推断未派发。同次恢复不多开 attempt，下次是否派发核对授权、预算
和中断原因。外层不主动派发依赖已知未解决问题的后续工作；正常核实、修复和无关授权工作
通过已有适用入口继续。单次交回不提供任意任务选择器、撤销或全局停止，也不约束其他调用者。

开发者分别提供问题复验与关联回归，宿主执行原绑定独立检查，外层再按当前版本证据核对交付。
开发通过待宿主检查时正常交回，不能算成功或为等待反复自测；原检查再次全绿也不消除仍存在
的额外反例。普通报告不停止 Harness，不以假 CONTRACT_GAP 或故意命令失败求停。

项目隔离修复向 Foundry 公共维护交接时，维护归属、归并条件、必要验证及交付状态统一见[项目修复与主版本归并](HARNESS_DESIGN_GUIDE.md#项目修复与主版本归并)。区分项目已修、主版本已修、固定包已包含与实际部署已升级；这项工程交接不改变本节既有 G1/G2、授权、恢复及累计预算，也不新增运行前置。

## Codex 报告恢复与计数交接

这些操作由有权限的外层/可信宿主按实际交接缺口使用，不是新增公共门禁、强制文件、问题
schema 或控制表。已足够的报告无需扫描原始流；子任务不访问控制库/宿主附件补记忆。

1. 先 `read-build`，按 Program/prepared/attempt/workpack 取回本轮所有尚未合并的
   `implementation_commands`；`last_command` 可能已经是验收。投影提供实施观测事件、
   command ID、阶段、执行器、`final_message` 和已绑定 `observation_root`；缺少实施观测
   明示为 MISSING_OBSERVATION 或 NO_IMPLEMENTATION_COMMAND，未知内容不能当零。
2. 最后消息只保留最后一个已完成 agent_message，可能是进度说明；未截断甚至模型正常
   结束也不证明包含当前版本、动作、开发结果、未解决项和本次增量。缺口出现时，可在原权限
   下只读同 Program 事件存储 `ControlEventStore(..., read_only=True, storage_format="REVISION_V1")`
   的 `list_events(program_id)`，仅核对相关 IMPLEMENTATION/CODEX 的 BUILD_COMMAND_OBSERVED。
3. 仍缺信息时只查对应命令已记录 observation_root，核对 binding.json 的 command ID 和
   executor 后读 result.json；其他归属由命令事件核对。附件也可能只有相同的最后消息或
   65,536 字符截断，换来源不等于已恢复完整。无合法路径或权限时保留部分报告。
4. 需要消息序列且已有权限时，只读该命令 stdout.bin 已保存的消息。先固定 command ID、
   当前已保存末尾位置和可用原预算，按顺序读至该位置或预算边界；不在较早一条看似完整
   报告处提前结束、不轮询、不扫无关命令、不重读已吸收片段。用实际 item.id 或行/字节位置
   记录来源；解析失败、流不完整、预算不足则保留缺口。多消息后中断且最后短消息未截断
   同样适用；读到末尾仍不能补出从未汇报的动作。不为找报告调用 advance、恢复或重执行。
5. 在已有外层工作记录中按 command ID/消息位置标记已吸收片段，再按问题依据、版本、方法
   和证据合并实际处理轮次。同消息出现在事件、附件、原始流只算一次；已见 command 后新补
   的片段仍要吸收，不同命令交接同一轮不再计一轮。早先未解决项只有对应反证或修复复验才能
   更新，后续消息没再提不等于解决。权限不足保留已取得事实和报告缺口，不改宿主验收状态。

沿用任务原有有限预算和已有约定；无适用约定时，外层可在已有计划采用额外问题处理的建议
默认：一次整体复核、同一疑点最多两轮主动核实、同一问题累计最多两轮失败修复；无总时间界限
时采用 30 分钟额外处理时间盒。已有更短限额和权限优先，为复验交接留余量。这些是可调整的
Codex 工程默认，不是新 Harness 字段/硬限制，也不增加逐项确认；成功修复不机械限件数，
实际时间、工具调用和 attempt 保留。原生独立断言修复继续按原合同及原预算，不能用额外处理
的两轮一概拒绝宿主分配；也不能借宿主再次派发清零已知失败历史或自行追加第三轮额外修复。

累计值不是逐消息增量：同一范围先报失败累计 1 后报 2，归属明确时合并为 2；范围/基数不明
保留已知与未知，不取最大值或末条数值猜测。计划不算执行；已执行而结果未知标为待结算，
后续证据结算原轮一次。复现红灯、超时/环境失败、NOT_DISPATCHED 不自动算产品失败；
成功其他问题不清掉旧失败。问题级轮次不由消息数、reported_command_failures 或 attempt 数代替。

新完成证据足以直接确认/证伪时可更新结论，不额外计主动核实轮，但耗用时间；仍需新复现、
诊断、搜索或补静态链就是下一轮核实，受采用的剩余额度约束。新证据重开不重置核实/失败/
待定轮次或总截止时间。补读既有记录也不增加轮次；进一步诊断需按实计数。记录不完整不阻止
首次合法修复或无关授权工作，只防盲重启历史不明的失败链。

下一 CODEX attempt 通过可选 codex_handoff 内嵌已恢复的问题、证据、实际累计、待定轮次、
额度/剩余量及不同的下一方法，或使用已允许双方读写的既有工作记录；仅写聊天或路径不等于
实际送达。外层维护累计，子任务报告增量；不同会话、请求回放和补全报告均不重置或重复计数。
两轮失败、报告缺口、Harness 再派发同时发生时保留原生修复与额外处理的实际归属，先有界恢复，
不盲开第三轮额外修复；ONE_ATTEMPT 让外层先收回判断，不把普通交回误称机器已停。

## 字节身份、顺序修改与恢复

- 来源已经存有全文，使用全文比较，不重复建立 Source Hash。
- 基本 SHA-256 仅用于明确声明的 verifier 与输入/输出文件身份（H2），在绑定、
  任务/验证边界检查；不扫描全树，不对事件、回执、日志或每次工具调用套 Hash。
- 同路径显式 replacement 开始后，旧物理版本视为已消费；Plan 要求全部旧版读者
  先完成。失败新版本可原位修复，但后继不能消费未验收的新版本。此处没有历史文件
  快照存储，也不假装覆盖后的旧字节仍可读取。
- 耐久命令完成附件可补回丢失的控制观测；部分 Case 完成后只续跑未派发 Case，
  全部检查已观测则恢复提交。先重核当前范围、被验输出和已验收依赖，不重复实施。
  已观测启动/验证器失败也恢复为对应失败，不永久误记为未知。无完整退出事实不重放。
- 若只有 attempt 预留事件、尚未提交任何命令意图，控制库按 revision CAS 将其记为
  `NOT_DISPATCHED`；原调度器必须先提交命令意图才能执行，因此不会与恢复后的新尝试双发。
  此预留仍消耗原预算，不返还、不新增批准；迟到的原调度器也不能覆盖已记录的恢复结果。
  一旦已有命令意图却缺少完整观测，则继续保持未知效果，不适用此自动恢复。
- effects 准备失败且完整事件证明未提交命令意图时，新失败结清 NOT_DISPATCHED，旧 UNKNOWN
  追加恢复，保留诊断和预算并单次交回；残缺/矛盾事实不放行。成功预检保留，不重跑。
- 只复验在保存输入和恢复时核对原接受字节，包括旧版本已保存的检查输入。已完成预检或已有
  检查观察时，声明文件缺失/改变返回诊断并保留尝试；还原原字节后只续未完成检查。
  尚无任何命令意图的预留仍按 NOT_DISPATCHED 规则结清；不把此种后续新尝试算成免费恢复。
- 完整实施观测已知、声明输出却缺失时，恢复和正常路径同样记为 `REJECTED`，可在原范围和
  预算内修复。恢复提交结果前再次检查当前授权、来源/检查器和控制 revision；过期或撤销
  不能借旧完成观测得到新的验收。预留空窗的恢复不等于重启后的进程身份核对已实现。
- 声明的已验收输出缺失/变化时，追加 `BUILD_ACCEPTANCE_INVALIDATED`，按依赖图
  失效生产任务及后继；原范围/累计预算内重新建设并独立验收，无关分支保持已验收。
  不删文件、不改历史；需求/验证器变化、在途被验字节变化仍停止。
  受影响任务依赖已被覆盖的旧 artifact 版本时停止，要求明确重建计划，不能伪造历史字节。
- read-build 返回命令阶段、原始结果、宿主附件和进程诊断。PID 探测只是提示，
  不作为进程身份/效果证明，不按 PID 名称杀进程。未观测启动的原子性空窗仍要求核对。
  当前活宿主对自己启动的进程组已支持取消；重启后仅靠旧 PID 不会杀进程。
  任意环境故障的自动复测、重启后的在途进程可靠身份核对/取消、跨已消费版本重建尚未关闭；
  不承诺外部 exactly-once，也不把诊断提示当成完整恢复实现。
