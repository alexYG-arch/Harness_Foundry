### 1.2 要解决的问题

现有流程已支持在批准范围内实施、独立检查、修复与恢复。本次重点补齐：

1. 从日志判断问题属于业务实现、目标 Harness、领域能力包、Foundry 通用机制、环境，还是验收条件表达；证据不足时保留未知。
2. 区分“这次修好了”和“后续更能避免、发现及修复这类问题”。
3. 用独立语义评审检查是否解决了正确的问题，继续用客观工具验证实际结果。
4. 将可靠经验整理为按需检索的 Wiki，并引用已有版本化能力与实现。
5. 比较候选与基线，保留有效改进，记录它是否真正进入交付包和项目部署。
6. 区分测试先行、缺陷复现后修复和补测，将同一行为的修复前失败、修复后通过及相关回归连接起来；不把最终 PASS 或不同平台的结果拼成 TDD 证据。

本文将 RSI（递归自我改进）限定为：系统依据运行证据改进自身的工作机制，改进后的版本继续参与后续改进，并验证收益和退步。普通任务修复是基础，但单次修复、版本递增或日志总结不单独证明 RSI 成立。第一版不训练模型权重，不承诺自主能力持续增长。

## 3. 文献依据与采用边界

### 3.1 TerminalHorizon：学习有效轨迹，不奖励轮数

依据用户提供的 *Scaling Agentic Data for Long-Horizon Terminal Intelligence*，arXiv [2610.13166v2](https://arxiv.org/abs/2610.13166v2)，重点为第 2 节、第 4.4 节和附录 C、F、G。

- 主要实验是构造任务与轨迹后进行监督微调，2,852 条训练轨迹带来的模型收益不能直接转写成 Foundry 流程收益。
- 借鉴独立试用与实际轨迹分析：公开任务要求、实际操作、环境反馈、修订理由和最终交付之间应有可检查的关系。
- 有价值的失败可用于诊断；重复轮询、无依据试错、答案泄漏及绕过接口不能因轮数或最终得分而成为优质经验。
- 保留开发阶段确认有效的版本，并检查最终交付仍包含改进；不能事后用隐藏验收成绩挑选最好的历史版本。
- 四个 RSI 案例是每模型每案例一次运行、12 小时预算上限，实际用时不同；不能据此承诺普遍或等成本收益。
- 任务逐步扩展仅可用于另行定义的开发案例或明确变更后的需求，不能暗中扩大当前业务验收范围。

### 3.2 HOA：语义评审、客观验证与可复用知识各司其职

依据用户提供的 *Humanize Olympiad Agents: A Multi-Session Workflow for Olympiad Problem Solving with Solve, Review, Wiki, Verify*，arXiv [2610.13632v1](https://arxiv.org/abs/2610.13632v1)，重点为图 2、第 3.2–3.5 节及实验限制。

- Worker 负责实现；独立 Reviewer 检查原始目标、完整性及语义；Verifier 是任务相关的客观工具，而非必须新增的模型角色。
- Reviewer 读取原始需求、验收计划、冻结候选和必要运行摘要，不继承实施者完整对话或隐藏推理，不在评审过程中修改候选。
- Wiki 可以提供带来源的知识，也可以引用经过验证、可直接调用的实现；按明确知识缺口检索，不把全部历史灌入提示词。
- 论文不同领域使用的验证方法不同；不能将数学形式化证明的保证推广成所有软件或界面任务的正确性保证。v1 部分实验仍标为 provisional，成本及组件贡献并未完全隔离。

此前讨论的 Harness2 作为研究背景保留；本计划不依赖尚未在本轮核实的仓库功能、性能或“自动递归进化”宣传。

```text
        └── 独立语义评审 + 适用客观检查 ──┘
                    ↓
基线比较 → 保留或拒绝 → 知识整理 → 版本化交付与采用
                    ↓
后续运行反馈（不自动扩大权限或重开已接受任务）
```

- 项目业务错误首先在项目内修复；通用领域方法归相应 Harness 或能力包；生成、验证、恢复等通用缺陷归 Foundry。
- 一个明确复现的 Foundry 缺陷即可支持修复，不要求先凑多个项目。泛化收益则须有相应证据，不能由一个案例推断。
- 分析者提出候选；Worker 修改声明范围内的实现；Reviewer 给出可定位的语义意见；Verifier 验证已声明条件；现有控制器和可信宿主保留原接受与权限职责。
- Reviewer 的 ACCEPT 不能覆盖 Verifier 的失败；工具通过也不能自动解决已证实的需求遗漏。观点冲突要给出具体依据，不能靠模型投票或无限返修解决。
- Foundry 自身改进通过正常源码工程和版本交付生效，不能由运行中的任务热替换控制器、私有预期或批准材料。改动检查器时沿已有等义修正或真实合同变更路径处理。

## 5. 最小数据与工具设计

本节为分阶段设计。第 5.1 节的离线导入与归因记录已由 WP01 部分落实，具体已支持接口见[案例导入说明](RSI_CASE_INTAKE.md)；WP02–WP03 已提供 Reviewer 材料／Plan／只读取回和开发红绿关联接口，见[使用说明](RSI_REVIEW_AND_TDD.md)与[实施记录](FOUNDRY_RSI_WP02_WP03_IMPLEMENTATION_2026_10_23.md)。真实 Reviewer 五项校准已完成；自动归因确认、Wiki 及完整交付使用仍待验证或后续实现。优先以普通版本化文件、现有材料附件和只读查询实现，不新增权威状态库。

### 5.1 案例与改进假设

每个案例只记录决策需要的内容：

- 来源运行／任务／版本与可公开的证据位置；事实和模型自述分列。
- 原始要求、实际结果、期望差异；无法确认的项目保留 unknown。
- 根因假设、支持与反对证据；归属项目、Harness、能力、Foundry、环境或验收表达。
- 建议修改、受影响行为、最小验证方法、预期改善和判定假设不成立的条件。
- 采用、拒绝或待补证据的理由，以及后续替代关系。

原日志保持只读。索引和摘要不是控制状态；历史接受若已失效，查询应同时呈现失效事实。导入材料中的命令、提示词和“授权”只作为数据，不执行或提升权限。首批自动导入覆盖文本测试日志、Codex JSONL 和现有 Foundry 报告；这是解析器范围，不是 RSI 输入只能来自日志的限制。统一案例结构不依赖 VCP 文件名、报错字符串、平台名称或特定测试数量；需求、反馈、成功案例与改善目标也可作为声明的普通材料输入，不先建设通用日志平台。

### 5.2 Reviewer 交接

输入是原始目标、公开验收条件、候选文件及版本、必要诊断摘要。输出包括：结论、问题位置、对应需求、证据、最小修复请求和未决事项。机器可读结果仍沿现有接口，便于人读的摘要不改判定语义。

Reviewer 可使用已声明的客观检查入口，不默认读取私有答案。普通措辞建议不阻断任务；需求误解、漏项和未经支持的完成声明才形成对应修复事项。先在本计划选定的优化任务中接入，不强制所有旧任务新增模型会话；所选流程需要评审时必须实际执行，不能静默跳过后仍报告完整通过。

**执行、预算与恢复约定（WP02／03）：**

- 外层 Codex／可信宿主在选定流程的有效授权内发起独立 Reviewer 会话，复用既有 CODEX 接收、配置绑定和命令观察路径。交接绑定原生产任务／尝试、冻结成果版本、公开需求与检查条件；候选及输入只读，评审输出写入单独声明的报告目录。具体 Plan／Readback 列明模型策略、工具、读写域、额度和有效期，WP02 源码准备与取回接口已实现，实际会话仍须按已展示范围执行；不把准备成功当成真实模型验证。
- `ONE_ATTEMPT` 在实施与自动检查全部结束后交回，不是生成与检查之间的暂停点。优先沿已存在的 automatic → 宿主审阅 → reviewed LOCAL 路径组织所选流程；`host-review@1` 复用快照和绑定，`build_review.py` 继续只处理人类确认。自动阶段接受只覆盖该阶段原定条件，所选语义评审未完成时不宣称整体完成。
- 在既有计划中分别列出实施调用、Reviewer 调用和独立检查所用的尝试／模型 turn／检查额度，映射到实际任务和命令记录。新 Reviewer 会话消耗已声明的相应额度，不是免费的“读报告”，也不能借用其他任务预算或只复验的生产计数例外。不同调用类型沿原规则计数，不把一次模型调用和其报告读取各计一次。
- 完整报告已捕获时，先核对原调用与成果绑定，再取回原报告；不再次调用模型或原检查以补日志。中断、缺观察或结果未知沿既有观察恢复路径核实，不将等待、恢复失败或未知效果视作完成；确需新调用时沿原授权与剩余额度记录实际消耗。prepared 接续、撤销和过期仍由既有控制路径判定，已捕获报告保持可读。
- Reviewer 提出的问题由外层结合对应需求、成果版本和证据核实，再沿适用的原生产者返修或宿主修正入口处理；不把建议直接当成接受失效。原问题的重复表述关联原事项，不虚增缺陷或修复次数；有新版本、新证据而实际发生的复评／修复保留真实消耗。已接受生产命令不为取回评审而重放，无法判定的问题保留未决，不以无限评审代替核实。

**评审自身的验证（G02／G08）：**使用少量已有明确判断依据的材料，覆盖真实需求遗漏、合法等价实现、仅措辞建议、证据不足及客观 FAIL 与正面评语冲突。分别报告命中、漏检、误拒与未知；合成回归验证交接和分类，不能替代真实 Reviewer 的判断验证。不要求所有任务增加第二模型或人工评分。候选比较确需模型判断时，按需隐藏新旧标签、交换展示顺序并记录分歧，不将盲评包装成保证正确或触发强制扩样。

### 5.3 Wiki 与能力层

第一版提供按问题和适用条件查询、提出知识候选及记录采用／撤回的最小工作流；接口名称在实施时确定，不预先建立服务、向量数据库或第二套权限系统。

条目包含说明、适用／不适用条件、来源与版本、证据类别、当前验证状态，以及可选的能力包／工具／契约引用。状态区分候选、在明确范围已验证、已替代或已撤回，不以“verified”暗示所有环境适用。

查询返回少量相关内容及来源。原始失败可以作为反例，不能整理成“成功方法”；修复开发测试通过但设备未验的条目仍保留这一限制。知识采用不自动安装、调用或授权引用的工具。私有预期、凭据、个人路径和项目保密材料不进入公共知识包。

本次运行记录实际采用的条目版本、来源及能力／工具引用，优先复用材料清单与结果附件；知识库更新不静默改变本次已绑定依据。后续反证形成替代或撤回关系，后续查询呈现当前适用状态，原条目、运行依据及结果仍保留；版本不适用或没有命中时返回具体限制，继续原来可行的任务路径，不把 Wiki 命中设为通用前置条件。若变化涉及正在使用的授权或实际工具范围，仍沿原权限与变更规则处理。

基线与候选对照分别固定知识条件及初始状态，记录有意作为实验变量的差异；不把候选运行产生的答案或总结传给基线，也不让两臂通过共享写入互相影响。已用于调优或曝光答案的样本按第 5.4、8 节处理，不因换会话重新称为未见样本。不为此新建知识服务或全图 Hash 链。

**接入与使用方式（WP04 源码入口已实现，WP05 交付接入已实现，真实使用待验）：**指南说明何时查询，查询工具负责定位条目，版本化文件承载知识，已有能力包提供实际实现。公共知识随选定交付包提供；项目私有知识保存在项目声明的位置，不自动汇入公共包。项目通过普通配置声明知识目录或包版本，优先使用可随交付解析的相对位置，不依赖开发者个人路径；WP04 已提供 `collection.json` 与 `tools/rsi_wiki.py propose/query/record`；字段、边界和源码调用见[Wiki 用法](RSI_WIKI.md)。WP05已提供可选交付材料准备、运行包清单和生成指南接入；首阶段实际生成有限检查已接受，新会话使用仍待G05验收，见[WP05实施记录](FOUNDRY_RSI_WP05_IMPLEMENTATION_2026_10_23.md)。

设计者、Worker 或 Reviewer 发现明确知识缺口时，提交问题、任务条件和相关版本，查询返回少量条目、来源、适用限制及可选能力引用。调用者结合当前需求选择采用或不采用，记录实际采用版本；找到工具引用不代表已安装或已获调用授权。条目区分事实资料、已验证方法、能力引用和失败反例。新经验先成为候选，核实后在相应维护位置采用或替代旧条目；查询不自动改写正式知识，无命中时继续原可行流程，不强制每次任务检索或编写 Wiki。

### 5.4 候选与采用

保存基线、变更说明、评审、检查与比较结果。仅按开发阶段可见且预先约定的指标选候选；一次保留验证用于最终判断，不用于反复调参。若查看失败后继续针对该案例修改，应标记其已成为开发案例，不再宣称它仍是未见样本。

在满足必要要求的候选间比较成本和收益；“最后一次修改”不自动优于基线。采用时区分源码已修、固定包已包含、目标项目已升级和后续效果已验证。回退恢复版本选择，不抹去历史、累计消耗或已发生的外部效果。

### 5.5 TDD 红绿证据与报告

目的不是要求每次 coding 多写一份报告，而是复用已有运行记录，说明哪项修改消除了哪项失败，以及哪些结论仍待验证。第一版只覆盖选定优化任务中有明确、可运行行为检查的新增功能或缺陷；普通文档修改、纯整理、已通过行为的补测不强制制造 RED。适用性在既有计划准备中声明，不在失败后改成不适用，也不追溯重开已接受任务。

**执行位置与粒度：**TDD 融入单个适用开发／修复任务的 Worker 内循环，以一个明确行为为粒度：公开预期 → 编写或选取开发测试 → 实际 RED 与原因核对 → 最小实现／修复 → 同一行为 GREEN → 必要重构与相关回归 → 固定成果交回。一个生产尝试内部可完成多个小行为循环，不要求每个 RED／GREEN 新建 Workpack、模型会话或人工确认。真实命令、时间及模型消耗仍按原规则记录；控制器实际产生的新尝试照常累计，不按红绿次数另造预算账目。

开发测试与最终独立验收分开。Worker 可维护公开开发测试，但不能修改私有预期或独立判定代码；保留红绿各自运行时的测试版本和原结果，不只引用最终已覆盖的文件。预期 RED 在开发任务内部观察，不把它放进最终验收并要求控制器将失败当作通过。现有控制器仍在实施返回后固定成果并执行独立检查；Reviewer 通常在完整行为或任务交回后审阅，确有语义缺口时才按原流程提前核实，不默认每次 RED 后都增加评审。开发 GREEN 不代替独立验收，候选收益比较则在第 5.6、8 节另行说明。文档、调研等不具备相应行为检查的任务使用适合的证据核对，不强套 TDD。

**先区分四种情况：**

- 测试先行：先定义行为测试，在尚未实现该行为的版本上实际观察到符合预期原因的失败，再实施并通过。
- 缺陷复现后修复：现有或新增测试实际复现缺陷，再修复并通过；不能仅凭有一对红绿结果就声称新增功能采用了测试先行。
- 补测或仅有绿色结果：旧实现已通过新测试，或未保留修改前运行；如实记录，不能倒填 RED。
- 不适用或证据不足：说明具体原因；未运行、环境阻断、运行记录缺失分别保留，不推断其实际成功或失败。

**最小记录：**优先引用现有任务、尝试、命令结果与版本信息，不复制原日志、不建立第二个权威状态库或全图 Hash 链。下列内容由 WP03 的可选关联输入表达，具体字段见[源码用法](RSI_REVIEW_AND_TDD.md)；不改现有默认运行报告格式。

| 内容 | 需要保留的事实 |
| --- | --- |
| 行为与归属 | 需求／缺陷、测试用例、输入或夹具、观察对象、具体断言，以及项目／Harness／Foundry 等修改对象 |
| RED | 修改前实现版本、测试版本、实际命令与环境、运行顺序及原始证据；预期失败原因与实际失败原因分列 |
| 修改 | 修复版本与最小变更说明；同时记录测试、夹具、环境或验收条件是否改变 |
| GREEN | 修改后实现版本、同一行为测试的版本与命令、实际结果及证据；关联对应 RED，而不是只选最近一次 PASS |
| 回归与限制 | 相关回归、独立验收、原生／设备检查各自的结果与未运行原因；保留失败尝试、消耗和未决问题 |

RED 按已声明的测试对象、目标行为和实际失败原因判断，不只按异常类型分类。与目标无关的依赖缺失、导入故障或测试进程未启动，不能充当该业务行为的 RED；但公开要求的新接口尚未实现所导致的定向失败，或本次测试对象本身就是解释器启动、环境解析与诊断时，相应失败可以是该目标行为的 RED。必须有实际检查将失败关联到公开要求，排除无关环境故障；仅有未启动记录或异常字符串、原因尚不清楚时仍为阻断或证据不足，不自动判定有效 RED。

GREEN 必须验证相同公开行为和验收语义，平台、输入与环境应可比较；条件有变化时披露差异并说明能否配对。测试 ID 相同不保证语义相同，删除断言、放宽阈值或换成无关测试不能组成有效红绿对。合法检查器等义修正和真正合同变更仍走既有路径，保留旧结果；原证据不能因新测试通过而被改写。

若声明完整 TDD，除红绿证据外还说明是否需要重构；确需重构时，在重构后的最终版本保留相关检查通过的证据，不只引用重构前 GREEN。不强制每次改动都重构，也不为凑齐 Red–Green–Refactor 增加无关变更。

修复前未跑过测试时，后来对保留旧版本的回放最多支持“事后复现”，不能证明当时测试先行；回放本身需要在既有范围和预算内，本计划不授权执行。报告生成只读，不为补齐字段自动调用模型、重跑历史或延长预算。

**角色与反馈：**

1. Worker 在适用任务内先复现、后修复，交回实际检查和变更；不修改独立验收条件或自判最终接受。
2. Reviewer 检查测试是否针对原始需求、RED 的原因是否相关、修复是否只是迁就测试；输出具体意见，不代替工具结果。
3. Verifier 使用已声明检查和实际结果确认观察事实；报告关联逻辑检查版本、顺序、用例与语义的可比性。不能仅据日志关键词、退出码或 Worker 自述认定完整通过。
4. 报告复用既有结果附件或只读视图，提供简短的人读摘要和兼容的可选结构化记录；保留现有 JSON 的默认格式和接受语义。报告是证据汇总，不是新授权、独立接受状态或强制新增文件。
5. 日志分析将有效红绿对、未解决失败和环境阻断分别送入案例；Wiki 条目引用适用条件、方法、反例和验证限制。Harness 改进与 Foundry 通用修复仍按归因分流。
6. RSI 候选比较检查最终交付是否保留该修复、相关行为是否退步，以及后续同类问题是否减少。单个红绿对证明的只是限定行为修复，不证明根因唯一、所有行为正确或递归收益成立。

人读摘要至少回答：测什么、修改前为什么失败、改了什么、相同检查是否通过、相关回归与独立验收还有什么未完成。不另设文字评分、逐任务人工确认或无限补证循环。证据缺失限制 TDD／修复效果声明；只有原计划明确要求的检查缺失或失败才按既有 Gate 处理，不能将所有旧任务一律增加 TDD 门槛。

### 5.6 如何使用 Foundry 开展持续改进

以下是拟交付给使用者的流程，覆盖原 WP01–10，不是已经支持的新 CLI 或后台服务。使用者先选择改进对象：目标 Harness／能力包，或 Foundry 自身。前者沿适用的搭建、增量修改与组件升级入口推进；后者沿正常源码工程、回归及版本交付推进，不强行套入目标项目的业务执行流程，也不热替换运行中的控制器。

**输入与开始方式：**使用者可从 Chat 提出“针对指定版本及材料改善某项行为”，先请求诊断和候选方案。日志不是唯一入口，也不必先有失败；成本或效率优化可以从成功运行和基线测量开始。材料不足时明确哪些结论尚不能判断，不先建齐一套平台才允许分析。

| 输入 | 用途与边界 |
| --- | --- |
| 改进对象、当前版本及交付状态 | 明确改 Foundry、Harness、能力包还是项目局部，区分源码与实际部署 |
| 原始需求、公开验收条件及改善目标 | 判断正确行为与所求收益；例如减少误报、重复操作、人工介入或成本，不从日志反推用户目标 |
| 实际运行记录、失败／成功案例、用户反馈 | 支持归因与假设；模型自述、观察事实和未知分开，保持原件只读 |
| 当前实现、声明工具与环境 | 定位实现及依赖，判断复现和交付条件；只读取本次授权材料 |
| 开发样本、保留样本及独立预期 | 开发与收益验证分开；私有答案留在检查域，不因输入清单而交给 Worker |
| 可修改范围、工具权限、预算与停止条件 | 在具体执行准备中绑定；普通诊断不等于执行、部署或发布批准 |

**一次改进的使用步骤：**

1. 读取材料并诊断：关联需求、实际行为及版本，列出事实、未知和候选原因，确定维护归属；日志案例不直接生成核心规则。
2. 提出可检验假设：说明最小修改、预期改善、可能退步及何种结果会否定假设；有知识缺口时按第 5.3 节查询 Wiki。
3. 准备比较与执行：固定基线、候选方向、环境、模型策略、知识条件、独立检查及预算；按既有流程取得所需真实授权，已覆盖的内部步骤不另行确认。记录可复用证据和需新增验证，不重跑已接受任务来补日志。
4. 开发候选：在已声明范围内实施，适用任务按第 5.5 节执行开发内循环；保留失败、旧产物和累计消耗，改变检查条件仍走既有等义修正或合同变更路径。
5. 独立检查：对固定成果执行适用客观检查及所选语义评审，核实原要求、相关回归和迁就测试问题；按责任返修、恢复或保留未决，不用评审意见替代接受记录。
6. 验证后续使用：只拿交付件和声明工具，在新目录、新会话与新输入下完成任务及报告恢复，按 G05／G08 证明所选能力可用；不以旧答案回放冒充新任务。
7. 校验收益：按第 8 节在约定条件与额度内比较，分别报告修复、复用、相对收益及未证实部分。没有明显收益可以拒绝候选或保留有限结论，不自动扩样、增加修复轮数或降低标准。
8. 交付与采用：保存所选版本和比较理由，按维护归属更新包、指南或知识；项目明确选择并验证新版后才记录实际采用。后续周期引用已采用版本及新运行反馈继续检验，不自动部署、重开旧任务或抹去失败记录。

**收益校验与交付说明：**

| 可以报告的结论 | 所需证据 |
| --- | --- |
| 原问题已修复 | 原行为实际复现、同语义修后检查及适用回归；只支持该限定行为 |
| 改进可复用 | 交付件在新会话、新输入下实际完成任务，不依赖临时宿主补丁 |
| 相对基线有收益 | 相同或已披露差异的条件下，独立正确性、首次／最终通过、返修、人工介入和全部成本的逐项对照 |
| 有递归改进证据 | 已采用的新机制实际参与后续改进周期，并产生及保留经验证的效果；单轮修复或 A/B 不足以证明 |

报告同时保留回归、失败、未知和成本转移；Wiki 条目数、红绿配对数和评审篇幅不单独计为收益。比较整套升级时只归因于整套变化；若要识别 Wiki 或 Reviewer 单独贡献，按原 WP09 另行准备适用消融，不默认增加实验组或分母。

最终交付至少能定位所选版本、使用入口、声明依赖、采用的知识引用、检查／比较结果、未验边界和采用／拒绝理由，优先引用既有材料，不新增强制文件清单。分别报告源码已修、固定包已包含、项目已升级及后续效果；工程候选可以有限交付，真实使用或收益未验仍保留。原包、原记录及累计消耗不被覆盖，后续版本选择也不撤销已经发生的外部效果。

## 8. 如何评估收益，不把成本转移藏起来

### 8.1 最小比较方法

先明确一个改进假设和对应行为。以当前基线为对照、单一候选为处理组；如需识别 Reviewer 与 Wiki 各自贡献，再另行批准“基线、仅 Reviewer、仅 Wiki、组合”消融比较，不默认四组全部运行。

比较条件包括任务要求、允许工具和环境、客观验收、模型及实际服务配置、预算、停止条件，以及第 5.3 节各自固定的知识版本与初始状态。产品日常可继续跟随全局模型策略；为了可解释的对照，实验内记录并控制选用配置，不能把同时换模型的收益全部归给机制。

诊断／开发案例与保留案例分开。保留案例验证未参与调优的同类行为，不增加不相干的业务要求。重复运行次数和误差表达在实验批准前确定；少量样本只报告逐例结果，不宣称统计显著或普遍提升。

### 8.2 观察指标

| 问题 | 指标与解释 |
| --- | --- |
| 是否更可靠 | 独立验收通过情况、首次通过与最终通过分列；技术故障、业务失败和未完成分别报告 |
| 是否减少返修 | 同一缺陷重复出现、无效重复操作、定位到可行动原因的轮次；不以轮数越多越好 |
| 红绿证据是否可信 | 在预先声明适用的任务中，分别统计有效配对、缺 RED、环境阻断、条件不可比和仅开发 GREEN 的数量与原因；关联最终交付版本，未运行不算失败或通过 |
| 红绿机制是否有收益 | 在另行批准的比较中观察缺陷复发、定位成本和后续同类任务结果；记录复现／复测／报告成本。配对数量或报告覆盖率提高只证明可追溯性，不能单独证明产品更稳定或 RSI 有效 |
| 是否减少人工负担 | 真正需要用户决定的次数、无效“继续”请求、人工纠正评审的次数和等待时间 |
| 是否值得成本 | 全部模型会话／token／费用（可得时）、检查耗时、总墙钟时间、失败尝试与知识整理成本；缓存量不直接换算价格 |
| 是否保住成果 | 最终版本与已选候选对应；原通过行为是否退步；回退或拒绝是否正确保留证据 |
| 知识是否有用 | 查询是否找到适用且有来源的条目、是否实际被正确采用、过期或不适用知识是否误导；命中率不是任务成功率 |
| 评审是否有用 | 真缺陷发现、误拒和漏检的具体案例；独立检查与人工必要裁定分开，不以评审文本长度衡量 |

收益判定先满足既有必要正确性和权限要求，再比较预先约定的目标指标与可接受成本。预算耗尽、连续无进展或发现真实范围变化按原策略停止；不临时降低门槛或无限续测。已验收无关任务不为证明方法有效而重开。

### 8.3 建议的首轮优化边界

未来首次受控优化建议限制为一个明确故障类别、一个基线、一个候选方向，最多两次候选修订；这是待批准的工程建议，不是新增全局限制。模型调用数、费用、墙钟时间、检查预算和固定到期时间尚未确定，当前没有新增模型评测额度。到界保留未完成结果，不自动重置。
