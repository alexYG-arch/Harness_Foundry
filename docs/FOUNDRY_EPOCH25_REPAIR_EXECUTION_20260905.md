## Repairs

1. **Registered operators versus external domain rules.** The Demo byte-lineage
   operator now receives exactly two ref/digest pairs. Mutation `target_ref` is
   separate from evaluation inputs; neither Producer nor independent Validator
   requires the mutation seed to be the first operator input. Registered
   operators must pass arity, type, and numeric-parameter checks even when their
   input URIs require external resolution. Invalid explicit signatures are
   rejected, not automatically classified as external algorithms.
   Related collection comparisons now read complete ID collections. Four-way
   audio equality has an explicit n-ary operator. Domain dependency and interval
   rules use distinct identities instead of pretending to be the primitive
   reference-existence or scalar numeric operator. These domain contracts remain
   external implementation obligations, not executable acceptance evidence.

2. **Complete object bindings.** Render and observed-motion relations use the
   full object collections and join by unique `object_id`. They compare
   `asset_id`, `visual_intent_id`, `audio_anchor_id`, `sentence_ids`, `claim_ids`,
   `motion_segment_ids`, and `motion_curve_ids`. Motion segment/curve IDs are
   derived from each Motion IR object's segments. The observed relation compares
   both Render and Render's referenced Motion IR. Reordering objects is allowed;
   missing, duplicate, or changed objects are not.

3. **FFprobe counterexample isolation.** The negative recipe edits the referenced
   FFprobe JSON's `input_sha256` and recomputes the existing FFprobe receipt
   digest. It leaves the shared `video_sha256` unchanged. The reference mutation
   model operates only on in-memory documents and an in-memory byte overlay.
   The independent registry checker requires this content-mutation binding.
   Tests verify the target relation fails while receipt byte integrity and the
   shared Render/Motion video identity remain intact. This is not a claim that
   the complete External Lab Case has executed.

4. **ImageGen authorization content.** A dedicated reference operator checks
   a HUMAN `GRANTED`, single-use authorization of the correct class. It binds
   authorization ID, all nine exact-scope fields, the current Job, one recorded
   consumption, and the asset output to the generation receipt. It checks
   `issued_at <= receipt.executed_at < expires_at`, so later review does not
   reinterpret a legitimately completed operation using the current wall clock.
   `NOT_GRANTED`, revoked, wrong-scope, wrong-Job, expired-at-execution, and
   wrong-output evidence fail. Planned ImageGen and other asset routes skip this
   materialization-only predicate. Existing receipt byte-integrity checks remain
   separate. This operator neither grants nor consumes authorization.
