## 1. 目标、基线与非目标

### 1.1 目标

- 从已确认需求推导必要且足够的搭建方案，保留算法、模块组织和实现选择的自由。
- 在计划与早期建设中发现接口、环境和交付覆盖缺口，而非全部留到最终验收。
- 明确实现错误自动修复；局部问题不默认变成全局规则；满足约定交付条件后停止。
- 用 TDD 防止已知问题回归，再用独立 Run Test 发现计划遗漏、错误假设和组合缺陷。
- 继续使用自然语言确认与机器管理的版本/事件引用，不新增人工 Hash、Freeze 或逐 Workpack 授权。

### 1.2 当前基线，不重复建设

本计划基于本地提交 `7672696` 的公开通用 Build 路由。后续实施前检查最新工作树差异，不覆盖用户改动。

| 已有能力 | 代码/文档依据 | 本轮处理 |
|---|---|---|
| 完整来源、需求/Case 映射、产物归属和依赖检查 | `build_plan.py`、`build_authoring.py` | 保留；不能把结构覆盖等同于语义完整 |
| 公开验收合同定位、正常/错误样例工具 | `acceptance_contract.py`、合同对齐文档 | 复用；语义对齐不靠任意 Python 等价性证明 |
| 独立检查、范围内修复、上游 artifact 修复 | `build_runtime.py` | 先特征回归；没有失败证据不重写控制器 |
| 范围内重规划、共享原预算 | `build_replan.py` | 保留，不增加任务级人工批准 |
| 全部计划检查通过后停止、重入不重做 | `BuildController.advance` | 保留；不直接升级成完整交付结论 |
| 原生运行、耐久观测、源码公开 gate、固定提交打包 | 现有 runtime、`tools/check_release_source.py`、打包工具 | 复用，不建第二控制库或第二套运行状态机 |

2026-09-25 曾复跑 8 项针对性离线回归，不能作为本计划已实施或真实模型运行的证明。历史同包双案例的范围与局限以 [Tracker](V2_9_IMPLEMENTATION_TRACKER.md) 最新记录为准。

### 1.3 非目标

不恢复旧 Candidate/epoch 路线；不引入视频等专项；不重建 Codex Agent 循环；不建设通用自进化平台、多模型排行榜、全平台矩阵、全量攻防或 Hash 链；不改变已确认业务合同以便测试通过；不自动修订正在运行的独立检查器或 Foundry 自身；不在本轮推送、发版或修改历史数据库。

## 2. 修补范围与归属

### R1：需求到最小搭建方案

在现有上游问答、搭建文档和 Skill 中落实以下设计工作，不新增必填的大型模板：

1. 区分公开行为/交付约束、用户待决定事项，以及 Agent 可自行决定的实现细节。
2. 由实际输入输出推导阶段、依赖、必要持久状态以及 CODEX/LOCAL 分工。
3. 对引入的常驻机制说明它解决哪项真实需求；没有必要时不生成记忆库、路由层、额外服务等模块。
4. 将已确认的全局约束和相关来源交给每个消费任务；原文保持可读，不用摘要替代。
5. 先说明现成能力由谁提供，再决定项目中生成什么。用一小段方案说明即可，不新增必填复杂 Schema：

   - Codex 载体：复用实际可用的模型执行与工具调用能力，不假定尚未确认的接口或后台行为。
   - Foundry 宿主：复用已有需求/权限绑定、依赖推进、独立验收、预算和耐久恢复。目标任务不能接管控制库、授权或独立检查器。
   - 项目 Harness：只实现该项目特有的规则、接口适配、必要本地步骤及未被上述层覆盖的能力。

复用不等于强制引入某个框架；实际不适用时允许选择更小的实现并简述原因。论文的弱种子是实验对照，不是要求 Foundry 清空成熟底层后再造一遍。

验收看方案是否覆盖目标、能运行且不擅自扩域，不比较是否采用某个唯一目录、模块数或参考 DAG。若现有机制已经正确，只补样例、指令和必要回归，不制造红灯来证明需要改代码。

### R2：阶段接口与实际调用前置

规划时按一个真实调用检查生产者/消费者的参数、数据形状、路径、解释器、临时目录与读写权限。契约必须说明可观察接口，内部表示仍开放。

授权后优先实现一个最小纵向切片：一个有效输入经过必要阶段，产生可被下游实际消费的输出。它是现有计划中的实施顺序，不是额外人工关卡；不能只跑 `--help` 或检查文件存在。完整交付范围仍保留在计划中，不将切片通过当整体通过。

复用当前 `test_execution.py`、工具绑定和工作目录接口。仅在复现缺陷后修对应 producer、参数传播或运行适配；不强制所有 Harness 使用本次案例的接口。

对本轮新增或修改的关键机制，先写清适用条件和预期行为，再按三层证据检查：

- **存在**：代码/配置已声明；仅算实现线索。
- **触发**：真实入口在适用场景调用了它；复用已有执行记录，不增加逐函数事件体系。
- **作用**：实际结果符合对应公开要求，例如恢复后未重复实施、错误产物回到正确生产者。触发本身不证明有用，更不证明统计性能提升。

按约定必须提供的能力不能因未触发而删除或算通过；在预定预算内补其适用场景，未覆盖则如实报告。与需求无关的可选死代码可局部删除。已有 B05/B06 等场景足以提供证据时直接复用，不再多跑一轮。

### R3：交付覆盖和停止条件

从已确认搭建文档反向核对：必要交付物、公开调用方式、实际使用场景、既有行为保留、适用的恢复要求，是否进入 Requirement/Plan/检查。

- 不要求仅用于生成 Harness 的项目额外开发完整业务产品；实际业务使用验收的范围须先写清。
- `PLAN_CHECKS_ACCEPTED` 继续只表示计划检查通过；保留 `harness_e2e_verified=false` 的现有通用 CLI 语义。
- 宿主交付说明引用已有 Case、原始运行结果及未完成项，不通过一个新布尔字段自签完整交付。
- 当前已约定交付全部完成后停止。新增优化或研究建议进入后续待办，不自动扩张本轮要求。
- 再次 read/advance 在内容、权限有效且无变化时，不增加 attempt、修改产物或重新请求授权。

### R4：范围内自动修复及必要的停顿

先保留并验证已有行为：明确 ASSERTION → 责任产物/生产者 → 原范围内修复 → 独立复验 → 后继；LOCAL 检查本身不会因重试获得修改上游代码的能力。

完善宿主指引和反馈对接时，确保机器处理 `read-build`、当前 revision、事件 ID 和后续推进，不把这些字段交给用户手工搬运。

| 失败类型 | 处理与停止规则 |
|---|---|
| 实现违反明确合同，且属于原写域/预算 | 自动修复；如缺陷来自声明输入，使用现有 artifact 修复归属 |
| 缺输出或可确定恢复的中断 | 使用现有有限修复/耐久恢复，不重置预算或重放已完成实施 |
| 合同缺失、矛盾或需要产品选择 | 返回具体问题及影响；不猜需求、不修改判定标准 |
| 检查器、环境、Foundry 核心故障 | 诊断并定位到正确层，不误标 ASSERTION；本计划不把原范围扩成通用自修复权限 |
| 预算耗尽、到期/撤销、未知副作用 | 停止并提供原始证据和所需决定，不能靠换 ID 续跑 |

需要修 Foundry 核心时，使用独立的源码工程范围及本计划 A/B 验证，不让目标 Agent 热修改控制器。普通实现修复不得降低 Validator，也不得重复要求“继续”或 Hash。

### 归属判定

依次问：违反谁的承诺、去掉业务细节后是否仍成立、根因最小修复在哪里。公共保证被破坏，一个可复现案例即可修核心；仅有局部适配则留在项目或可选适配器。修核心实现不等于新增通用规则。没有复现和收益证据的“通用优化”不阻塞当前交付。

## 3. 双层测试的互补关系

| 维度 | A：TDD 修复 gate | B：独立 Run Test |
|---|---|---|
| 要回答的问题 | 这个明确缺陷是否被修好，是否会回归？ | 从真实使用链路看，是否有漏需求、组合或运行问题？ |
| 测试依据 | 被违反的公开合同＋最小复现 | 原始项目材料＋已审搭建文档＋外部行为，不从修复 diff 推导全部预期 |
| 主要实现 | 标准库 unittest、局部/跨模块回归、真实临时本地子进程 | 公开入口、固定包、原生执行、真实模型、新会话使用、包外独立观察器 |
| 样例来源 | 已知失败及必要正常/相邻例 | 不同具体数据、阶段组合、重入/恢复及未用于调试的实例 |
| 隔离要求 | 测试失败原因与补丁对应，不删除既有有效断言 | 不导入 A 的期望结果或调用被测 Harness 的判定函数充当最终 Oracle |
| 何时运行 | 每个修复的前后；合入时相关回归 | 早期纵向试跑；集成完成后的固定包正式运行 |
| 不证明什么 | 不证明模型会正确搭建，也不证明完整交付 | 不证明所有未来项目无缺陷，也不是自动发布许可 |

可共享公开格式解析、通用进程采集和业务合同文本，不能共享决定正确性的同一个实现。两个 Agent、两个脚本或两个会话本身不等于验证独立；同一宿主也可通过独立预期和隔离的观察器实现这两层。

## 4. A 层：把 TDD 放入修复 gate

### 4.1 单个修复的流程

1. **定位**：记录实际失败、预期公开行为、归属层、最小输入和受影响路径。
2. **RED**：先加入能在未修复版本上失败的最小回归。检查失败必须来自业务/控制断言，不是缺依赖、导入失败或错误环境。
3. **GREEN**：在正确责任层作最小修复，保持原验收语义。修 producer 和控制流，不能只改测试期望。
4. **REFACTOR**：必要重构后运行正常对照、相邻边界、受影响模块及依赖回归。
5. **独立核对**：从合同复查断言是否真的有依据，确认失败不会仅因另一个错误被掩盖。
6. **通过 gate**：才进入集成；保留失败与通过的简短证据，不新增签名/摘要链。

若原实现已经通过新测试，标为“能力已存在/补覆盖”，不得声称修了缺陷。指令或语义设计改进可能无法通过确定性单测证明 RED；这种情况先保留现状样例和可观测失败，A 只验证传递/控制协议，真实设计质量由 B 验证。不能把 prompt 中出现某句话当作模型行为已正确。

### 4.2 TDD 场景清单

以下是覆盖义务，不是强制新增相同数量的测试；已有测试满足时复用。新缺陷才补新的最小复现。

| ID | 场景与预期 | 主要落点 |
|---|---|---|
| A01 | 不同输入/项目形式仍保留全文、全局约束及来源；缺关键决定不能后台自批 | `test_build_review.py`、`test_source_intake.py`、`test_build_authoring.py` |
| A02 | 需求/Case/产物遗漏、依赖错误被拒；不同合法任务组织都可用，不注入专项阶段 | `test_build_plan.py`、`test_build_replan.py` |
| A03 | 同一合同的非空正常例通过，错误元素/结果被拒；崩溃不算负例成功 | `test_acceptance_contract.py` |
| A04 | 相同入口在内部 workdir、外部 workdir/只读源码和绑定子解释器下正确运行 | `test_test_execution.py`、`test_release_acceptance_adapters.py` |
| A05 | 下游发现上游声明产物缺陷后回到正确生产者，保留无关已通过分支 | `test_build_runtime.py` |
| A06 | 失败→修复→后继在一个范围批准内完成；不修改 checker、CASE 或权限，不退款/扩预算 | runtime、entrypoint、replan 回归 |
| A07 | 完成后再次推进零新派发；局部计划通过仍不宣称完整交付 | runtime、entrypoint 回归及交付报告测试 |
| A08 | 已完成观测恢复不重做；未知副作用、合同缺口、检查器/环境失败不假扮业务失败 | runtime、合同及观测回归 |
| A09 | 修复不强制手输 Hash；实现变更不产生无关人工门；真实合同/权限变化仍停止 | entrypoint、review、Skill 合同回归 |
| A10 | 开发测试报告不以最终 PASS 覆盖首轮失败；复用场景中 Harness 版本变化不能被记为同版成功；缺失模型/配置证据不冒称可比 | WP4 的开发适配器/报告测试，优先扩展现有 release acceptance tests |

必要时只为本次最关键的断言在一次性源码副本上做一个针对性破坏，确认测试会报警，例如移除“完成后不派发”判断。它是测试敏感性检查，不建立全库 mutation 攻防平台，不编辑历史或正式包。

### 4.3 Gate 层级与命令

- 每个修复：最小 RED/GREEN → 受影响模块与相邻路径。不能要求每次保存文件都跑全量。
- 源码集成后：按 AGENTS 执行全量现有回归，并记录 skipped/opt-in 而非记为通过。
- 新增必要公共回归加入 `tools/check_release_source.py` 的模块集合，沿用现有 CI；不能另建较弱的“绿色”检查绕过当前 gate。
- 工作流/Skill 改动后运行规范与 Skill 检查；历史规范检查仅是历史基线，不升级为真实运行证明。

现有命令如下；实施时使用已声明测试依赖的环境，新报告路径由宿主选择，不要求用户复制 ID：

```bash
PYTHONPATH=src python3 -m unittest discover -s tests -p 'test_*.py' -v
python3 tools/hffactory.py verify-spec --json
python3 tools/validate_skill.py
python3 tools/check_release_source.py --report <新的报告路径>
```

必要公共测试出现零发现、失败、错误或跳过时 gate 不通过。缺基础设施属于 NOT_RUN/BLOCKED，不修改断言取得绿色。没有生产源码变更时不重复无关全量或真实模型运行。

## 5. B 层：独立、较全面的 Run Test

### 5.1 关键补强：不能从预制 Plan 才开始测

现有 `devtools/release_acceptance/prepare.py` 为固定双案例预置 H/U/E 等阶段，适合运行器和组合回归，但不能单独证明“从需求推导计划”的质量。

本次 B 的真实路径应为：

```text
原始材料与开发目标
  → Agent 问答、搭建文档、方案推导
  → 人工确认实际文档
  → Agent 生成 Requirement/Plan；独立核对需求覆盖与接口衔接
  → 展示具体运行范围并获得实际批准
  → 从固定包建设 Harness，记录首次下游使用前的版本
  → 新 Codex 会话实际读取、调用 Harness 完成约定使用任务
  → 一个选定工程以同版 Harness 完成第二个已约定任务
  → 外部业务检查＋组合/修复/恢复/停止检查，分别记录首轮与最终结果
  → 按既有合同交付，或将真实缺陷回流 A
```

搭建文档之前没有 Program/目标，模型工作负载之前没有隐式运行权。测试材料不能预填批准；新会话使用不是模型多样性测试。现有固定 Plan 夹具保留作回归，不作为这一段能力的替代。

### 5.2 案例选择：复用业务，增加真正不同的压力

先复用已公开的 Task CLI 新工程与 CSV 既有工程增量的业务材料，避免再造大型专项。重新取得所需确认/运行权，不继承旧批准。两例是本次测试选择，不是 Foundry 产品的固定项目数。

| 案例 | 要观察的搭建能力 | 独立外部观察 |
|---|---|---|
| 新工程：Task CLI | 从需求形成最小开发 Harness；新会话依据它开发并检查应用 | 直接调用业务 CLI、核对状态/输出/错误；不能只相信生成的测试报告 |
| 既有工程：CSV 增量 | 理解已有代码与说明，保留旧 API、测试和用户笔记，只实现约定增量 | 用事先确定的输入/输出对照检查原功能和新增功能；核对不应改变的文件/行为 |

每例准备少量未参与 A 调试的有效/无效输入、合法路径/工作目录变化和边界数据；预期来自公开业务合同。不得偷偷增加性能、平台或数据格式要求。项目算法可不同，实际公开行为必须满足合同。

为避免只验证老案例拟合，在其中一例保留新的数据实例与合法目录组合。它仍不能证明跨所有业务领域泛化；若将来新增非 Coding 能力承诺，再选择对应工程，不在本轮扩成所有领域矩阵。

### 5.3 Run Test 场景矩阵

R 为本轮固定范围。失败后只修范围内问题；新的产品能力请求进入后续，不无限扩张 R。

| ID | 运行场景 | 通过标准与独立证据 | 主要补 A 的盲区 |
|---|---|---|---|
| B01 | 原始需求到搭建文档/Plan | 对照源材料，没有漏掉约定交付；说明能力归属和复用；实现选择开放，不靠预制 DAG；关键歧义实际提出 | 缺失需求根本没进入 IR，或重复建设底层，结构测试仍绿 |
| B02 | 正常新建与既有增量 | 同一固定包真实建出 Harness；新会话确实读取/使用；首轮和修复后结果分别保留；最终外部业务结果满足合同 | 文件/模板存在但不可用；初始缺陷被最终 PASS 掩盖 |
| B03 | 生产者→消费者组合 | 实际公开入口、数据形状、子进程解释器、两种合法 workdir 均可用；只读对象未被写入 | 各阶段单独通过，组合失败 |
| B04 | 未参与调试的实例与关系检查 | 按合同验证新增实例；仅使用合同成立的关系，如 CSV 行置换不改变汇总计数 | 对少量固定样例硬编码、输入分布过窄 |
| B05 | 明确缺陷的真实修复 | 独立检查拒绝；反馈进入有写权限的生产者；真实模型修改相关实现；复验与后继通过；原授权/预算不变 | “重试即修复”或测试脚本手动恢复被误认成自修复 |
| B06 | 宿主中断与新宿主续跑 | 指定实际执行窗口被触发；耐久观测恢复，不重放已完成实施，不退款；后继正确推进 | 仅模拟 PASS 或正常返回被误认成中断恢复 |
| B07 | 完成交付与再次推进 | 外部交付义务通过后停止；再次 read/advance 无新增 attempt、模型调用或产物变更 | 计划绿就过度宣称交付、完成后继续优化 |
| B08 | 必须暂停的真实边界 | 缺合同/错误检查器/失效范围在隔离场景中正确暂停；不要求 Hash，也不静默越界 | 所有非零都当业务失败、机器引用被回抛用户 |
| B09 | 同一 Harness 跨两个任务复用 | 选定工程内，同版 Harness 在独立会话中承担初始实现及另一项已约定开发任务；业务结果分别由外部检查；Harness 没有为第二任务被暗中改写 | 一次使用或多组业务数据被误认成开发 Harness 可复用 |

B01 的语义核对不能由另一个模型一句“PASS”代替：按源材料逐项指向计划和行为证据；真正的用户决定仍交用户。B08 优先使用真实本地命令/一次性控制库和公开入口，不为已经有充分离线证据的每个错误再付费调用模型。

场景编号不是执行顺序：B09 是事先约定的交付义务，必须在 B07 的最终完成判定之前运行，不通过重新打开已完成范围来追加第二任务。

### 5.4 故障注入与测试自身的可信度

- 先校验外部观察器：已知正确样例必须通过，已知错误样例必须拒绝，观察器崩溃不能当“成功拦截”。
- 少量定向故障只发生在本轮一次性目标/副本或明确的观测窗口，全部预先写入测试范围；不修改历史包、旧产物或控制数据库。
- B05 优先使用自然发生且可复现的违约；若没有，使用预先设计的有限注入。注入发生在首次验收之前的明确产物/接口，必须有真实运行授权，不用手改已验收文件制造漂移。
- 若测试方法需要宿主注入，精确披露位置和时机，标注为“注入缺陷的真实模型修复”，不是“模型自然犯错”。维修必须由真实任务修改产物，不能由探针撤除故障后宣称模型修好了。
- 不为强行走到下游而削弱已有阶段检查。若故障先被上游发现，就如实记录；没有触发的跨阶段分支不能冒称已验证，按剩余范围决定是否运行预定补充场景。
- 生成的检查器应拒绝错误业务副本；但最终正确性仍由外部业务观察器判断，不能让两层共同依赖一个“永远 PASS”的函数。
- 恢复探针优先复用现有 `recovery_probe.py`；未实际进入指定窗口记为 NOT_EXERCISED，不记通过。

### 5.5 隔离与留出实例

期望行为在运行前依据已审需求确定；具体留出数据与 Oracle 放在实施任务写域/必要时读域之外，不能把隐藏测试变成隐藏需求。实现者可看到公开合同和开发样例，不能看到所有留出答案后继续声称“未见评估”。

共享的是公开合同，不是 A 的测试答案、内部私有函数或实现生成的自评。每个失败保留实际命令、stdout/stderr、业务结果和运行版本。

留出实例用于定位修复后，就转为开发/回归样例。预先保留一小组后备实例；不用每次失败临时发明新标准，也不通过无限换种子挑一轮绿。边缘波动才做预先限制的复跑，不给所有用例机械加多次重复。

### 5.6 固定包、预算与触发频率

- 开发早期只跑最小纵向试验，报告为诊断；A/接口稳定后用明确提交组装固定包，运行最终 R。
- 真正模型运行前展示实际包、两例完整文档/Plan、模型与服务、工具、verifier、读写路径、故障注入、预算和到期时间。机器管理包身份，不要求用户输入摘要。
- 预算初稿：每工程最多 10 个 attempt、每任务最多 2 次、单命令最多 900 秒、范围有效期 4 小时。它只是估算，必须在具体 Plan 生成后核算建设、首次/第二次使用、修复、恢复及本地任务数量并展示最终值；不足不能执行中自动加次数。
- 统计模型/本地调用、耗时及已有 usage；调用/时间限制不冒称 Token 或账单硬上限。新会话准备及宿主分析成本也应与目标运行统计区分。
- 授权可一次覆盖两例已展示的运行范围及范围内修复/恢复；不逐任务批准。测试方法/合同、绑定 checker、权限、包或预算的实质变化按真实边界重新处理，不借“自动测试”绕过。
- Foundry 包字节变化后不能继续把结果合并为同一包验收。新固定包先跑受影响诊断，最终 R 的必要场景须有该版本的证据；可批量修完同一问题族后再跑正式 R，避免每改一行重跑模型。
- R 可映射到少量组合运行，不要求每一行启动一个新的模型。真实运行不加入普通 push CI 的默认付费路径；CI 继续负责 A 和 B 的离线适配器测试。

### 5.7 首轮搭建与修复后交付分别记录

“首轮版本”是构建者提交用于第一次下游独立使用、尚未消费该次下游 Run Test 反馈的 Harness。允许正常的构建期调试和 A 层自测；它不是模型第一次输出的代码，也不限制一次任务内部的推理/工具次数。

- 首轮记录：相应 Foundry 包、Harness 版本/产物引用、实际进入的场景、逐场景结果及失败归属。
- 如果连下游使用前提都未满足，记录“构建未就绪”及原因，不从案例集合中删除。基础设施导致无法观察时记未验证，不冒充 Harness 质量结论。
- 修复记录：哪些失败反馈被使用，改动属于业务实现、项目 Harness 还是 Foundry，累计次数/耗时及实际可得 usage。人工/测试注入与自然发生的缺陷分开。
- 最终记录：最后用于交付的 Harness 版本及其完整场景结果；它可以不同于首轮版本，但不能用最终结果覆盖首轮失败。
- Harness 没有变化、只修业务实现时也要分清，不将任务内修复包装为 Harness 升级。
- 复用现有 attempt、产物身份、运行记录或必要的小范围副本；不对每轮新增全树 Hash、冻结令牌或人工批准。

首轮质量用于定位搭建改进，最终合同是否满足仍决定交付。本轮只有少量案例，逐例报告，不据此声称稳定成功率或统计显著改善。

### 5.8 B09：同一 Harness 的第二次真实任务

默认在 Task CLI 工程安排一个小型复用场景，不额外增加第三个大型工程。具体两个任务写入实际展示的测试搭建文档：

1. 新会话使用已生成 Harness 完成原合同内的初始实现。
2. 另一个新会话使用同一 Harness，完成原合同内一个明确业务缺陷的诊断与修补。它可以复用 B05 的业务实现缺陷场景，但只有两者各自证据都满足时才同时计入，不能靠命名合并。

第二次任务不是重复运行同一命令，也不是把 CSV 换几行数据；业务代码可按任务范围变化，Harness 的规则、脚本和配置不得为第二次任务偷偷改写。会话应实际读取/调用 Harness，外部观察器独立检查两次任务结果。

选择复用版本时可使用首轮已合格版本，或经过明确修复后用于最终交付的版本。若第二次任务要求改 Harness，保留旧版的复用失败，形成新版本后才讨论新的复用证明；不能把两个不同 Harness 的成功拼成同版成功。新版本须具备两类任务的对应证据，运行仍受原剩余范围与预算约束，不自动重置。

人为业务缺陷只放入提前声明的一次性输入/副本，并在其首个验收前安排，不手改已验收业务文件或控制状态。初始应用到修补任务的文件版本、输入依赖及替换关系在 Plan 中明确。若没有合适的天然缺陷，注入方式沿用 §5.4 的披露和真实修复要求。

生成 Harness 的固定脚本/规则与正常允许变化的运行数据须分开声明。实际有需求的检查点、业务输出等状态变化不是代码升级；也不能把改规则伪装成状态变化。若所测 Harness 本来不需要持久状态，不为此新增状态管理。

### 5.9 仅在声称优化收益时进行同条件比较

修正明确违反合同的错误，依据 RED/GREEN、相关回归和 B 的实际结果闭合，不增加“必须优于旧版分数”的门槛。

如果要声称某项规划/工具/恢复策略让搭建更高效或更通用，再安排小范围旧版/新版对比：

- 固定公开任务合同、输入实例、执行模型、有效工具/CLI 配置、权限、检查器和预算；记录构建者与执行者各自角色，不把新会话当成新模型。
- 使用可观测的实际模型/客户端信息；服务内部版本无法获知时说明未受控因素，不能仅凭同一模型名称宣称严格可复现。
- 同时报告任务结果、回归和成本；构建、后续使用、修复三类成本分开，未知 usage 不填零。
- 先确定比较和有限复跑安排；不得从多轮结果里只挑最好的一次，也不把小样本波动直接归因于代码。
- 没有清楚收益时，不新增可选优化或全局规则；保留本来合格的实现。不因此保留已经确认违反合同的缺陷。
- 不默认对所有修复重跑旧包，不新增多模型矩阵，不照搬论文的固定重复次数/演进预算。比较未获授权或未做时，就不提出收益结论。

这不是第三层测试，属于 B 在提出优化主张时的一种使用方式；所需调用必须预先计入展示的具体范围。

## 7. Run Test 发现问题后，如何回流而不无限循环

```text
B 发现失败
  → 核对是实现/计划/测试基础设施/合同问题
  → 判断项目、适配层还是 Foundry 核心归属
  → 缩成 A 的最小复现（语义问题保留具体案例，不伪造确定性证明）
  → 修根因 + A gate
  → 复跑受影响 B 场景及相关正常对照
  → 同一最终包的 R 汇总
  → 达成交付则停止；范围外建议进入后续
```

- B 的业务失败不能因为 A 通过被忽略；检查器故障不能作为产品已失败或已修复的证据。
- 失败归属在原有范围内明确时自动推进，不要求人重新发“修复”或 Hash。
- 相同失败签名再次出现且没有新证据/不同修复假设时，先诊断原因，不重复派发同一个无效命令。
- 新发现的范围内缺陷记录并处理；发现范围外能力需求不偷偷加入 R，也不隐瞒，应明确报告后续建议。
- 若需要修改公开合同或绑定检查器，先说明差异与原因，不能只放宽 Validator；按真实权限边界更新后续范围。
- 预算到期/耗尽、未知副作用或重大用户决定是真实停止点。停止时报告剩余问题，不宣称“直到所有可能问题为零”。

## 8. 最终通过条件与报告

完成本计划需要同时满足：

1. R1–R4 的实际变更或“无需改动”的结论有证据，变更落在正确责任层。
2. 每个明确修复有 RED/GREEN 或诚实标明已有行为/语义改进的证据；相关回归和当前公开 source gate 通过。
3. 固定包的 B01–B09 覆盖义务有实际结果；未触发、未运行、缺基础设施不能算通过，也不能用两个脚本自评替代真实调用。首轮及最终结果分别保留，B09 确认同版 Harness 对两类任务的实际使用。
4. 两个案例的原始需求、搭建方案、生成 Harness 与实际使用行为对应；局部通过没有被宣称为全部交付。
5. 明确违约的修复、后继推进和完成停止无需逐任务人工介入；真实边界仍有效。
6. 本次验收范围内没有已知未解决缺陷。不能从有限案例宣称普遍无缺陷、跨全部模型/平台或所有领域适用。

## 10. HarnessDev 的采用边界

参考：[HarnessDev: Can LLMs Create and Evolve Their Own Agent Harness?，arXiv:2609.01437v1，2026-09-01](https://arxiv.org/abs/2609.01437v1)，[原文](https://arxiv.org/html/2609.01437v1)。

- §3.1–3.5 区分创建、执行、评价及创建/演进，并评估可复用 Harness；本计划据此细化首轮与最终记录、同版跨任务使用。这里的首轮口径是 Foundry 工程定义，不冒称论文的原始指标。
- §4.2 讨论声明机制与实际触发的差别；本计划只检查本轮关键机制，触发不等于因果收益。
- §4.3 的版本波动和执行模型依赖，支持对优化主张采用受控比较；不把论文的噪声数值、评测规模或预算移植成 Foundry 阈值。
- §6.1 的覆盖与固定开发环境限制，不能证明递归自改控制器安全，也不能直接外推为所有模型、领域和平台的结论。
