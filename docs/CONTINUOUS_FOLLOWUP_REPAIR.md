# 连续跟进与入口衔接的通用改进

基线：v1.2.2／105cf3f。2026-10-31 工程实现与验证；本次源码提交不代表已部署或发布。
协议2.9不变。本文记录本次增量，不改旧验收、累计消耗或既有规划分母。

## 问题归因

原生 `CONTINUOUS` 负责就绪任务、实施、独立检查及范围内有限返修，并非 Chat 通知服务。
核对 v1.2.0、v1.2.1、v1.2.2，均已有连续模式及合同缺口交回逻辑，不能将此次现象解释为
v1.2.2 新增停止限制，也不能据此推断过去从未出现相同问题。

此次线索暴露两处通用不足：外层可能在启动后台后结束跟进；生产者得到下游要求，
却没有在同一任务上下文中得到下游产物与依赖声明，容易生成无对应提供者的共享入口。
具体路由错误、计划职责遗漏和用户合同缺口仍须分别核实；缺某个文件名不能直接证明
必须新增文件或重新授权。

原生交回不代表整项搭建结束。既有范围与入口足够时，外层继续诊断、修复和合法接续；
真正缺少用户决定、权限、预算，或存在到期、撤销及未决效果时，才停受影响执行。
原生自动返修与外层处理互相衔接，既不原样反复重试，也不将所有 HELD 都变成人工门禁。

## 最小改动

- `build_authoring.read_build_task_context` 在原有 `downstream_obligations` 中增加直接消费者
  的 `artifacts`、`depends_on`，取自同一已固定提案。新提案不回改旧上下文，返回对象不修改存储。
- 实施提示利用这些声明核对共享入口的提供者；允许共享模块、已有工具、延迟注册及内部实现自由。
  声明不代表文件已生成，也不授予前序额外读写权限或提前实施后继的权力。
- 源码及分发 Skill／AGENTS 明确持续 Chat 跟进、交回后的处理责任及真实停止边界。
  复用原等待、状态读取、报告恢复和修正入口，不新增控制器、定时器、审批或通用预检。
- [设计指南](HARNESS_DESIGN_GUIDE.md#4-这些部分能实际接起来吗)补充公共行为、实际调用目标、
  产物归属和依赖先后的核对；[运行指引](GENERIC_BUILD_RUNTIME.md#持续执行与外层接续)
  区分原生返回、外层继续和确实需要人类决定的情况。

没有变更调度、权限校验、预算扣减、接受判定及数据库恢复逻辑。旧捕获仍按原命令身份取回，
旧失败和消耗保留。没有接续诊断线索中的业务，没有改变其 Plan、检查器或运行记录。
