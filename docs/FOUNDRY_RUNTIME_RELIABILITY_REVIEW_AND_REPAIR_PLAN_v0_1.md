# Foundry 运行可靠性：整体复核与收敛修复方案 v0.1

日期：2026-09-19。状态：`PROPOSED_NOT_IMPLEMENTED`。

实施细化见 [Workpack 执行方案 v0.1](FOUNDRY_RUNTIME_RELIABILITY_WORKPACK_EXECUTION_v0_1.md)：
定义 R0–R5 改动面、接口决定、配对回归、串并行顺序及当前 M1 处置。该方案仍未实施，不构成运行批准。

这是本轮文献、社区报告、源码和本地复现的审查产物，不是实施完成、运行批准或发布结论。
它细化现有 `FOUNDRY_GENERIC_CODEX_HARNESS_UPDATE_PLAN_v0_2.md` 及 Workpack execution annex，
不另建 Program、控制库、Requirement/Plan revision 或 Freeze 链路。工程进度仍归现有 Tracker。

## 1. 结论及适用范围

反复暴露问题的主要原因不是已经证实的 Astra 推理能力不足，也不是 PRD 有中文，
而是 Foundry 从静态生产/校验向真实运行产品扩展时，运行数据、恢复和验收仍存在接口断层。
修复与测试经常围绕上一次错误消息完成，成功长路径和故障恢复路径没有同步闭合。

当前方案不是推倒 Foundry，也不是继续增加 Validator。应保留已经有价值的单库事务、
Requirement/Plan 分离、宿主范围批准、独立验证及“不把退出成功当作业务验收”；
集中修复接收器、运行观测、恢复路由、执行环境与发行闭包，并调整工程验收顺序。

本轮覆盖 generic Build 的接入、授权、原生 Codex/local 执行、观测、验证、推进、恢复、打包及其测试。
它不是所有历史兼容模块的穷尽证明。视频专项不重新进入目标；尚未完成的专项退役继续归 W1A/W5B/W6。
最终边界仍是：他人可接入 Codex，用同一发行包搭建并使用明确需求范围内的 Coding Harness。
M1 是子流程联通，不能代替完整 PRD、全部通用能力或发布验收。

## 3. 根因分组：一次修复一个故障类别，而不是一个错误字符串

| ID / 优先级 | 已确认问题与代码定位 | 共同根因、影响和闭合方向 |
| --- | --- | --- |
| R-F1 / P0 | `local_process.py:112–167` 限制每流 65,536 字节，先按字节裁剪后解码，并合并 stdout/stderr 的 truncated 标志；`coding_process.py:172–180` 将其作为协议判定输入 | 人读日志和机器事件共用有损通道。完整终态被丢失，stderr 裁剪也触发未知；修流式采集合同，不只调大上限或忽略解码错误 |
| R-F2 / P0 | `coding_process.py:126` 使用 `--ephemeral`；`build_runtime.py:454–464` 在 runner 返回后才记录命令观测；临时输出不保留 | 执行效果与耐久观测之间有恢复空窗。不能靠退出码补造终态，也不能承诺外部效果 exactly-once；需要 attempt 归属的耐久命令观测及核对策略 |

以上是不同层次的通用缺陷，不应归为翻译应用专项。R-F1 的 Unicode、末尾终态、stderr 三种表现属于一个根因，不能拆成三轮临时补丁。

另有两个需要验收、尚未证实为本次根因的风险：

- 当前客户端实测为 `0.155.0-alpha.9.2`；接收器依赖具体参数和事件。未知事件严格拒绝与版本漂移可能影响可用性，需要受支持版本的协议契约测试；不能宣称升级 CLI 必然修复。
- 指令 preflight 检查可读性，不证明相关 Skill/引用资源和角色语义都可用。项目配置冲突目前按停止处理；是否支持、如何提示应明确，不靠授予整个主目录读取解决。

当前 Tracker 已明确 W4B 的部分检查恢复等未完成，不是所有缺口直到本次才出现。
但其上方摘要仍有 M1“未运行”，后方已有实际失败记录；应从同一证据更新当前投影，避免读者将旧局部完成或旧 NOT_RUN 当作现状。

## 4. 为什么前面修了多轮仍然出问题

1. **真实路径逐层揭露。** 早先启动读取失败阻止模型真正运行；修复后才走到长输出采集。现象先后出现，不代表新补丁一定制造了后一缺陷。
2. **回归反映了旧假设。** 若测试将“截断即未知”视为正确，只增加同类型断言不会发现完整合法任务被误杀。需要检查假设本身及正向能力。
3. **控制安全与产品可用混在一起。** 不误验收是必要条件；永久挂起不能代替恢复能力。前序推进过于依赖局部绿灯，对可用性证据要求不够完整。
4. **真实环境组合太晚验证。** 配置、父级指令、工具路径、原生事件和长任务被分开测试，实际 M1 成了组合测试。应在进入大 PRD 前以生产通道跑小型纵向探针。
5. **闭合单位是补丁而不是行为。** “改一处、加一例、全套绿、再试”缺少故障类别、影响面和收敛规则；容易把运行适配器/验证器故障误派给模型修改业务代码。
6. **生成时代证据不能继承为运行产品验收。** Foundry 2.9 使用标准上游链路生成、结构符合、旧核心能力通过，都不能自动证明新的原生运行与恢复能力。问题不在于必须换上游生成器。

因此本轮不建议再补一处编码错误后直接 M1 重跑，也不建议重写全部 Foundry 或无限扩展审查范围。

## 5. 文献和社区对设计的启示

### 5.1 官方产品与工程材料

- [Codex non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode)：`--json` 输出机器事件，`--ephemeral` 不保留 rollout。由此推导：显示裁剪不能成为协议裁剪；恢复证据必须由明确的持久化设计承担。
- [GPT-6 Astra prompting guidance](https://developers.openai.com/api/docs/guides/latest-model#prompting-best-practices)：强调清理冲突的 AGENTS/Skills、让模型持续完成授权内工作、对真正缺失信息提问。用于减少重复实施指令和虚假人工 Gate，不用于免除宿主约束与独立验收。
- [Codex App Server lifecycle](https://learn.chatgpt.com/docs/app-server#lifecycle-overview)：提供线程/轮次生命周期和恢复接口。可作为未来有持久交互需求时的适配选项；本轮优先修现有 CLI 通道，不引入双后端迁移来掩盖当前问题。
- [Anthropic: Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)（2026-01）：区分轨迹与环境中的实际结果，并要求检查评分器。对应本项目：模型说完成、生成测试或终态事件，都不能替代独立业务 Case。
- [AWS: Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)：重试需要稳定请求身份和效果语义。这里采用既有 attempt/command ID 与单库事务；不把全文件 Hash 或“再跑一次”当作幂等。
- [Python incremental codecs](https://docs.python.org/3/library/codecs.html#incremental-encoding-and-decoding)：跨块字符必须有解码状态。可修复合法 UTF-8 被块边界破坏，但它单独不能解决终态丢失或恢复持久化。

### 5.2 研究文献

- [Towards a Science of AI Agent Reliability](https://arxiv.org/abs/2602.16666)（2026，v3）：可靠性不应缩成单个成功率，需观察不同条件下的一致性、稳健性、可预测性与安全性。这里采用有限场景矩阵，不照搬整套研究指标；论文不是 Foundry 或 Astra 的实测结果。
- [HarnessLens: Verify Smarter, Evolve Further](https://arxiv.org/abs/2608.27311)（2026-08-27 预印本）：按修改影响的行为选择验证，并用留出集检验，避免总分掩盖回归。研究限于一个模型家族及若干 Harness/基准。这里只吸收“影响面验证＋最终留出验收”，不引入其自动进化框架，也不引用其提升数字作为本项目承诺。
- [Simple Testing Can Prevent Most Critical Failures](https://www.usenix.org/conference/osdi14/technical-sessions/presentation/yuan)（OSDI 2014）：错误处理和有限故障序列值得重点测试。对应派发、效果、观测、验证、提交几个关键中断窗；无需先建设大规模故障攻击平台。

### 5.3 社区交叉核对：只能作为线索

- [openai/codex issue #16872](https://github.com/openai/codex/issues/16872)：作者报告旧版 app-server 共享线程完成后 rollout 不可读/不可恢复。客户端、版本和通道不同，不能认定是本项目同一故障；它说明“完成事件存在”和“之后能恢复”需要分别验收。
- [LLMDevs：CLI 集成经验](https://www.reddit.com/r/LLMDevs/comments/1vx5b55/how_i_integrate_codex_and_claude_code_into_my_ai/)：作者列出全局指令/Skill/MCP 隐式上下文、启动和输出解析的集成负担。作为环境闭包检查的参考，不据此推断平台许可、故障发生率或 Foundry 根因。

综合判断：约束输入输出、权限和验收，放开模型在范围内的推理与实现，是可保留的方向。
但模型自主性不能弥补宿主丢事件；加强 Prompt 也不能代替进程生命周期与恢复工程。

## 6. 最小目标设计

### 6.1 三个层次分开，不增设第二控制器

```text
批准范围 / Requirement / Plan        SQLite 仍是唯一权威状态
                  │
       Codex / local 命令执行
                  │
      无损生命周期观测 ─── 有界人读日志
                  │             裁剪只影响展示
       独立 Case / 当前产物
                  │
       事务提交 → 依赖任务推进
                  ↑
       重启核对 / 部分检查续跑
```

- **事件与日志：** 分别处理 stdout JSONL、stderr 诊断和显示摘要；增量解码/解析，识别真正结束及失败。持久事件附件隶属命令，不成为自行批准的状态库。
- **资源有界：** 限制单事件大小、磁盘占用、时间和内存；限额必须按真实样例定值并有明确超限故障。机器证据限额不能冒充显示限额，不能无限缓存所有输出。
- **耐久顺序：** 记录派发意图、可确认的进程启动、阶段观测和终态；恢复读取可用证据。记录意图并不证明启动，PID 本身也不足以证明同一进程。覆盖相邻记录之间的崩溃窗口，不承诺任意外部副作用的 exactly-once。
- **环境统一：** 共享明确的解释器/工具绑定与必要只读资源；模型可自主选设计、拆代码、调试。保留适用父指令，解决角色冲突；不自动修改用户全局配置或安装系统工具。
- **公开诊断：** `read-build` 展示最后阶段、原始原因、效果确定程度、可用证据、下一步和是否需新权限。正常 `advance` 先核对再推进，不要求人工去查 SQLite。

### 6.2 恢复决策按效果确定程度，不一律重跑或一律永久挂起

| 可观察状态 | 拟采用动作 | 权限约束 |
| --- | --- | --- |
| 确认未派发，环境问题已修复 | 使用原任务及既有预算有界重试 | 当前批准有效且范围相同；不能清零预算 |
| 原进程仍在运行 | 等待/按既定策略取消，不重复派发 | 撤销、到期和进程管理规则继续生效 |
| 实施已完整观测，部分只读检查缺失 | 校验输入仍匹配，续跑缺失检查 | 不重做实施，不复用失效证据 |
| 全部检查完成但提交前崩溃 | 从已存在观测重核并事务提交 | 检查当前授权、产物及依赖；不能重复效果 |
| 只有当前本地产物，旧终态不可恢复 | 保留旧 UNKNOWN；依据预先定义的核对/接纳路径另记新决定，或明确允许后新尝试 | 不能伪造旧终态；若现批准不涵盖接纳/重试，才需一次具体决定 |
| 存在无法核对的外部/不可逆效果 | 真实停止并列明缺什么证据/选择 | 不自动重放，不以模型自述代替事实 |

来源/上游产物变化时，仅失效实际受影响的检查、任务与后继；保留历史。
这属于已有 W4B 范围，不建立新的全图 Hash 链或重跑全工程的默认规则。

## 7. 修复 Workpack 与集成顺序

下表是工程工作拆分，不是已批准执行的目标 Workpack。源工程进入执行后可在已有范围内连续推进，
不新增逐包人工 Review。可并行的是独立调查、夹具和不同文件实现；共享控制器/合同由单一集成顺序合入。

| 包 | 对应原计划 | 交付与关闭标准 | 前置/并行 |

| R3：耐久命令观测、恢复与失效 | W3/W4A/W4B | 关键中断窗、部分 Case 续跑、BLOCKED 重新核对、UNKNOWN 处置、依赖失效、readback 原因链全部可执行；无伪造旧成功 | R1/R2 接口就绪；`build_runtime/store/build_entrypoint` 串行集成 |
| R4：生产通道纵向验收 | W2/W3/W4/W7A | 无模型生产采集器矩阵 → 小型原生 Codex 探针 → M1 实施/独立检查/后继/目标使用；含真实拒绝后有界修复证据 | R1–R3；原生调用仅在具体有效范围和预算内，不拿夹具替代 |
| R5：通用发行与留出闭合 | W1A/W5B/W6/W7B/W7C | 保留核心能力；专项从公开通用链退役；同一包在干净接入环境做新建及既有工程案例；目标加载使用；缺陷账本闭合 | 资源盘点可提前；最终依赖 R4，发行测试不临场从开发目录补文件 |

优先级：先修 R0/R1/R2/R3，才能合理再试 M1；R5 的文档/依赖盘点现在即可设计，不能等最后才发现。
不要求先完成所有行业的需求 Oracle、所有平台或所有历史文件整理才运行小型原生探针。

## 8. 固定验收矩阵与有限 Review

### 8.1 必测的故障类别

| 类别 | 必须通过的正向情形 | 必须保留的失败/恢复判定 |
| --- | --- | --- |
| 事件体量与字符边界 | 超过显示上限的合法多事件及单事件、UTF-8 跨块、终态在尾部 | 真非法编码、残缺 JSON、缺终态不可当完成；达到真实资源上限可解释停止 |
| 双流与版本 | 大 stderr 不影响完整 stdout；受支持客户端事件样例 | 关键生命周期不兼容明确阻断；非关键新通知按合同处理，不盲目放行 |
| 环境 | 非系统 Python、工具路径、正常父级指令与资源 | 缺工具/指令/配置冲突在运行前定位，不在失败后放宽全局读域 |
| 授权与预算 | 同一有效范围内跨任务、修复、恢复不重复询问 | 越界、撤销、到期、预算耗尽不派发或提交；记录已发生观测不伪装成授权 |
| 命令中断窗 | 派发前、启动后、完成后、观测前后均能确定下一动作 | 活进程不重复派发；不可确定效果不重放；所有历史保留 |
| 检查与事务 | 多 Case 中途崩溃只续缺项；全部观测后提交恢复 | 当前产物不匹配时不复用；失败验收不发布前置能力 |
| 依赖与修复 | 两个依赖任务、独立拒绝、限定修复后推进 | 上游变化失效相关后继；无关工作不重做；框架错误不派给模型改业务 |
| PRD 与结果 | 完整来源可查，明确子流程功能/状态/异常均有外部 Case | 需求缺口或冲突须暴露，不自行发明产品要求；源码存在不算使用成功 |
| 包与接入 | 同一发行候选包仅凭公开资源完成接入、生成、运行、目标加载 | 缺文档/依赖、开发机隐含路径、专项默认路由即失败 |

每类使用最少能覆盖合同的代表样例；不做所有参数的笛卡尔积，也不把偶发假想攻击扩成当前目标。
先用确定性状态转换表与故障注入实现；确有收益时再选用状态式测试库，不增加生产依赖。
故障注入使用自有测试样例与测试控制库，不篡改当前 M1 产物或独立验收预期来制造“修复成功”。
真实模型的探针、修复与留出测试必须计入明确预算；该矩阵本身不授予额外模型调用或路径权限。

### 8.2 Review 的收敛规则

1. 实现前固定本轮故障类别及验收范围；每项缺陷必须有可达路径、复现/证据、所属层和正确预期。抽象担忧单列待验证，不默认阻塞。
2. 每次修改跑该影响面的正反例及依赖回归；集成与发行各跑要求的完整套件。不靠重复全套次数替代缺失的 Case。
3. 两个有明确目的的审查阶段：集成阶段检查上述合同；发行阶段从干净环境做不同业务/既有工程留出验收。不是反复让同一提示“再找一些问题”。
4. 留出案例一旦用于修复，不再称完全盲测；保留其回归，并对改动影响范围复验。新的独立样例只为验证具体泛化疑点，不无限换题。
5. 新发现若落在既有故障类别，回所属包一次闭合全类；若实质改变产品需求/支持平台/外部权限，登记为范围决策，不偷偷加到本次完成标准。
6. 自动修复有既定尝试/时间预算；同一症状再次出现且无新增证据，停止重复试跑，回到复现与假设核对。不通过重置 Program、清空 attempt 或换 epoch 续费。
7. 发布必需的原生/宿主测试不能以 SKIP 计 PASS；未执行明确写 NOT_RUN。最终结论分别报告静态、夹具进程、原生模型、目标行为与包级验收。

**本轮方案的退出标准：** R-F1 至 R-F6 全部有对照回归和生产路径证据；所承诺的关键中断与恢复场景通过；
同一发行候选在新建与既有工程两个明确案例完成建设和目标使用；既有核心能力没有回归；
验收范围内没有已知未闭合缺陷。此时停止本轮审查，不声称永远不会有未知问题。

## 9. 减少过度攻防、Hash 与人工步骤

- 保留原计划 H1/H2 的必要发行/输入或产物身份用途，按既有白名单落实；状态顺序用 revision，调用身份用已有 ID，验收用实际行为。
- 不添加每事件 SHA-256、递归摘要链、全工作区重复哈希、额外账本、外部认证或多轮模型投票。
- 不为正常 stdout/stderr 变长增加人工批准；不用 UNKNOWN 作为所有错误的永久终点，也不把 UNKNOWN 一律放宽成 PASS。
- 需求、验收与外部权限由明确边界控制；模型内部方案、编码和常规调试自由。文献所述 Astra 自主性落实在这里，而不是放弃宿主工程。
- 工程内部集成/校验/可逆修复不逐包找用户；只有新根目录、模型服务/预算、真实外部效果等授权扩展或实质需求选择才提具体问题。
- 当前方案不需要新的 Harness 框架、队列服务或 App Server 迁移；只有现有 CLI 通道经过修复仍不能满足已承诺持久交互时才另评估适配。
