## 1. 修复目标与明确不做

**目标：** 让通用 Foundry 在已批准范围内可靠完成“需求接入 → Coding Harness 建设 →
独立验证 → 有界修复 → 后继推进 → 中断恢复”，并用发行包的真实接入与目标使用证明可交付。

保留：Codex 载体、模型在范围内的实现自由、本地 Python 步骤、单一控制库、Requirement/Plan 分离、
独立 Case、实际人类范围批准及平台权限。修复的是整类运行缺陷，不是把测试预期放宽成成功。

本轮不做：恢复视频专项、换上游生成器、切换模型/API、迁移到 App Server、增加队列/第二数据库、
全量事件 Hash 链、全平台适配或任意行业 Oracle。历史兼容状态不重写；通用发行物的专项退役仍须完成。

“源码修好”“M1 通过”“发行包可用”“已经发布”是四个不同结论，禁止互相代替。

## 2. 当前基线与实施原则

制定本方案时，经公开 `read-build` 再次只读核对：

- M1 控制流仍为 revision 23，`writes_performed=false`，`harness_e2e_verified=false`。
- 三次历史启动失败保留；最新尝试是 `UNKNOWN_SIDE_EFFECT`，不因本方案自动重试。
- 先前 65 项局部测试通过及采集器复现见根因报告；本轮未重新运行这些测试，也未将其提升为 E2E。
- 工作树已有较多源码与文档修改。实施前记录实际差异，不重置工作树、不覆盖用户或前序工作。

工程规则：

1. 每项改动须对应 R-F1–R-F6 或上位 G1–G13 的具体未闭合义务；不顺便清理无关历史文件。
2. 先补能揭露错误假设的回归，再改生产实现；Producer、消费者、Validator 的对应关系一起核对。
3. 先确定最小接口和行为，再并行不同文件工作；共享控制器与状态归约逻辑串行集成。
4. 新发现先判断“同类缺陷、既有未完成能力、新范围”三种归属，不默认开启一轮全新大修。
5. 源码实施授权不等于目标运行授权。进入真实模型、目标加载和包级案例时，逐次核对实际有效范围，不沿用历史 Candidate 批准。

## 3. 关键设计决定

### D1：机器事件与展示日志分开

保留有界的人读 stdout/stderr 摘要，但不再从裁剪后的文本重建机器协议。

- 采集器持续排空两个输出流；stdin 大输入也不能阻塞输出消费。
- 协议以原始字节增量解码/逐行解析，保留跨块字符状态；禁止先 `decode(errors=replace)` 再 `encode` 送入权威协议判定。
- stdout 协议完整度与 stdout/stderr 展示裁剪分别记录。stderr 显示裁剪不改变已完整观测的模型终态。
- 完成必须同时满足合法生命周期、成功进程结束及无真实协议缺失；任务是否通过仍交给独立 Case。
- 展示上限可继续沿用现有 64 KiB；机器事件的单条/总存储限额另有明确值和超限原因，不能无限增长或静默丢尾部。
- 固定回归覆盖原 64 KiB 临界点、1 MiB 合法单事件和 8 MiB 多事件流。这些是测试样例，不是宣称平台支持上限。

拟定内部观测语义为：进程退出/超时、协议状态与原因、终态/线程信息、命令观测引用、两流展示裁剪情况。
实现可以沿用现有字段并明确语义；不为了这些概念建立一套新的跨模块 Schema 框架。

### D2：有限命令由宿主持久观测，不依赖模型自报

继续使用当前有限 `codex exec` 路径；这一轮不以切换后端作为修复手段。
保持 `--ephemeral` 时，由宿主保留恢复所需的协议与命令事实；不承诺恢复原模型的未持久化推理上下文。

- 使用现有 Program/attempt 和新增的必要 command 身份；同一命令的重复记录不重复执行。
- 同一控制库记录派发意图、可确认启动、完成观测和验收决定。原始流可放在命令归属的宿主私有附件中，不成为第二控制状态源。
- 附件位于目标写域之外；目标进程无权伪造。私有 PRD/日志不进入发行包。不为每条事件增加 SHA-256。
- 采集、附件刷新和控制事件写入有明确顺序；重启只承认可读、已完整落盘的事实，不把缓冲区数据当持久证据。
- 每条模型 item 不必增加控制库 revision；在必要生命周期点记录，原始流作为诊断与恢复输入。
- 无法跨越操作系统启动与 SQLite 提交的原子性空窗；测试必须证明该窗口被准确解释为待核对，而不是宣称 exactly-once。
- 进程组清理、超时和存储写失败产生独立原因；不按进程名字杀进程，不在记录失败后盲目再次派发。

### D3：恢复状态由事实与下一动作组成

`UNKNOWN_SIDE_EFFECT` 不直接改成 PASS；增加的是核对能力，不是放行例外。

| 情况 | 控制器动作 | 不允许的替代做法 |
| --- | --- | --- |
| 确认未派发，环境已恢复 | 当前授权有效时，按原预算新尝试 | 每次失败清零计数 |
| 原命令仍运行 | 观察/等待，或执行既定取消策略 | 同时重派第二份 |
| 实施已完成观测、部分检查未运行 | 校验产物与依赖，续跑缺失或明确可重试的只读检查 | 重新实施整个任务 |
| 检查完成、尚未提交 | 重核当前授权与输入后事务提交 | 重跑命令制造第二次效果 |
| 旧终态丢失，只剩本地产物 | 保留旧未知；依据核对事实与适用权限，记录新的处置决定 | 伪造旧完成事件或将文件存在当验收 |
| 无法确定的外部或不可逆效果 | 停止并说明缺少的证据/用户决定 | 默认重试或默认接受 |

已验收输入发生变化，按声明依赖失效真正受影响的任务及检查；不删除历史、不清空预算、不默认重跑无关分支。
“输入变了”与“需求变了”分开：需求/验收边界变化仍需用户决定，不能作为内部修复自行改写。

### D4：失败必须路由到正确层

| 失败来源 | 处理责任 |
| --- | --- |
| 来源缺失、语义冲突、用户目标不明确 | 接入层给出带来源的具体问题，不自行编造产品需求 |
| 工具缺失、原生客户端不兼容、采集/存储错误 | Foundry 接收器/宿主工程；不让目标模型重写业务来“修复” |
| 独立检查没有实际运行、检查器崩溃 | 独立验证路径；不能当成业务断言不通过 |
| 检查器正常运行且业务行为不符合 | 将可解释的 Case 反馈交给目标 Codex，在原范围/预算内修复 |
| 效果不明、来源/依赖变化、授权失效 | 先核对或停止，不进入普通业务重试 |

检查器需区分“正常执行的业务 PASS/FAIL”和“检查基础设施失败”；退出码加结构化结果/固定测试断言即可实现最小区分。
任何结构化 PASS 仍须来自独立实际执行及对应产物，不能只让实现侧写一个结果 JSON。

### D5：工具与指令显式绑定，实施方法不锁死

- 从现有 `scope.executables` 和读取范围派生模型可见的工具信息，优先使用已绑定绝对解释器/程序路径；不另建一份独立权限清单。
- 若需要 PATH，必须在生产原生通道证明子命令真正收到预期环境；仅改父进程环境或 prompt 不算通过。
- 不通过开放用户主目录、忽略父级 AGENTS、自动安装系统工具解决问题。全局指令和必需 Skill/引用资源应可读且角色清楚。
- 新目标使用清楚的目标角色指令；不把 Factory 的 authoring 工作步骤误当成目标 coding 工作步骤。现有 M1 不擅自迁移路径。
- 需求、输出、独立验收与资源边界固定；模型自行选择类、函数、算法和普通调试步骤。
- 先支持当前经过实测的宿主/原生客户端组合；其他平台标记未验，不为了通用性声称全平台可用。

## 5. 各包执行卡

### R0 — 建立能推翻错误假设的最小回归

**动作：** 将现有无模型采集复现迁入正式测试；把“截断即未知”拆成展示裁剪与机器证据缺失；
列明启动、观测、验证、提交关键故障窗和预期下一动作。核对每项 G1–G13 尚未完成的归属。

**产出：** 测试名称、输入、预期、生产消费点和对应 F 项的简短清单，放入现有测试/Tracker。
不复制大型来源，不重新冻结业务 Requirement，不为测试集增加审批 token。

**验收：** 合法长输出及 stderr 复现能在旧实现暴露失败；真残缺输出仍不被验收；
另有小输出成功对照。旧的 65 项局部绿灯明确只代表其原覆盖，不覆盖本轮新增义务。

### R1 — 一次闭合采集这一类问题

**动作：** 实现双流排空、增量解析、展示裁剪分离；消除裁剪后重新编码的权威输入；
给 R3 暴露最小的宿主观测回调/引用接口。普通 LOCAL 命令及 CLI capability probe 也须回归。

**测试：** `test_local_process`、`test_coding_protocol`、`test_coding_process`，使用真正的本地子进程夹具。
覆盖 UTF-8 跨块、有效大单事件/多事件、stderr 独自超显示限额、终态在尾部、无终态、真非法数据、
超时、采集器写失败、受支持版本协议样例。版本未知不伪造兼容；非关键通知兼容须有明确依据。

**关闭：** 正常长流与小流的生命周期判定一致；日志裁剪不改变协议结论；缺失证据和真实失败仍不能完成。
读写与内存不随日志总量无界增长。不是把 64 KiB 改成更大常量便关闭。

### R2 — 工具、指令和接入资源一致

**动作：** 将已有程序绑定传给模型任务上下文，统一 LOCAL/Verifier 解释器；检查实际子命令环境；
给出缺工具/必需指令资源/配置冲突的准确诊断。补齐包中的 Build CLI、Runtime、Source intake 等真实引用资源。

**测试：** `test_coding_process`、`test_build_entrypoint`、`test_build_runtime`、`test_portable_local_cli`。
使用非系统 Python、缺失工具、正常父级指令、缺失引用资源、带空格路径及干净接入目录等代表情形。
不得为通过测试自动修改真实用户全局配置；指令资源不包括客户端凭据读取。

**关闭：** 工具与依赖真实可用，错误发生在可解释的层；发行资源引用可达。
本包只关闭接入基础，不因此宣称专项已退役或发行包 E2E 已完成。

### R3 — 控制链的耐久观测与有限恢复

**动作 A：** 接 R1 的命令观测，记录必要阶段并保留宿主附件；受控追加事件使用同一 revision 库。
记录已经发生的效果与授予新权限分离：撤销/过期后仍可保留观测，但不能继续派发或成功提交。

**动作 B：** 实现 D3 恢复归约及 D4 失败路由；部分检查续跑、输入变化失效、原预算累计、
原进程核对和当前 M1 这类旧 UNKNOWN 的处置均有明确路径。
`read-build` 增加原始原因、最后阶段、证据引用、可执行下一动作和是否需新决定。
正常 `advance-build` 先核对再推进；只在现有入口确实无法表达真实处置决定时增加最小入口，
不得为每个检查点增加一条需要人工操作的 CLI。

**测试：** `test_build_runtime`、`test_build_entrypoint`、`test_revision_control_store`。
最小序列覆盖：派发前；启动记录前后；实施完成但观测未提交；检查只完成一部分；
全部检查完成未验收；已验收但派生视图丢失。另测撤销/到期、原进程存活、已退出但证据不足、
Verifier 运行故障、业务检查失败、上游变化只失效相关后继。

**关闭：** 每个故障窗要么有证据地继续、要么等待活进程、要么给出真正需要外部决定的具体原因；
不制造成功，不重复已确认效果，不把可恢复状态永久留在无解释 HELD。
共享原子性窗口无法确定时可以停止，不能为了“全部自动化”假装不存在。

### R4 — 先真实小通道，再处理现有 M1

**顺序：** 无模型生产采集器/控制器矩阵 → 小型原生 Codex 联通 → 当前 M1 核对与有界后续。
小型探针要求读取声明来源、产生实际文件、独立检查和 LOCAL 后继，不能仅运行 `--help` 或 `/usr/bin/true`。

**现有 M1：**

1. 先通过公开读接口查看当时的授权、预算、原进程和产物；不能沿用本文中“当时有效”的快照。
2. 旧协议尾部不可恢复时，保留旧 UNKNOWN。新核对/验收说明的是当前产物，不补造旧模型终态。
3. 对当前产物重新独立核对或新尝试，必须由已实现的合法处置路径接入；若现范围未覆盖，集中说明实际增量后取得一次决定。
4. 真正执行独立业务 Case、后继任务及目标使用，结果回归原来源的 M1 子流程，不降低预期。

**测试与预算：** 故障注入使用自有测试样例/控制库，不污染当前 M1。模型调用、新根目录和预算需要具体有效 scope，
可一次展示一组必要探针/案例范围，不按每个内部 Workpack 反复问用户。未覆盖的运行等待时，继续其他可做的源工程。

**关闭：** 有真实原生实现、独立拒绝与范围内修复、后继消费、目标使用和恢复证据。
仍只关闭 M1/相应运行义务，不宣称原完整 PRD 已全部实现。

### R5 — 同一发行包证明通用性

**准备：** 复用 W1A/W5B/W6/W7 的剩余工作，明确核心能力保留、专项源码/引用退出通用发行物、
仅 H1/H2 必要 Hash、公开依赖/许可、支持宿主、快速开始及恢复说明。不能把专项改名藏入 Core。

**拟定两类发行验收：**

- A：完整但规模小的非视频 CLI PRD，例如本地任务清单的创建、状态修改、查询和持久化。要求 Foundry 生成可用 Coding Harness，
  随后在新 Codex 会话加载该 Harness 完成真实任务，并独立验收最终行为。
- B：既有数据处理工具的增量需求，例如新增 CSV 分隔符选项，同时保持原功能和预先存在的无关修改。
  使用同一个 Foundry 发行候选，不能加入按案例名分支的生产逻辑。

这些是推荐的独立样例，不替换已批准的私人 PRD/M1。运行前明确实际来源、完整 Case 和范围；
M1 仅是联通材料，不把它的子范围冒充完整 PRD 验收。

**关闭：** 在可声明的干净接入环境，只凭同一包、公开说明及合法用户 Codex 登录完成 A/B；
无需原开发工作区、作者凭据或现场补文件。真正加载并使用所建 Harness，不能只直接调用 Codex 生成业务源码后改名为 Harness。
原通用核心/生成/启动能力回归通过，G1–G13 在既定范围内都有对应证据。
自动化独立接入验证不表述为真实第三方用户试用，准备发行候选不等于已发布。

## 6. 验收命令、失败回路与有限停止条件

### 6.1 测试顺序

实施中先跑相应包的聚焦测试；实现修改后按仓库要求运行完整套件，工作流修改同时验证规范与 Skill。
使用项目已配置的解释器/依赖环境，不为了执行命令自动安装软件或替换系统 Python。

```sh
PYTHONPATH=src python3 -m unittest discover -s tests -p 'test_*.py' -v
python3 tools/hffactory.py verify-spec --json
python3 tools/validate_skill.py
```

核心保留由现有 `validate-core` 等入口验收；包级接入与原生模型另有实际结果。
执行日志和当前结果记录于现有 Tracker；本次源码修复没有修改 Skill/AGENTS。
未来改 Skill/AGENTS 时依对应技能和规范实施。

### 6.2 修复回路

```text
具体复现 → 归属已有 F 项/能力 → 改生产边界 → 配对回归 → 受影响链路验证
                                       │
                  无新证据地同样失败 ───┘ 停止盲目试跑，重新核对假设
```

- 每个缺陷记录最少信息：复现、实际/预期、责任层、改动、验收结果、剩余不确定性。
- 测试应证明“不再错误拒绝正常任务”以及“不错误接受失败任务”，不是只有拒绝越来越严。
- 反复看到同一症状但没有新证据时，不消耗下一次真实模型重跑；先在可控夹具定位故障窗。
- 两个审查阶段：R3 集成审查；R5 同包独立场景审查。新缺陷只回到责任包及影响面，不重新扫描所有历史材料来制造下一轮任务。
- 对当前承诺范围内的真实缺陷，必须修复或明确报告阻塞，不能用“已达到轮数”强制接受；对新增目标不悄悄扩大验收范围。
- 留出案例用于修复后即转为回归案例，不再称完全盲测；新样例仅用于核实具体未解决的泛化疑点。

### 6.3 完成条件

源码修复完成：R-F1–R-F6 对应生产改动与回归闭合，关键中断序列可解释、可恢复，完整必要回归通过。
真实运行完成：R4 对应的模型实施、独立 Case、修复、后继和目标使用实际发生；非全 PRD 结论。
可发布完成：同一发行候选的 R5 两类案例及 G1–G13 承诺满足，验收范围无已知未闭合缺陷。

必需测试的 SKIP/NOT_RUN 不能计 PASS；旧版本的成功不能代替受改动影响的当前版本证据。
达成上述边界后停止本轮修复，不继续无限找题；后续缺陷走同一可复现、归属、回归机制。

## 7. 权限、迁移与回退

- 本文仅制定方案。进入实施后，范围内源码/测试/文档和可逆集成可连续进行，不新增每包 Human Gate。
- 真正需要用户的只有需求选择、具体运行授权扩展/到期、无法核对效果的处置，以及尚未授权的推送/发布等外部动作。
- 新事件优先使用现有 `REVISION_V1` 的事件载荷；不为几个字段新增表或数据库。必要的格式改动须有真实理由和定向读取测试。
- 旧 attempt、批准、源码来源与不可变 Candidate 保留。旧事件缺少的新证据记为不可用，不合成新协议字段来假装历史已满足。
- 本地自动续跑不凭新 prepared event 或 Program 隐式抹去此前预算；追加预算只能来自明确的新决定。
- 回退以停止派发、保留现场和回退尚未运行的代码/候选为主。已经写入新语义运行事件后，不把旧执行器直接接回同一活跃库；先由支持该状态的实现核对。
- 如果修复需要新读域、模型或安装依赖，先完成不依赖这些变化的工作，再一次性列出最小增量；不得绕过平台限制。

## 8. 实施入口

收到实施指令后，从 R0 的现有复现入正式测试开始，接着推进 R1/R2 的独立部分，再串行集成 R3。
R4 前只做真实范围核对，不自动继承旧启动批准；R5 准备可提前，实际运行按其具体范围推进。
本方案不要求再次 REOPEN/Freeze 视频 Candidate，也不要求用户手工复制 Hash。
