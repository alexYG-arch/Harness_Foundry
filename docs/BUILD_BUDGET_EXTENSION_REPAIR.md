# 累计预算增额补修

状态：基于1.2.0的修复已由7660c97提交main，并纳入1.2.1发布范围。发布包与下载核对见[1.2.1说明](releases/v1.2.1.md)；不代表其他设备已升级。协议仍为2.9。

## 问题与维护归属

原同 Program 接续强制两项预算上限相等，能够保留原消耗，却不能表达真实批准后的
“已用6次，再加1次，总上限7”。这属于通用授权接口缺口；反复确认、改成无关联的准备、
新建 Program 或修改数据库都不能修复累计关系。其他项目的业务、检查器及说明文档问题
仍留在原维护位置，本次不合入项目专用实现，也不操作其数据库或第7轮业务。

## 实现与使用

复用现有 prepare、approve、rebind、advance 和 read-build。
准备请求的可选 `budget_extension` 声明两项准确增量与原因；完整 scope 保留新绝对上限。
准备只存声明，真实人类批准经原入口提交时记录新旧关系；同范围自动修正不能批准增额。
旧事件、唯一 attempt 身份、原只复验计费规则和恢复路径不变。普通不增额接续保持旧校验。

来源、Plan、版本、读写权限、服务、有效期、撤销、未知效果和并发 revision 检查继续使用
原机制。增额不是新调度器，也不为每个内部步骤增加确认。相同请求幂等取回不再加额，
已经完整捕获的命令不因增额重放，符合原条件的 accepted 可复用。

完整参数、读取方式和多任务上限边界见
[公开CLI说明](GENERIC_BUILD_CLI.md#保留累计消耗的显式增额)。
维护入口为 `build_rebind.py`、`build_runtime.py`、`build_entrypoint.py` 和 `build_display.py`；
`test_build_budget_extension.py` 进入现有公开源码检查集合。没有修改生产调度或预算投影算法。
