## 1. 目标与完成定义

完善并发布供其他用户接入其自身 Codex 使用的通用 Foundry：保留和验证现有通用生成、启动及核心能力，所有 Harness 需求先形成经人工 Review 的搭建文档，再作为正式建设输入；Coding Harness 场景包含基于完整 PRD／项目说明和开发需求生成的开发内容。补齐授权范围内的 Workpack 自主执行、独立验证、推进和恢复。以实际发布包、非作者使用环境和代表性工程证明：用户无需原作者代操作或补私有文件，即可建出符合明确需求、完整可用、验收范围内无已知未解决缺陷的 Harness。后续工程使用同样的验收与缺陷闭合机制。

Foundry 和目标 Harness 都以 Codex 为载体，由 Agent 主导任务理解、规划和实施。GPT-6 Astra 是本轮主要验证模型；本地 Python 等程序承担适合确定性执行的处理、校验和状态操作。不要求每个 Stage 调用模型，不要求每个 Harness 启动独立服务，也不为普通局部步骤强制创建子 Agent。

交付必须同时满足四个层次，不能互相替代：

1. Foundry 核心及生成、启动能力保持正确。
2. Foundry 可以在明确授权内真实构建、验证、修复并交付目标 Harness。
3. 目标 Harness 按正式使用方式加载后，能由 Codex Agent 完成约定任务，实际输出通过验收。
4. 他人仅依靠发行物、公开文档、自己的 Codex 和声明依赖，可以完成接入与真实搭建；必须用独立接入环境复现，作者原工作区成功不能替代此层。

“完整可用”限定于公开支持的输入、宿主、依赖与验收范围；不承诺消除所有未知缺陷。范围内已知缺陷必须关闭，不能降级、隐藏或临时删掉验收要求以获得发布 PASS。

### 1.1 范围与非目标

- 用户补充确认：通用 Foundry 必须剔除已有专项，不限于视频。从生产路径、合同、指令和发布包中移除项目专属实现，不以“默认关闭”或改成可选插件作为剔除完成。视频、TTS、Motion、FFprobe、图片效果、公共 Skill 转视频均在剔除范围；本轮不继续 Skill Video Harness 工程。
- 保留上述工程暴露出的通用能力：需求追踪、任务依赖、Job 归属与读写边界、产物身份、真实执行观测、独立验收、失效传播与恢复。
- 历史 Candidate、Program、授权、来源快照和旧证据保持原样。通用化不意味着重新批准旧项目，也不要求继续支持已移出范围的视频运行时。
- 不建设多租户平台、跨组织认证网络、分布式调度集群或通用插件市场；不以全量攻防、重复 Hash 或更多仪式性文件作为完成信号。
- 不重写 Codex 已提供的工具循环、上下文管理和交互能力。新增组件必须对应现有闭环的具体缺口。

### 1.2 专项剔除清单与边界

| 剔除对象 | 处理方式 | 必须保留的通用能力 |
|---|---|---|
| 视频/TTS/Motion/Render/Demo 等专项产物、算子、阈值和阶段 | 从生产器、Validator、Schema、Prompt、默认配置与发行清单一并移除 | 可声明的产物、关系约束、实际运行观测与验收 |
| 公共 Skill URL、指定 GitHub 仓库、特定 Skill 名称和入口作为必选业务 | 删除固定注入及专用运行接口；不在本轮建设另一个 Skill 解释器产品 | 来源读取、来源归属、依赖与用户声明的输入合同 |
| 旧目标 ID、私有字段、历史 epoch 数值触发生产行为 | 移除专项分支，以显式通用能力/合同版本决定行为；历史状态不重写 | 版本识别、合法迁移、需求与运行隔离 |
| 固定视频 12 阶段，以及硬编码项目/Workpack/Job 名称 | 阶段与任务来自当前需求和生成结果，不由某个历史案例决定 | 依赖图、任务归属、失败返回和恢复 |
| 固定 Lab/Linkage/Main 三工程或专项认证作为所有项目的前置 | 取消强制项目形态及具体义务 ID 的绑定；按真实需求设置验证边界 | 实施与验收职责分离、控制器提交、真实产物关联 |
| 旧专项说明、测试材料和回执混入通用发布包 | 历史资料仅用于非运行档案；将有通用价值的失败形态改写为领域无关回归 | 缺陷来源与回归追踪；不丢失通用错误的检测能力 |

W1 应形成逐项删除/通用化/归档处置，不只搜索删除关键词。验收同时检查源代码依赖、生成结果与发行包：普通新需求不能触发专项入口；包中不能残留可被调用的专项实现。专项回归分为“转为通用反例”与“随专项退役”，说明依据，禁止借清理专项删除仍适用的核心/行为测试。

“通用”也不等于建立无限可扩展框架。主工程和留出工程的业务代码与测试留在各自目标工程，不反向写入 Foundry 核心；以后新项目通过需求、任务合同和本地实现接入。

## 3. 目标架构：稳定边界，可调整实施

| 责任层 | 应负责 | 不应负责 |
|---|---|---|
| Codex 宿主 | Agent 会话、工具执行载体、平台权限、宿主已有的上下文与交互能力 | 为 Foundry 自动认可产品验收 |
| Astra Agent | 需求理解、必要澄清、架构与代码设计、局部规划、实现、调试、范围内修复 | 扩大授权、改写用户目标、删减验收或自行宣布权威 PASS |
| Foundry 通用控制 | 工程身份、范围、依赖、允许的操作、执行观测、验收提交、预算与恢复 | 固定每一步推理或为每个工具动作另建一套编排 |
| 本地处理/验证组件 | 确定性解析、转换、计算、检查和真实结果观测 | 以模型生成的回执替代实际运行 |
| 目标 Harness | 业务规则、阶段合同、Agent 指令、所需本地模块及验收入口 | 依赖开发机私有路径或反向要求修改 Foundry 核心 |

### 3.1 宪章和合同保留到什么程度

使用精简且可执行的宪章：目标、非目标、输入输出、重要约束、权限、完成条件、失败与恢复原则。可机器检查的规则绑定真实执行/验收点；语义规则保留可观察的验收方式。不能把无法形式化的业务判断伪装成 Schema 或 Hash 检查，也不把每条普通建议升级为强制 Gate。

复用现有 Requirement、Architecture、Parent、Workpack、Job、Artifact 与事件存储模型，仅补齐闭环必要字段。实施前明确以下最小边界，不新建并行权威库：

- 用户需求和验收义务：决定必须完成什么。
- 建设授权：决定在哪里、用什么权限和预算执行哪些类别的操作。
- 可修订实施计划：决定当前如何完成；记录版本、依赖和变更理由。
- Stage/Workpack 合同：输入、产出、前置依赖、完成条件与失败返回。
- 验收记录：绑定真实执行、被验产物、判定和有效性；由控制器提交。

### 3.2 两种变更不能混为一谈

**可自主调整：** 内部模块、代码结构、算法、局部工具调用顺序、修复方法，以及不改变外部合同的任务拆分/合并/重排。Astra 提议后由控制器检查依赖和授权，接受的计划修订进入现有事件流。

**需要用户决定：** 目标或输出承诺变化、验收标准弱化、数据外发范围扩大、预算上限突破、覆盖真实用户数据等。模型不能将这些变更包装成“实现细节”。

业务承诺中的固定 Stage 仍是合同；它内部的实施步骤不是固定 Stage。已验收前置能力若因修改失效，相关后继等待复验；不能以动态计划为由绕过依赖。实现代码变化不自动触发全项目重新冻结或申请新 output root。

## 4. 需求澄清：不擅自补产品目标，也不追问实现细节

将需求信息区分为用户确认事实、来源可核对事实、显式假设、Agent 实施选择和未决问题。标记是信息来源说明，不要求为每个句子生成单独回执。

进入建设前，至少能回答：服务谁、解决什么、输入输出是什么、允许哪些工具/数据处理、怎样判定成功，以及何时必须停止。对影响结果的缺口，先查现有资料，再问最多三个最高价值问题；允许同时推进与缺口无关的已授权工作。

| 情况 | 处理 |
|---|---|
| “文档 Harness”但未说明检索、整理还是审批 | 给出具体差异并澄清，不能直接选业务目标 |
| 字段齐全但“质量好”等验收不可判定 | 提议可观察的例子/指标，待用户确认，不将空泛描述视为闭合 |
| 已明确本地文档检索、出处和禁止编造 | 索引方式、模块拆分等交给 Agent 自主决定 |
| 可逆且不影响范围的小细节 | 使用合理默认值；有交付影响的假设在简短 Readback 中说明 |
| 建设中发现新的关键冲突 | 停止依赖该决策的路径，保留已完成工作，不偷偷扩大范围 |

上游澄清结果写入搭建文档；不能只留在聊天里或未展示的内部状态。问答关闭、资料完整或
后台 PASS 后仍须交付实际文档，停在用户 Review；确认后才进入 Foundry 的 Requirement
状态。问题关闭必须有用户答案、来源证据或合法的实施决策依据，不能把 `OPEN` 改为
`RESOLVED` 就算闭合。回归应覆盖“资料可自行回答”“确实需要用户”“合理默认无需追问”
“用户修正旧假设”，以及四类均不能跳过文档展示与实际确认。

### 4.1 首要场景：PRD＋开发需求 → 搭建文档（含开发内容）→ 人工 Review → Foundry → Coding Harness

场景适配通过输入理解和生成的项目合同实现，不向核心写入某个产品、框架或应用模板的特判。Foundry 可以围绕明确需求自主设计 Coding Harness，但不能把“生成了应用代码”与“建好了可重复使用的 Coding Harness”混为一谈。

**上游准备：** 完整 PRD 或项目说明，加上开发需求、现有代码/平台/技术限制，先形成开发文档和未决项；经用户对实际版本和范围人工 Review 后才进入 Foundry。不得只把 PRD 改名，也不得由 Agent 自批。

**Foundry 正式输入：** 已 Review 的开发文档及其确认绑定；完整 PRD、现有仓库、接口与测试作为明确声明的追溯/约束材料。不能解析、缺失附件或只有截断摘要时报告缺口，不猜测缺页。来源冲突返回上游修订，内容变化不能沿用旧 Review。

**适配过程：** 从已确认开发文档形成目标、功能、状态、数据、接口、非功能要求与验收合同，保留文档及原 PRD 定位；识别新建或改造工程，生成上下文入口、开发/验证任务、工具边界、依赖与恢复规则。材料不是覆盖权限的指令。PRD 更新先进入上游文档影响分析和必要人工 Review，不把原 PRD 变化直接当成建设授权。

**交付：** 可由 Codex 实际加载使用的 Coding Harness，包含必要的工程指引/配置、本地执行与验证入口、任务及输入输出合同、恢复和使用说明。按需形成文件，不强制固定目录数量或大套模板。不能只交付规划文档、AGENTS.md、测试空壳或一个未经使用的生成器。

**成功标准：** 在目标 Coding Harness 下，由 Codex 根据验收样例的 PRD／项目说明执行真实开发任务，运行应用或命令、通过需求关联测试，处理一次缺陷或增量变更，并在续跑时保留已完成状态。既有项目场景还须保留原功能与不相关用户改动。所声明验收任务的全部范围必须完成，不能只交付脚手架。

首发至少覆盖完整 PRD 驱动的新建工程和项目说明驱动的既有工程适配。其他业务 Harness 仍走通用合同；此场景不把 Foundry 缩成某个行业的代码生成器。

## 5. Astra 与授权更新

### 5.1 指令与执行方式

审查 `AGENTS.md`、Foundry Skill、任务 Prompt 和生成给目标 Harness 的指令，删除重复、相互矛盾、要求逐步许可或把第一次实现当终点的条款。Skill 采用简短入口和按需加载；业务约束、工程操作建议、历史说明明确分开。

完成条件写为“实现、运行、观察结果、修复失败、验收并交付”，不是“输出实现方案”或“第一轮代码写完”。记录必要决策理由、假设、改动与证据，不要求记录模型内部思维链。

优先复用现有 Codex CLI 接口，先解决真实调用、观测与接续问题。只有它无法满足已确认的会话/事件需求时，再针对性评估 SDK 或 App Server；不同时建设多种宿主实现。明确绑定实际使用的 `gpt-6-astra`、CLI 版本与有效权限配置，不以 `model=null` 声称已验证 Astra，不静默回退到其他模型。

本轮不要求迁往裸 Responses API。异步工具、运行中指令更新等 API 功能不能推断为当前 Codex 接口已具备；仅在宿主确认支持且有实际需要时纳入。并行 Agent 不是默认必需；用户/工程授权允许且任务可独立时才启用，避免通过并行放大写域或成本。

### 5.2 连续建设授权，保留真实决策点

建议扩展现有 Parent 机制，让一次可读的建设授权覆盖明确范围内的生成、启动、模型服务调用、实施、本地验证、修复、接续及隔离安装验收。机器为具体 attempt 派生更窄的作用域；不要求用户手输 Hash、逐节点回复“继续”或重复批准同一风险。

这是一项待实现协议变化：现有预构建委托、离线 Parent 和编码 Parent 不会因本文而自动合并、扩权或获得新权限。继续保留单独的只读检查、仅 Authoring 和显式完整 Build 使用方式；正常启动 Foundry 不应自行创建目标工程。

授权至少说明目标和根目录、读写与网络/凭据范围、模型服务流量、可执行操作、时间/调用/修复预算、停止条件及有效期。模型服务联网与本地命令联网分别说明；“本地 Harness”不等于发送给 Codex 服务的任务内容完全不出机。代表性验收使用可公开的合成材料，不读取私有业务数据。

预算必须区分可强制执行的限制和仅可观测的统计。当前调用/时间限制不等于模型 token 或账单硬上限；宿主不能执行的预算保证不得写成已实现能力。需要硬上限时，先确认可用的宿主/服务机制再开始对应运行。

| 情况 | 授权内应自动处理 | 何时返回用户 |
|---|---|---|
| 范围内实现、测试、修复、复验、接续 | 连续推进 | 需要更改目标/验收或突破预算 |
| 临时错误或已知可恢复中断 | 有限重试、读取现有结果、恢复 | 副作用不能核实或原授权失效 |
| 隔离目录安装和验收 | 已包含于建设授权时连续执行 | 新增系统级安装、付费依赖或外发 |
| 目标实现文件变化 | 更新实际输入与受影响证据，重新验收 | 改变控制器/验收信任逻辑或授权范围 |
| 发布、推送、覆盖或删除真实资产 | 只准备可审阅结果 | 需要对应明确授权；不得沿用历史模糊批准 |

审批次数按实际风险变化解释，不机械要求每次工程恰好发生固定次数。超预算不能被“自动恢复”重置；授权撤销后阻止新派发，并准确报告已运行进程是否已终止、是否仍有副作用。

### 6.1 顺序和可并行范围

W0 先确定边界。W1A 专项剔除与 W5B Hash 最小化共用 Producer/Validator，按 W1A → W5B 串行合入；调查、测试设计可并行。通用接口可用后，W1B 需求适配、W5A 指令/授权、W2 执行器、W3 验收器按文件归属并行；W6 依赖盘点和 W7 用例准备可提前。共享 `control_kernel.py`、`cli.py`、`service.py`、Schema 和生成器由集成负责人串行整合，不能各建状态机。没有并行 Agent 授权时按相同依赖顺序单 Agent 完成。

**尽早纵向联通：** 在 W1/W2/W3/W5 的最小可用切片完成后，先做一个非视频工程的真实闭环：需求 → 生成 → Codex 实施 → 本地处理 → 独立验收 → 后继任务 → 失败修复 → 再验收。此时即可暴露宿主、授权和接口问题，不等待全部抽象层“完成”后才首次调用真实模型。该执行需要实际建设授权，计划本身不构成授权。

最小链路成功后，补完适用需求和 W4 恢复场景，再由 W6/W7 进行包级验收。W3 不得止于某一个 Lab 协议或三个固定义务，也不为通用化去实现一个覆盖所有行业的万能 Oracle；按项目合同绑定必要的可执行验证器。

### 6.2 W3/W4 的关键事务边界

1. 任务实施与目标写域不包含权威验收状态；Verifier 和预期结果不可被被验任务改写。
2. 现有控制器保留实际 attempt、过程观测及产物关联；Verifier 消费当前输入与结果，不接受任务自写 PASS。
3. 全部适用义务满足后，在现有 SQLite 事务中提交验收和产生的能力。验收不能成为依赖自身结果的任务命令。
4. 报告/回执文件从已提交状态投影；写文件失败可以重建，不重新执行任务。诊断临时副本不成为权威状态。
5. 修复使用新 attempt，保留失败原因与历史结果；仅失效受影响依赖。较新的失败、待完成或过期证据不能被旧 PASS 掩盖。
6. 区分“结果已观测未提交”“尚在运行”“已退出但观测缺失”“已提交但视图缺失”。先核实，后恢复；未知外部副作用不承诺 exactly-once，也不自动重放。

## 7. 回归、反漂移和比例适当的检查

### 7.1 覆盖表：每个目标要有真正的反例

| 目标 | 正向验收 | 必要反例/恢复 | 责任 |
|---|---|---|---|
| G1 保留核心/生成/启动 | 现有入口与普通通用输入仍正确 | 错误依赖/不支持的旧合同明确拒绝，不伪迁移 | W0/W1/W6 |
| G2 专项已剔除且无领域耦合 | §1.2 逐项处置；源代码和包中无专项生产入口；两个工程均不修改核心 | 去掉所有专项字段仍可建设；新业务不会重新硬编码进核心；不能靠空壳绕过行为义务 | W1/W6/W7 |
| G3 需求不漂移 | 问对关键问题并采用资料事实/合理默认 | 模糊目标、矛盾来源、未授权假设不能自动变成需求 | W1/W5 |
| G4 Codex 真实实施 | 模型事件和实际产物均可观察 | 模型自报完成但缺少功能时验收失败 | W2/W3 |

| G7 自主接续与修复 | 前置通过后推进，失败修复后重验 | 前置失败不推进；超预算不无限重试 | W4/W5 |
| G8 中断恢复 | 已完成工作复用，缺失视图重建 | 观测/提交前后中断不重复产生受保护效果 | W4 |
| G9 权限正确且不冗余 | 同一围栏内跨阶段连续工作 | 权限扩大、撤销、过期和未知副作用得到正确处置 | W5 |
| G10 包级交付 | 实际 Foundry 包建出可正式加载的 Harness | 缺少隐含开发机依赖时报告真实缺口，不能偷偷回原仓库取文件 | W6/W7 |
| G11 PRD／项目说明适配 | 新建与既有项目产生 Coding Harness，并实际完成约定开发任务 | 遗漏需求、只生成脚手架、破坏原功能或把缺失文档当已读不能通过 | W1/W2/W3/W7 |
| G12 最小 Hash | 生产 Hash 均属 §7.3 两类白名单，有实际消费者；普通流程无需人工 Hash | 重复摘要、回执套摘要、全树反复扫描、Hash 当业务 PASS 都不能通过 | W5/W6 |
| G13 他人 Codex 可用 | 干净独立用户环境凭发行物和文档完成 Codex 接入、构建、使用及验收 | 需要作者专属账户状态、原聊天、私有路径或临场改源码才能运行不能通过 | W6/W7 |

同时检查核心、生成器、独立 Validator 和真实运行路径，不能只改 Validator 或只修改 Fixture 让断言通过。模型辅助 Review 可以发现语义问题，但不能独自替代可观察的功能证据；同一 Chat 不声称外部独立认证。

### 7.2 Review/修复循环

每个发现保留最小记录：受影响需求、复现输入、实际/预期、根因所在层、修复、回归、影响的验收证据及当前状态。使用一个缺陷账本，不再复制多份相互竞争的状态。

循环为：复现 → 定位 Producer/控制/执行/验收根因 → 修复生产路径 → 加相关回归 → 复验受影响项 → 更新闭合状态。独立复核通过公共入口和真实输出检查，而不是照着实现复述 PASS 条件。

完成约定覆盖、必要回归及留出工程后，没有新改动、失败或具体疑点就不重复进行泛化“再找一轮问题”。新发现仍要记录并闭合；循环不以“永远找不到任何新问题”为终点，也不以审查轮数或测试总数作质量证明。

### 7.3 Hash 仅保留基本用途，禁止滥用

这是用户明确要求，不是可选优化。新通用生产链默认不用 Hash；优先用数据库事务/修订号、稳定 ID、引用关系、明确版本和幂等键处理状态、授权与任务关系。Hash 不承担内容质量、业务正确性、人工同意或可信执行证明。

此限制针对 Foundry 自建的 Hash 校验与流程合同，不删除 Git、包管理器、TLS 或 Codex 自身必需的底层机制，也不为这些机制再叠加重复校验层。

仅保留两类基本用途：

| 白名单 | 允许用途 | 频率与边界 |
|---|---|---|
| H1 发行物完整性 | 确认下载/交付的归档与已验发行物一致 | 每个发行归档一个摘要；交付/接收边界校验，复用已有结果，不递归给回执套摘要 |
| H2 关键输入或验收对象身份 | 没有可靠不可变版本可用时，确认实际消费/验收的是同一关键内容，防止复用已过期结果 | 限于必要对象，在绑定或内容变化边界计算；稳定版本足够时不用；不扩展为每个临时文件/阶段/日志的全套摘要 |

禁止为每条需求、每轮聊天、每个步骤、每份回执默认增加 SHA-256；禁止重复聚合/递归 Hash 链、每次工具调用扫描整个工程、手工复制 Hash、Hash 变化即重冻结全工程，以及用“Hash 全通过”替代功能验收。不能只换成另一种校验算法或签名继续同样的滥用。

W5 先盘点现有生成器、Validator、Schema、事件/授权链和打包中的 Hash：对象、实际消费者、发现变化后的动作，以及 ID/版本/事务是否足够。对白名单外用途连同上下游合同一起删除或替换，不保留无人消费的旧字段，也不建设新的 Hash 治理平台。以少量迁移对照和回归证明结果，而非再为每个删除动作新增证书。

删除 Hash 不删除业务校验、输入合法性、关系约束、路径隔离和实际运行证据。H2 仍需检测相关产物变化，不能仅靠路径相同或时间戳相同断言内容未变。只失效真实受影响的验收依赖。

旧不可变 Candidate/授权/事件链不改写；必要的历史读取隔离在旧兼容路线，不能把旧全量 Hash 机制带入新通用路线作为默认要求。本轮只制定替换方案，不直接移除现有受约束合同。新路径实施时 Producer、Validator 与测试必须同时更新。

### 7.4 比例适当的安全和测试

保留路径隔离、凭据保护、真实授权、主要失败与恢复回归；不把向他人分发本地工具升级为多租户或跨组织攻防平台。威胁模型仍是每位用户在自己的 Codex 和本地工程中操作，但不能假设对方拥有作者的环境、知识或账户。

验证是否值得增加，以“能发现哪个实际可达错误、发现后怎样改变处理”为依据。当前仓库仍要求实现变更后完整 unittest；工程指令正式更新前照常遵守。拟采用开发中相关测试、集成里程碑完整回归、发行前完整回归与真实 E2E，不为每次微小编辑重复昂贵检查。

## 8. 真实端到端验收设计

### 8.1 验收工程与场景

**首要场景：完整 PRD → 经人工确认的搭建文档 → 新工程 Coding Harness。** 建议使用范围有限、功能完整的小型任务管理 API/CLI 项目，PRD 明确用户流程、数据、状态、接口、异常和验收。上游结合开发需求形成文档并展示，取得实际人工确认后，Foundry 据此建立项目适配的 Coding Harness；随后在该 Harness 中由 Codex 完成定义的开发范围、运行真实命令/API、通过功能测试并修复一个可复现缺陷。至少包含两个真实依赖的工作包以及本地确定性验证，不接受纯文档或脚手架交付。

**留出场景：项目说明 + 既有仓库 → 经人工确认的搭建文档 → Coding Harness。** 建议使用 CSV 质量报告 CLI 的增量开发项目，提供明确需求、已有代码和测试，先确认搭建文档，再验证工程识别、保留既有功能、不覆盖无关改动、任务接续和变更后回归。业务不同但使用同一个 Foundry 包，不向核心加入案例 ID 分支。材料与评测答案分开，需求本身不对建设者隐藏。

v0.1 的文档检索/CSV 业务 Harness 是建议样例，不是已获准执行的工程；本版把必要验收优先改为用户新增的 Coding Harness 场景，复用可用材料，避免无必要扩成四套工程。具体业务样例仍可替换，但 PRD 新建与项目说明改造这两个输入场景、Codex 实际使用及本地处理验证不能省略。用例代码只留在目标工程/验收材料，不成为 Foundry 专项。

### 8.2 从发行物到目标结果的验收顺序

1. 干净的独立接入环境取得拟发布的 Foundry 包，仅按公开文档、声明依赖和操作者合法的 Codex 登录接入；不得读取原开发仓库、原聊天或随包复制作者账户状态。
2. 通过上游入口提供需求材料，验证读取和必要问答、输出搭建文档、用户 Review 并确认，再进入 Foundry。额外核对“没有问题、后台 PASS”仍会交付文档并停止等待；不要求用户手工编写内部 JSON/Hash 或重填完整 PRD。
3. 明确实际目录、模型服务与预算后，由该包真实生成并构建 Coding Harness，完成任务依赖、独立验收和连续推进。
4. 按正式方式在 Codex 中加载生成的 Harness，完成对应场景的开发任务并运行实际应用/命令；检查功能和最终结果，而非只检查进程退出或文件存在。
5. 对一个明确缺陷观察拒绝、范围内修复、复验及恢复推进；对受支持中断核对状态、结果与作用次数。尽量用本地步骤覆盖进程边界，不反复消耗模型。
6. 使用同一个 Foundry 包完成留出工程。若需要修复 Foundry，记录通用缺陷，重新构建包并复验受影响工程；不得宣称旧包已通过。
7. 对最终发行物确认基本完整性，形成支持环境、实际场景、关闭缺陷和已知限制说明。

验收分开记录本地测试、真实模型构建、生成 Harness 实际使用、安装/加载后运行、独立环境接入，以及确有发生的真实他人试用。必须执行项被跳过时记录 NOT_RUN/BLOCKED，不能合并为总 PASS。

### 8.3 他人接入 Codex 的发布标准

首发提供一种清楚、可验证的正式接入方式及快速开始，不要求同时实现全局 Skill、Plugin、SDK 等多条分发路线。安装/加载方式在 W6 依据现有产物验证后确定，不在文档中虚构现成安装命令。

发行内容至少包括必要源代码/运行资源、项目入口、声明依赖及版本范围、许可/第三方声明、最小示例 PRD/项目说明、运行与恢复说明。不得包含作者凭据、私有绝对路径、聊天历史、旧运行状态或依赖原 workspace 的临时补丁。不能静默覆盖用户已有 Codex 全局配置、项目指令或未提交代码。

必须在不依赖作者工程上下文的独立用户环境中，以实际 Codex 完成接入、建设和目标验收。使用新会话、干净项目配置、发行物和公开说明，隔离原开发仓库及私有运行状态；仅换一个目录但仍能回读原 workspace 不够。账户由当前操作者合法登录，不要求新增账号，不复制或分享凭据。发现文档缺步骤或依赖缺失，应修复发行物再复测，不能靠临场手改目标源码通过。

可由自动化 Agent 或独立操作者复现上述接入路径，不强制增加外部人工审批或等待第三方试用作为常规发布门。真实他人试用是有价值的附加证据，但没有实际发生时不得宣称“已有其他用户验证”。若缺少独立环境或真实 Codex 运行条件，记录未验收；其他已授权工程工作可继续。对外结论准确区分“独立环境复现通过”和“真实他人试用通过”。

## 9. 发布门、版本与停止条件

发行前全部满足：

1. 既有核心、通用生成和启动回归通过；产品 Manifest 和用户入口与实际能力一致。
2. G1–G13 均有适用证据，无缺失、陈旧或用静态检查冒充运行的项。
3. 实际 Astra/Codex 构建、连续 Workpack、独立验收、修复和恢复已观察到。
4. PRD 新建与项目说明改造工程，从待发布 Foundry 包建出 Coding Harness，并由 Codex 实际完成约定开发任务与功能验收。
5. §1.2 的已有专项已从生产路径和发行包剔除，而非仅默认关闭；无核心改动才能接入普通新项目的隐藏要求，无开发机私有依赖。
6. 范围内已知缺陷全部关闭；范围外限制公开说明。若需要调整承诺范围，先由用户决定，不能自行削减后宣称原目标已达成。
7. 生产 Hash 仅限 H1/H2 基本用途，白名单外用途已删除/替换；普通使用不需要人工输入 Hash，实际行为验证没有缩水。
8. 干净独立接入环境仅凭发行包、公开文档和合法 Codex 登录成功完成接入、搭建与目标使用；作者原工作区测试不能代替，也不把自动化复现冒充真实他人试用。
9. 文档、安装方式、能力说明、产品版本和实际包一致；发布/推送按明确授权执行。

文档计划、代码提交、版本号提升、核心 PASS、Candidate 静态 PASS 和模型完成消息，都不能单独关闭本目标。不预先承诺 3.0；版本提升应由实际兼容性变化决定，不用版本号代替完成证据。

预算用尽、缺少真实环境/授权或无法消除的副作用不确定性是可解释的停止状态，不是“已完成”。可以继续推进不依赖该阻塞的工作，但不能以无限重试掩盖阻塞。
