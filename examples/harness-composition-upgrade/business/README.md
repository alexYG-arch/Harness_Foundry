# R3 非编码业务验收材料

这些是 S1 的合成任务、独立预期和后续接入准备，尚未由交付的 Harness 执行业务。三个目录分别覆盖 PRD＋设计、数据计算推理、市场调研；共用虚构的「邻里预约」背景，不是真实客户、账目、调查或市场证据。`manifest.json` 是本示例的普通索引，不是新协议或运行时 Schema。

输入和期望先于业务运行固定。后续实施方读取各组的任务、`inputs/`、明确选定的 `workflows/` 及用户定制；外层把 `expected.json` 与 `counterexamples.json` 放入独立检查器的只读输入。不要把答案键直接复制成业务输出，也不要只凭生成方自评接受成果。开放的文字和设计允许不同正确表达，不设统一分数或逐任务人工批准。

每组 `manifest.json` 的 `outputs` 列出待生成的成果，**现在没有这些结果**。检查实际产出时仍回到原输入；尤其设计不能只与可能漏项的 PRD 比较。`counterexamples.json` 是用于检查判定路径的错误样本，不是一次真实执行失败报告。

| 组 | 独立预期覆盖 | 真实执行还需完成 |
|---|---|---|
| PRD＋设计 | 来源需求、冲突、空/错/离线状态、业务与视觉/交互一致性 | 交付工作流实际加载、PRD 和原型生成、浏览器渲染及交互取证、升级后重做 |
| 数据计算推理 | 手算、去重/修订、单位/时间、分母、缺失与推断边界 | 交付工作流实际读取计算、解释结果、独立比对、升级后重算 |
| 市场调研 | 有日期位置的固定来源、冲突、不能外推的结论 | 固定包综合，以及单独的真实公开检索/原文取回、升级后复核 |

三组工作流 V1→V2 都改变 Harness 的工作规则，而非仅替换题目输入。`upgrade.md` 说明改了什么、哪些用户定制必须保留、哪些行为重新验证。工作流文件是将来实际加载的版本样本；它们的存在不证明已经被模型加载，也不证明组成/应用已经获得控制器接受。

[工具接入准备](TOOL_PREPARATION.md)明确实际调用者、路径和取回方式。当前只确认项目 `.venv` 的 Python 可执行；没有调用模型、浏览器、原生设计应用或搜索。DOC/API 机制试点的恢复、计数、清理证据，只在同机制同条件时复用；它们不证明这些业务结果。
