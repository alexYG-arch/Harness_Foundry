# 能力选版、目标升级与合法接续

WP04 增加宿主侧 `upgrade.py`，将**完整的新选择**整理为新材料，并说明与上次选择的差异。它复用 `prepare.py` 的包、环境和隔离检查，不执行工具、不修改目标或控制库。原有直接文档搭建与追加不同能力的方式继续可用。

## 准备新材料

```sh
.venv/bin/python -B examples/capability-adapters/upgrade.py \
  --previous /宿主/旧材料/materials.json \
  --config /宿主/完整新配置.json \
  --output /宿主/新材料目录
```

上述路径是填写示意；输出目录必须是新位置，旧材料和证据保留。`--config` 沿用准备器的 `project_root`、`selections`、`environment_bindings`、可选 `base_materials`／`source_root`。`selections` 列出下一阶段仍需要的全部能力，不是只列变化项；每包明确目录、版本及适用任务。例如 Qt 保留 1、DATA 选择另一个已实际准备好的版本，二者都在清单中。这两个升级示例目前提供 Qt/CMake@1 和 DATA@1；测试中的第二版仅是临时工程夹具，没有发布新的业务版本。DOC、host-review 与看板的独立候选见 [候选分发说明](CANDIDATES.md)。

`base_materials` 使用项目自己维护的基础 request/scope 和来源，包含应保留的项目规则、定制与依赖，不能拿旧的能力混合结果作替换基底。这样不需要从混合 scope 中猜测哪些引用可删，也不会把旧能力来源或批准悄悄带到新版。已有准备器仍可将旧混合材料作为 base **追加不同能力**；替换同一能力时用完整配置，或按原材料流程明确重建。两种方式的语义不变。

Python API：

```python
materials, files, transition = build_upgrade(previous_materials, next_config, new_output)
materials, transition = write_upgrade(previous_materials, next_config, new_output)
```

`build_upgrade` 只读取并返回材料、文件字节及交接说明；`write_upgrade` 仅写新材料目录。`materials.json` 可沿原来源捕获、编译、文档确认、Readback 与授权路径使用。`transition.json` 列出包版本／内容／位置、工具入口、本机绑定、来源和相关任务的差异，以及旧选择当前是否仍匹配、旧诊断和新材料 readiness。它是解释材料，不是新协议、接受凭据、预算账本或控制器的重建决定。

旧包或绑定已变化时，旧记录继续解释旧事实；新配置可以明确修正缺依赖或路径，不因旧 INCOMPLETE 永久阻挡修正。相同版本名下内容有变化也如实列出，不把名称相同当成相同内容。新材料继续按实际配置检查；仅更换版本字符串、声明 READY 或生成交接说明都不构成实际使用验证。

要移除最后一个能力，可显式提供 `selections: []`，交回项目自己维护的基础材料；没有 base 时只得到空能力片段。仍由项目基础配置保存必要共享工具、来源和检查设置。零选择不把能力 `environment_bindings` 当成项目环境改写：同入口重述及已移除能力的残留项不阻挡；与项目同 ID 执行入口冲突的更正明确标为未应用／INCOMPLETE，需将所需变化写入项目 base.scope 后重新准备。准备器不会卸载 SDK、删除包目录、目标文件、历史接受或报告。发生写出 I/O 错误时保留局部材料，用新目录重新准备；不得将局部结果当成完整候选。

零选择仍处理项目 `preparation.verifier_inputs`：复用准备器既有的私有输入隔离、目标路径内容／共享标记冲突检查和去重，并在项目已声明 `verification_resources` 时合并 `checker_files`。去重不省略对任何原始私有来源的隔离核对，不能因同目标同字节而遗漏其中一个来源。合法 `shared:true` 原始输入继续可由双方使用；没有资源配置时保留检查依赖片段，不自动启用资源模式。无 base 的空能力片段保持可用；准备器不创建受保护副本。

## 交付给目标的内容与 G/C/N

独立维护的包可以并存。新建项目显式选择新目录；旧目标继续使用原绑定和原交付件。宿主在交给执行者前通过 `consume.prepare_call` 核对实际选中身份；完整材料和私有检查文件仍在宿主／检查域，不能将它们连同整包复制给生产者。目标只得到所需公开工具、运行依赖、项目配置及声明宿主。

当目标使用外部只读包，只更新明确的选择和调用绑定，并复验受影响行为即可。只有实际交付到目标、且允许用户定制的普通文件需要合并。此时复用 [现有 helpers](../harness-composition-upgrade/helpers/README.md)：

| 输入 | 应取的内容 |
|---|---|
| G | 该目标上次实际生成并保留的组件基线，可能已含项目适配；不能直接拿旧包源文件冒充 |
| C | 目标当前文件，包括用户修改 |
| N | 按新选择及当前项目要求生成的候选 |

`merge.py` 先生成独立候选和差异；冲突保留 C/G/N，明确处理后再形成 apply 意图。没有可靠 G 继续走原项目增量路径，不伪造基线。`apply.py` 只按明确 expected/desired 操作普通文件，先检查再替换；中断后已达到 desired 的文件不重复写，新的用户修改需先纳入意图。helper 结果不是 Harness 接受；完整检查后由原流程处理新基线和接受记录。

移除按明确拥有的文件／引用处理：某能力专用且不再使用的文件可以列 `remove`；共享文件由仍使用它的能力保留，一个文件只列一次；用户定制或非本组件拥有的文件保留，必要时 `leave-unmanaged`。这些是项目交付映射，不是全盘扫描或递归卸载。恢复旧版本也是一次明确的新选择／文件意图，沿实际当前状态检查；不承诺撤销任意外部服务副作用。

## 接到现有 rebind、只复验与恢复

真实目标工作继续沿 [原 CLI 的合法接续](../../docs/GENERIC_BUILD_CLI.md#显式同-program-接续) 处理；具体命令与字段以该文档为准，不从交接说明直接派发。

1. 保存完整新配置和新材料，把相关能力版本／生产依赖说明作为既有 SOURCE 输入，scope 绑定实际解释器／可执行项，LOCAL 工作包使用 `consume.prepare_call` 返回的新版 `local_argv`（包括脚本路径）。新选择不会自动改写原 Plan 执行命令；宿主 CODEX 工作流也要交接实际返回的调用入口。项目检查器和独立预期沿受保护入口，不能仅更改环境表而沿用不匹配的检查绑定。
2. 同一 Program 具备原接续条件时，新的 `prepare-build-authorization` 请求使用明确旧 `prepared_event_id` 的 `rebind_from`。后续批准和执行仍走现有入口；旧材料中的确认、批准和运行上下文不复制给新范围。
3. 核对 `read-build` 的实际投影：哪些接受复用、哪些只复验、哪些生产者及消费者待重建，以及跨 prepared 的累计预算。交接中的来源差异只是定位提示；核心同时核对生产、检查、产品和权限范围签名。`source_read_roots` 当前属于整个检查范围，路径变化可能使其他已接受任务也需复验，不能承诺任何变更永远只影响一个任务。
4. 只改检查依赖／检查环境且生产和产物仍满足原条件时，可走既有只复验；实际新验证会消耗一次尝试，旧生产不重放。生产来源变化则由核心决定重建。`NOT_DISPATCHED` 仍保留实际消耗，不据此认定业务修复失败；未知副作用仍按原恢复规则处理。
5. 完整 command／报告捕获后的中断，沿原恢复入口收尾归档、清理和接受，不重新调用工具、分配资源或增加同一尝试计数。新检查与恢复是两件事；新增必要验证记录真实新消耗，不能伪装成恢复。

没有第二套预算／重试／恢复记录，也不迁移 Program 到另一设备。第二设备重新解析环境并独立验证，旧设备证据保持其原范围。
