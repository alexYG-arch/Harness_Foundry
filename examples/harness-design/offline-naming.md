# 例示：离线素材命名检查

这是公开开发设计片段，未执行，也不是完整待批准合同。实际项目仍补齐来源版本、工具和读写域等信息，再按[现有流程](../../docs/GENERIC_BUILD_PLAN.md)展示并确认。

## 示例原需求

制作组已有素材目录及文字命名规则。希望在新批次素材到来时，得到违规文件的位置、违反的具体规则和改名建议；原文件保持不变。用户还希望在后续任务中检查自己修改后的名称清单，确认先前问题是否已消除。命名规则不明确的情况列为待决定，不自行增加规则。只需要本地检查，不需要检索网络或读取素材内容。

## 可以怎样设计

交付目标是一套能反复接受新目录或名称清单的检查 Harness，而不只是当前批次的错误列表。规则解释、调用入口和结果对应关系随交付保留。普通输入换批时不改 Harness；新规则改变合同，按实际范围处理。

| 需求 | 方案与可观察结果 |
| --- | --- |
| 定位违规项并解释 | 从公开规则定位每条判断依据；输出相对文件位置、规则引用及建议 |
| 不改原文件 | 检查只读输入，建议写到声明的结果目录；独立核对原文件没有变化 |
| 后续检查已修改清单 | 使用同一入口的清单输入，关联原问题和当前名称；不把未确认的建议当成已执行改名 |
| 规则有歧义 | 输出具体未决口径及受影响项，不伪造通过或失败 |

一种合法方案是交付简短宿主说明和单个本地脚本，由 Codex 读取规则、调用脚本并解释结果。另一种是复用项目已有扫描器，以薄配置和适配入口输出相同业务信息。两者都可以不选外置能力包；只要规则处理和后续调用足够明确，不必加入数据库、常驻服务、多个代理或额外模型调用。

若项目已有工具本身就提供全部所需行为，Harness 只补调用约定、任务记录和结果解释。目录扫描与规则判断可合在一个程序，也可分开；独立检查不以文件名、模块数量或相同输出排版作为正确性。

## 衔接与检查

设计时推演“公开规则＋当前输入→实际检查入口→结果→下一次清单检查”。明确路径解释、字符比较等实际影响结果的口径，避免把开发机路径写进交付。范围不包含改名，就不生成或执行改名命令。

宿主先从原规则制定独立预期，以另存的名称实例检查合法项、违规项和歧义项；生产者可以读取规则及公开开发实例，不能读取保留答案。观察入口是否真正处理了输入、建议是否对应原项、原文件是否保留，而不只检查结果文件存在。必要负例只围绕这些已提出的承诺。

实际验证若要证明同版承担两种任务，应在新会话先完成批次检查，再由另一个新会话用交付件检查用户修改后的清单；两次都记录实际入口和输入。这里的两任务来自示例原需求，不是所有 Harness 的默认义务。没有这样的使用证据时，只报告设计或开发检查状态。
